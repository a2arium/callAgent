# How-to: Support StageFacade in the Framework

Use this guide when you maintain the callagent framework and want StageFacade to be a safe, first-class control-plane feature rather than a thin helper with inconsistent behavior.

## Goal

Make StageFacade:

- consistent across agents
- runtime-enforced, not convention-only
- visible in TurnTrace
- easy to test with the official harness
- hard to misuse from Policy or Learning

## Non-goals

- moving business logic into stage management
- making StageFacade a full statechart engine
- replacing `MentalState` with control-state marks

## What the framework must guarantee

If the framework recommends StageFacade, it must guarantee these behaviors:

1. stage is stored in **control state**, not in `MentalState`
2. stage invariants are checked consistently
3. autoMarks are applied consistently
4. `onEnter` hooks run consistently
5. stage transitions are visible in TurnTrace
6. stage transitions are testable in the official harness

If these are not guaranteed, StageFacade will drift into a best-effort helper and teams will work around it.

## The runtime contract for StageFacade

StageFacade should be treated as part of the runtime control-plane contract.

### Required capabilities

The runtime should support these operations:

- `Stage.get(ctxOrEnv)`
- `Stage.set(ctxOrEnv, nextStage)`
- `Stage.is(ctxOrEnv, stage)`
- `Stage.assert(ctxOrEnv)` or equivalent invariant validation
- `Stage.summary(ctxOrEnv)` for trace/test output (recommended)

You may expose fewer or differently named methods, but the framework must provide a small stable API surface for stage operations.

## Step 1: Keep stage storage in control state only

Framework rule:

- stage must live in control/pending state or an equivalent runtime-owned control surface
- stage must not be written into `MentalState`

Recommended runtime shape:

- current stage
- stage-related marks
- pending tokens
- optional stage transition history for diagnostics

If users are expected to store stage in raw `controlVars`, document that as public surface. Otherwise, hide it behind StageFacade.

## Step 2: Define invariant semantics precisely

The framework must define exactly what stage invariants mean.

### `require`

Recommended semantics:

- the referenced key/path must exist
- value must not be `undefined`

### `forbid`

Recommended semantics:

- the referenced key/path must be absent or `undefined`

Do not leave this ambiguous. If some teams treat `false` as forbidden and others treat only “missing” as forbidden, the same config will behave differently.

### Nested path rules

If you support paths like:

- `fetch.token`
- `completed.called`

then document:

- path separator
- whether arrays are supported
- whether missing parent objects are allowed
- what happens when path resolution fails

## Step 3: Apply stage transitions atomically

A stage change should be a single runtime operation.

When `Stage.set(...)` runs, the framework should do this atomically and in order:

1. read current stage
2. validate transition request (if transition rules exist)
3. apply new stage
4. apply autoMarks for the new stage
5. validate invariants for the new stage
6. run `onEnter` for the new stage
7. record stage transition in TurnTrace

If any required step fails, the runtime should either:

- reject the stage transition before it becomes visible, or
- transition into a structured failure state

Do not allow partially applied stage transitions.

## Step 4: Restrict what `onEnter` may do

StageFacade is part of the control plane. `onEnter` must not become a hidden effect runner.

### Recommended framework rule

Allow only **telemetry-style runtime methods** inside `onEnter`.

Allowed examples:

- `ctx.progress(...)`
- `ctx.complete(...)` if completion is defined as runtime status emission

Not allowed:

- tool calls
- LLM calls
- child-agent dispatch
- user replies
- input requests
- external writes

### Implementation options

#### Option A — soft restriction

Document the allowed methods and rely on review/tests.

#### Option B — strong restriction

Pass a restricted `StageEnterContext` to `onEnter` exposing only safe runtime methods.

Example:

```ts
type StageEnterContext = {
  progress(pct: number, message: string): void;
  complete(pct: number, message: string): void;
};
```

This is the safer design.

## Step 5: Support typed control keys

If StageFacade uses string paths, the framework should reduce stringly-typed drift.

Recommended options:

### Option A

Allow users to define a typed key map and reuse it in invariants/autoMarks.

### Option B

Add a helper in the framework for typed control keys.

Example shape:

```ts
const ControlKey = {
  fetchToken: 'fetch.token',
  validationToken: 'validation.token',
  completedCalled: 'completed.called'
} as const;
```

Even if keys remain strings at runtime, the framework should encourage one shared vocabulary.

## Step 6: Expose stage transitions in TurnTrace

TurnTrace should show stage activity clearly.

Minimum stage-related trace fields:

- `stageBefore`
- `stageAfter`
- `stageTransition?: { from: string; to: string }`
- `stageAutoMarksApplied?: string[]`
- `stageInvariantChecks?: { required?: string[]; forbidden?: string[]; ok: boolean }[]`
- `stageInvariantError?: InvariantError`

Why this matters:

- stage bugs are otherwise hard to debug
- stage transitions are central to await/resume flows
- LLM-generated changes are safer when traces show control-plane consequences

## Step 7: Add harness support

The official harness should support stage testing directly.

Recommended helpers:

- `currentStage()`
- `expectStage(before?, after?)`
- `expectStageTransition(from, to)`
- `expectInvariantError(code)`
- `seedControlState(...)`
- `seedPending(...)`

Recommended tests:

- valid transition applies autoMarks
- missing required key rejects transition
- forbidden key rejects transition
- `onEnter` runs once per entry
- stage transition appears in TurnTrace

## Step 8: Keep Policy and Learning separated by API design

The framework should make misuse harder.

### Policy

- do not pass stage or env into Policy
- Policy should receive only `MentalState`

### Learning

- Learning may see observations and previous action
- Learning should not receive mutable control-state setters

### Execution / Transition

- these are the proper places to use StageFacade for control changes

This should be enforced by callback signatures where possible, not just documentation.

## Step 9: Decide what is public surface

If the framework recommends StageFacade publicly, then these become part of the public contract:

- how to define stage unions
- invariant semantics
- autoMark semantics
- onEnter semantics
- where stage is stored conceptually
- what StageFacade methods are stable
- what TurnTrace guarantees exist for stage transitions

If any of these are unstable, do not imply that users should depend on them.

## Recommended acceptance criteria

StageFacade support is ready when:

1. stage transitions are atomic
2. invalid transitions fail loudly and structurally
3. autoMarks apply predictably
4. `onEnter` cannot perform unsafe effects
5. TurnTrace shows stage transitions and invariant failures
6. harness tests can assert stage behavior without internal hacks

## Common pitfalls

### Pitfall 1: StageFacade is only a thin setter

Symptoms:

- no invariant checks
- no trace visibility
- autoMarks applied inconsistently

Fix:

- move invariant application and trace emission into runtime-controlled stage transition logic

### Pitfall 2: Policy starts depending on stage

Symptoms:

- users ask for stage in Policy because the framework exposes it everywhere

Fix:

- keep Policy callback signature minimal
- document stage as control-plane only

### Pitfall 3: onEnter becomes an effect tunnel

Symptoms:

- tool dispatch or LLM calls happen inside onEnter

Fix:

- restrict onEnter context to telemetry-only methods

### Pitfall 4: string keys drift across agents

Symptoms:

- many slightly different path names for the same control meaning

Fix:

- provide a shared key vocabulary or typed helper pattern

## Fast maintainer checklist

Before shipping StageFacade support, confirm:

- invariant semantics are documented precisely
- stage transition is atomic
- onEnter is constrained
- TurnTrace includes stage transition data
- harness supports stage assertions
- Policy cannot accidentally depend on stage
- examples use only public surface
