Phase 4 is a deliberately breaking phase across the conversation API surface (selector policy, topic archive, manifest schema), the durable transport layer (`DurableSubscription`), and the manifest `communication` capability bag. The migration documents above are mandatory and must be written **incrementally alongside implementation** — one migration document per sub-phase, committed in the same change as the code that ships the breaking surface, not after the fact.

> **Sub-phasing rationale.** Phase 4 is intentionally split into **four shippable sub-phases** (`5.4a` → `5.4d`). Each sub-phase is independently mergeable, ships its own migration doc, and updates the canonical example agents. This mirrors the Phase 2 split (5.2 / 5.2a / 5.2b). The sub-phases are sequenced by infrastructure dependency:

> | Sub-phase | Sub-scope | Why this order |

**Scope:** Phase 4 closes every remaining "Phase 4" deferral in [`apps/docs/planned_architecture/multi-agent-communication.md`](../planned_architecture/multi-agent-communication.md), **plus four carry-over items that the arch doc normatively requires but previous phases shipped incomplete** (see the audit list after item 10). Concretely:

1. **Cross-runtime transport adapters** — `IEventBus` + `MessageLog` + `DurableSubscription` get production broker implementations (Kafka, NATS JetStream) selected by runtime config; the in-memory + DB-backed defaults remain available for tests and single-process deployments. The "durable log is the stronger truth" guardrail (`multi-agent-communication.md` § "Conversation log is the stronger truth") becomes mechanically enforceable across runtimes.
2. **`DurableSubscription` port** — first-class durable subscription contract (`ack` / `nack` / cursor groups) under `packages/core/src/public-types/messageLog/**`, additive to `MessageLog`. Phase 3's `MessageLog.replay` is the read seam; `DurableSubscription` is the consumer seam. This is the surface Kafka / NATS / JetStream adapters implement to deliver durable messages with retry / dead-letter semantics. **Naming decision (committed):** drop the `I`-prefix. The planned-architecture doc uses `IDurableSubscription` colloquially, but Phase 3 already set precedent with `MessageLog` (no `I`) for the same reason — user rule prefers `type` aliases over `interface`-prefix convention. The planned-arch doc is updated in the 5.4b migration doc to match.
3. **Selector turn-taking policy** — implements the `'selector'` topic turn policy from `multi-agent-communication.md` § FR-2.4. The framework consults a registered, deterministic `TopicSelectorPolicy` that chooses the next speaker from the current member set + shared topic context (the v1 implementation uses a member-description-based deterministic tie-break; LLM-driven selection is a future-pluggable variant outside Phase 4). Joins the existing `broadcast` / `round_robin` / `explicit_recipient` selectors as a fourth `TopicSelector` kind: `selector_policy`.
4. **Typed shared topic documents** — `ctx.conversation.readProjection(ref, projection)` and `ctx.conversation.appendSignal(ref, ...)` per `multi-agent-communication.md` § FR-2.6 v2. v1 implementation is **not CRDT-backed** — the totally-ordered topic log + a typed projection registry give cross-member shared state without CRDTs (per § "v1 default: message log only + projections"). CRDT-backed shared docs remain a Phase 4+ extension point with the same public surface.
5. **Topic archive lifecycle** — Phase 3 closed `archive` for threads; Phase 4 brings topics to parity. `ctx.conversation.archive(topicRef, ...)` becomes the typed entry point; `ArchiveUnsupportedForTopics` (Phase 3 placeholder) is **deleted** from the typed error union **and** the accompanying `throw new Error('ArchiveUnsupportedForTopics')` runtime path in `ConversationService.close` is removed (see § 5.4a.0 for the broader string-throw cleanup).
6. **Manifest `communication` capability extensions** — `multi-agent-communication.md` § "Manifest extensions" → "Future expansions" lands. Adds `threadable`, `wakeOnTopicMessage`, `acceptedSpeechActs`, `acceptedContentTypes`, `jsonSchemas`, `topicPoliciesSupported` to `AgentRuntimeManifestSchema.communication`. The framework uses these for typed pre-dispatch validation (sender-side and recipient-side) and for capability advertisement to peer agents (e.g. a topic policy that probes `topicPoliciesSupported` before promoting a member to moderator under `selector_policy`).
7. **Custom topic stop policy registry** — `TopicStopPolicy` `kind: 'custom'` (`multi-agent-communication.md` § FR-2.5) becomes executable. Stop policies are registered via runtime configuration (`StopPolicyRegistry`), not inlined as raw functions; serializable across runtimes; testable in isolation. **Carry-over scope:** the whole `TopicStopPolicySchema` (all five branches — `maxTurns | maxRounds | timeout | signalBased | custom`) ships in 5.4a; Phase 2 normatively required `stopPolicies: readonly [TopicStopPolicy, ...TopicStopPolicy[]]` on every topic create (`multi-agent-communication.md` lines 136 & 965) but the surface was never implemented. Phase 4 treats this as part of the closeout, not as an "additive fifth branch".
8. **Wire `communication.threadTtlMs` into the runtime** — Phase 3 added the manifest schema field but never plumbed it into `TaskEngine`/`ConversationService`'s `resolveThreadTtlMs` (still hardcoded to `1h`). Phase 4 finishes the wiring; this is a small but real correctness item. **Sequenced as 5.4a step 0** so it can ship independently of the larger 5.4a surface.
9. **Speech-act vocabulary widening** — `SpeechActSchema` today is the Phase 1 closed enum `['question','answer','inform','request']`. Phase 4 expands it to the planned-architecture vocabulary (adds `'signal'`, `'task'`, `'followup'`, `'vote'`, and a curated `'system.*'` namespace) because 5.4d (`appendSignal`, `acceptedSpeechActs`) and the signal-based stop policy in 5.4a (`signalBased`) cannot close their surfaces against today's enum. This is a breaking widening; consumer exhaustiveness on `SpeechActSchema` fails compile (Rule 4; §12 5.4a).
10. **`SignalKind` closed vocabulary** — `appendSignal` writes a `signal` speech act whose `signalType` is not a free string. Phase 4 introduces `SignalKindSchema` (core vocabulary + `x-` extension namespace) used by both `appendSignal` and the system-level signals in 5.4b / 5.4d (`topic.backpressure.changed`, `topic.policy.unsupported`, etc.). This keeps the durable log + projection inputs in closed vocabulary (Rule 4).

### Out of scope (still deferred to Phase 5+)

- **CRDT-backed shared topic documents** — Phase 4 ships the `readProjection` / `appendSignal` API and the typed projection registry. CRDT-backed implementations (e.g. Yjs / Automerge under the same port) are a future plug-in, not Phase 4 work.
- **LLM-driven `selector_policy` variants** — Phase 4 ships a deterministic, member-description-based selector policy. LLM-call-from-policy is explicitly **not** Phase 4 (and is anti-Rule under [`apps/docs/3-how_to_keep_policy_pure.md`](../3-how_to_keep_policy_pure.md) without a Learning-side staging surface). LLM selectors arrive in a later spec under the same `TopicSelectorPolicy` registry seam.
- **Distributed topic re-balancing** — multi-runtime topics use the broker's partition / consumer-group semantics. Re-balancing strategies (sticky / cooperative-sticky / range) are inherited from the underlying broker; Phase 4 does not invent a framework-level rebalancer.
- **Per-broker exactly-once semantics** — Phase 4 standardizes on **at-least-once** delivery; idempotency at the message-log layer (`MessageLog.findByIdempotency`) collapses duplicates. Exactly-once over Kafka transactions is an opt-in adapter hardening that postdates Phase 4.
- **Cross-tenant topic federation** — out of scope. All Phase 4 transport adapters honor the existing `tenantId` boundary; cross-tenant sharing is a separate feature with its own auth model.
- **Schema migration tooling for shared topic projections** — Phase 4 ships the projection registry and reducer pattern; auto-migration of historical topic logs into a new projection version is a separate hardening pass.

## Problem Statement

Phase 3 closed thread lifecycle (close / archive / TTL), introduced the `MessageLog` port, reimplemented `sendTaskToAgent` as conversation sugar, and stamped trace linkage. What it deliberately left open:

- The conversation log is durable, but the **transient bus is single-process only**. `OutboxPublisher` polls the outbox table and **logs the dispatch** — there is no actual bridge from the outbox to the configured `IEventBus`, and no broker adapter behind `IEventBus`. Multi-runtime conversation is conceptually documented (`multi-agent-communication.md` § "EventBus and transport evolution") and operationally absent.
- `MessageLog.replay` is a paged read, not a durable subscription. There is **no `DurableSubscription` type, no consumer-group concept, no cursor / ack / nack** anywhere in the code. Cross-runtime delivery has no consumer-side seam.
- `TopicSelector` ships three kinds — `broadcast`, `round_robin`, `explicit_recipient`. The `selector_policy` (or `'selector'`) kind from `multi-agent-communication.md` § FR-2.4 has **no schema, no registry, no resolver, no test**. Topics that need a custom turn-taking policy must today fall back to `round_robin` or `explicit_recipient`.
- `TopicStopPolicy.kind === 'custom'` is mentioned in the planned-architecture doc but **has no registry**, **no resolver**, **no in-code execution path**. Stop policies are encoded as `maxTurns | maxRounds | timeout | signalBased` only.
- Topic **archive** is missing. Phase 3 ships thread archive end-to-end and even introduces `ArchiveUnsupportedForTopics` as a temporary typed error to catch the unimplemented case. Phase 4 must promote topic archive to a first-class verb and **delete** the placeholder error in the same change.
- The manifest `communication` block (in `packages/types/src/agent/agentRuntimeManifest.ts`) declares only `autoJoinInvitedTopics` and `threadTtlMs`. The Phase 4 capability surface (`acceptedSpeechActs`, `acceptedContentTypes`, `jsonSchemas`, `topicPoliciesSupported`, `threadable`, `wakeOnTopicMessage`) is undeclared. The framework cannot pre-validate that an agent accepts a given speech act, content type, or topic policy before dispatch — every check happens reactively, by the recipient agent's own code.
- `communication.threadTtlMs` is declared in the manifest but **not consumed**. `TaskEngine` constructs `ConversationService` with `resolveThreadTtlMs: () => 3600000` (a hardcoded 1-hour fallback) regardless of what the agent's manifest says. This is a Phase 3 correctness gap.
- There is **no `ctx.conversation.readProjection` or `ctx.conversation.appendSignal`**. Topic shared state today is reconstructable from the message log only by reading via `MessageLog.read` and folding manually inside the agent — which violates the policy-purity / Learning single-writer rules unless the projection is computed inside Learning.
- `OutboxPublisher` runs as a singleton, polls every 500 ms, and reads `MEMORY_DATABASE_URL` directly. Adapter selection (`eventBus.adapter`, `messageLog.adapter`) per `multi-agent-communication.md` § "Adapter strategy" is **not config-driven** — there is no config bag and no place to plug in a real broker.

## 🏗 Requirements

This section is grouped by sub-phase. Within each sub-phase, requirements are numbered. Cross-sub-phase requirements are marked explicitly.

##### 5.4a.0.ii — `SignalKindSchema` introduction

**Files:**
- `packages/core/src/public-types/conversation/signal.ts` **(NEW)**
- `packages/core/src/public-types/conversation/index.ts` **(MODIFY — re-export)**

Public contract:

```ts
/**
 * Closed vocabulary of system-level signal kinds emitted or written into the durable log.
 *
 * Core vocabulary is additive-only and stable. Integrators needing custom signals MUST use
 * the `x-<name>` extension namespace. The framework refuses any other free-form string at
 * the `appendSignal` boundary.
 */
export const SignalKindSchema = z.union([
    z.enum([
        // Backpressure (5.4b)
        'topic.backpressure.changed',
        // Topic policy capability advertisement (5.4d)
        'topic.policy.unsupported',
        // Topic lifecycle (5.4a)
        'topic.archive.scheduled',
        // Capability validation (5.4d)
        'delivery.capability.rejected',
    ]),
    z.string().regex(/^x-[a-z0-9][a-z0-9._-]{0,118}$/),
]);
export type SignalKind = z.infer<typeof SignalKindSchema>;
```

Normative:

- **Closed core + `x-` extension.** Rule 4 honored for the core vocabulary; the `x-` namespace is a controlled open extension (string with a regex guard), not a free-form escape hatch. Validation failure is a typed `InvalidSignalKind` error at the `appendSignal` boundary (see 5.4d.3).
- **Write path.** Every `appendSignal` writes `speechAct: 'signal'`, `signalType: SignalKind` (closed), `signalPayload: JsonValue`.
- **Read path.** Projections that need to react to signals narrow `record.speechAct === 'signal'` and then switch on `signalType`; TS enforces exhaustiveness.

Public type (Zod-sourced):

```ts
export const TopicSelectorPolicyContextSchema = z.object({
    tenantId: z.string().min(1),
    topicId: ConversationIdSchema,
    senderMemberId: MemberIdSchema,
    members: z.array(ResolvedTopicMemberSchema).min(1),
    rotationCursor: z.string().nullable(),
    lastSpeakerMemberId: MemberIdSchema.optional(),
    sequenceNumber: z.number().int().nonnegative(),
    /** Opaque per-call params, validated by the registered policy. */
    params: JsonValueSchema.optional(),
    /** Wall-clock instant of the post call (resolved via Clock; never produced inside the policy). */
    nowIso: z.string().datetime(),
});
export type TopicSelectorPolicyContext = z.infer<typeof TopicSelectorPolicyContextSchema>;

export const TopicSelectorPolicyResultSchema = z.discriminatedUnion('kind', [
    z.object({
        kind: z.literal('selected'),
        recipients: z.array(ResolvedTopicMemberSchema).min(0),
        nextRotationCursor: z.string().nullable(),
    }),
    z.object({
        kind: z.literal('rejected'),
        error: z.discriminatedUnion('type', [
            z.object({ type: z.literal('PolicyParamsInvalid'), message: z.string() }),
            z.object({ type: z.literal('PolicyAbstain'), message: z.string() }),
            z.object({ type: z.literal('PolicyInternalError'), message: z.string() }),
        ]),
    }),
]);
export type TopicSelectorPolicyResult = z.infer<typeof TopicSelectorPolicyResultSchema>;

export type TopicSelectorPolicy = {
    /** Registry key. Must match the `policyId` in the `selector_policy` selector. */
    policyId: string;
    /** Optional Zod schema for the policy-specific `params` field; validated before `select()` runs. */
    paramsSchema?: z.ZodTypeAny;
    /**
     * Pure function. Must be deterministic given (context, members, rotationCursor, params).
     * No I/O, no clock calls, no randomness without a seed in `params`.
     */
    select(context: TopicSelectorPolicyContext): TopicSelectorPolicyResult;
};
```

`TopicSelectorPolicyRegistry`:

```ts
export type TopicSelectorPolicyRegistry = {
    register(policy: TopicSelectorPolicy): void;
    resolve(policyId: string): TopicSelectorPolicy | undefined;
    list(): ReadonlyArray<string>;
};
```

Semantic requirements:

- **Determinism (normative).** A registered `select(...)` MUST be deterministic. The framework asserts this in tests via the harness `withPolicyDeterminismGuard` helper that calls `select(...)` twice with identical context and rejects divergent results.
- **Purity (normative).** Policies receive `nowIso` from the framework (resolved via `Clock`); they MUST NOT call `Date.now()` / `process.hrtime()` / `Math.random()` directly. Violations are runtime-detected by the harness in `__strict__` mode (default `true` in tests).
- **`paramsSchema` is the source of truth (Rule 2).** When supplied, the registry validates the per-call `params` against it before invoking `select`. Validation failure → `TopicSelectorPolicyResult { kind: 'rejected', error: { type: 'PolicyParamsInvalid' } }`.
- **`PolicyAbstain`** is the documented hand-off for "this policy does not pick a recipient under the current context"; `ConversationService.post` falls back to `broadcast` semantics when a `selector_policy` abstains, and the trace records both the abstention and the fallback (see § 5.4a.3 trace stamping).
- **No public `any`.** `params` is `unknown` at the registry boundary and `z.infer<paramsSchema>` inside the policy.

`TopicSelector.ts` — extend `resolveTopicSelector(...)`:

- New input: `policyRegistry: TopicSelectorPolicyRegistry`.
- Branch when `selector.kind === 'selector_policy'`:
  1. `registry.resolve(selector.policyId)` → if `undefined`, return `{ ok: false, error: 'SelectorPolicyNotRegistered' }` (new error in 5.4a.4).
  2. If `paramsSchema` supplied, validate `selector.params` → on failure return `{ ok: false, error: 'PolicyParamsInvalid' }`.
  3. Build `TopicSelectorPolicyContext` (members already filtered by sender exclusion, sorted by `compareMembers`; `nowIso` from `Clock`).
  4. Invoke `policy.select(ctx)`.
  5. Map `TopicSelectorPolicyResult` to `TopicSelectorResolution`:
     - `selected` → `{ ok: true, recipients, nextRotationCursor }`.
     - `rejected` with `PolicyAbstain` → fall back to `broadcast` resolution (preserves topic liveness); fallback is stamped on the trace, not silent.
     - `rejected` with `PolicyParamsInvalid` / `PolicyInternalError` → `{ ok: false, error: 'PolicyParamsInvalid' | 'PolicyInternalError' }`.
- The existing `TopicSelectorResolution` discriminated union extends with the two new error kinds; exhaustiveness in `ConversationService.post` is enforced by TS (Rule 4).

`ConversationService.post` (~ConversationService.ts:1099–1228):

- Receives the registry through constructor injection (`deps.topicSelectorPolicyRegistry`).
- Routes the new error kinds to typed `ConversationError` branches in `FanoutSendReceipt.rejected` (`'SelectorPolicyNotRegistered' | 'PolicyParamsInvalid' | 'PolicyInternalError'`).
- Stamps `selectorKind: 'selector_policy'` and `selectorPolicyId: <id>` on the `MessageLog.append` call (extends `MessageLogAppendParams.selectorKind` with a sibling optional `selectorPolicyId: z.string().optional()` — additive Zod change, see § 5.4a.5 for the persistence side).

`MessageLogDeliverySchema.status` widens from `'delivered' | 'rejected' | 'queued'` to `'delivered' | 'rejected' | 'queued' | 'buffered' | 'throttled' | 'paused' | 'dead-lettered'`. Rule 14; consumer switches must add four cases.

`BackpressureManager` **is the sole budget owner** (normative):

- Adapters in 5.4c MUST NOT maintain their own independent backpressure budgets; instead they report per-consumer inflight counts / ack timing to a single injected `BackpressureManager` instance and consult its state before dispatch. The adapter contract test bag (5.4c.4) verifies this by asserting that identical `{buffer,throttle,pause}` thresholds produce identical state transitions across `InMemoryEventBus`, `KafkaEventBus`, `NatsJetStreamEventBus` under the same synthetic load. Rule 7 (purity of state-machine rules) is honored because the manager only consumes wall-clock time via an injected `Clock`.
- Per-(`tenantId`, `consumerId`) state machine:
  - `delivered` (default).
  - `buffered` (consumer has N un-acked messages; N > `bufferThreshold`, default 100).
  - `throttled` (un-acked count crossed the throttle threshold, default 200; subsequent dispatches are delayed by an exponential backoff window).
  - `paused` (un-acked count crossed the pause threshold, default 500; subsequent dispatches are queued and not sent until ack/nack drains the buffer).
  - `dead-lettered` (a single message exceeded `maxRetries`; the message is moved to `conversation_dead_letter`).
- Thresholds are configurable via `conversation.backpressure.{bufferThreshold,throttleThreshold,pauseThreshold,maxRetries}`.
- State transitions emit `system.policy` observations on the topic (member-fan-out): `{ kind: 'topic.backpressure.changed', from, to, consumerId, ts }` — agents observe their own throttle state and can adjust outbound cadence.
- `BackpressureManager` is deterministic under tests via injected `Clock`; thresholds and timers default to test-friendly values when `harness.useDeterministicBackpressure()` is called.

- `KafkaEventBus` implements `IEventBus`:
  - `publish` produces to a transient `events.<channel>` topic (configurable retention; default 1 hour).

 * is never populated at runtime; it exists so `readProjection(topic, projection)` can
 * return `ReadProjectionReceipt<T>` via inference — without requiring the caller to pass
 * `T` as an explicit generic (Rule 1 + Rule 15).

export type TopicProjectionToken<T> = {
    readonly projectionName: string;
    readonly stateSchema: z.ZodType<T>;
    readonly __projectionState?: T; // phantom-only; never assigned
};

export type TopicProjection<T> = TopicProjectionToken<T> & {
    /** Initial state factory. Pure. */
    initial(): T;
    /**

     * Determinism is contractual: two replays of the same log produce identical state.
     */
    reduce(state: T, record: MessageLogRecord): T;

/**

 * which `readProjection` consumes via inference. This is the Rule-1-compliant replacement

export function defineTopicProjection<T>(spec: {
    projectionName: string;
    stateSchema: z.ZodType<T>;

     * `resolveToken` below, which consumes a `TopicProjectionToken<T>` and returns

/**

Normative:

- **No `readProjection` by string name at the public surface.** Consumers MUST import the `TopicProjectionToken<T>` (e.g. `TopicTranscript`) or use `defineTopicProjection(...)` themselves. A `projectionName: string` overload is explicitly out-of-scope because it would erase `T` to `JsonValue` and defeat the typing goal.
- **Policy vs. Execution placement (decision):** `readProjection` is **Execution-only** — same placement as `sendMessage`, `post`, etc. It reads durable state via `MessageLog`, which requires runtime resources Policy does not (and must not — Rule 7 / Rule 8) touch. **Policy access to the same data happens via `conversationReducer` materialized state on `M.memory.conversation.<topicId>.projections.<projectionName>`** (already Learning's single-writer surface), NOT via `readProjection` from Policy. This resolves the contradiction in earlier drafts of this spec and in `multi-agent-communication.md` § FR-2.6 which previously conflated the two.
- **Learning-side pipeline for projection materialization:** `conversationReducer` gains a switch — when the `TopicProjectionRegistry` has a projection registered and the incoming record belongs to a topic, the reducer folds `projection.reduce(...)` into `M.memory.conversation.topics[id].projections[projectionName]`. This keeps Policy reads pure (Policy does not await anything) and Learning the single writer (Rule 9 of `mlo_architecture_and_extensibility.mdc`). Because `conversationReducer` runs once per observation, the memory view is eventually consistent with the durable log.
- **Consistency contract:**
  - `ctx.memory.conversation.topics[id].projections.<name>` (Policy): eventually consistent; lags durable state by at most one Learning cycle.
  - `await ctx.conversation.readProjection(topic, token)` (Execution): eventually consistent by default; `consistency: 'read-your-writes'` bypasses the cache and folds the log synchronously.
  - Both surfaces return state narrowed by the same `stateSchema`; both produce `ProjectionStateInvalid` on parse failure.

Semantic requirements:

- **`readProjection` is pure** at the API boundary: it folds `MessageLog.read({ conversationId, fromSequence: 0, limit: max })` (paginated under the hood) through the registered reducer. Caching is an implementation concern; v1 uses an in-process LRU keyed on `(topicId, projectionName, asOfSequence)`.
- **`appendSignal`** is a thin wrapper around `MessageLog.append` with `speechAct = 'signal'`, `signalType: SignalKind` (closed vocabulary), and `selectorKind = 'broadcast'` — it is a `system.policy`-class write that does not require recipient resolution. Invalid `signalType` at this boundary rejects with `{ type: 'InvalidSignalKind', signalType }` (added to `ConversationErrorSchema` in 5.4d.3).
- **Generic narrowing via token.** `ReadProjectionReceipt<T>` is inferred from the `TopicProjectionToken<T>` argument; the underlying schema yields `JsonValue` and narrows via the token's `stateSchema`. The runtime parses `state` against `stateSchema.parse(...)` before returning; mismatches produce `'rejected'` with `ProjectionStateInvalid`. Rule 1: no public `any`; `T` is recovered from the token, never passed positionally.
- **Read-your-writes (optional).** When `consistency: 'read-your-writes'` is set, `readProjection` calls `MessageLog.read` with `fromSequence: 0` and folds synchronously; eventually-consistent (default) may return a cached state.
- **Rule 15: simple + advanced.** Most users do not register custom projections; the default installation registers one built-in projection: `TopicTranscript` token (the linearized message stream). Advanced users call `defineTopicProjection({...})` and register the result.

#### 5.4d.5 — Pre-dispatch capability validation

**Files:**

Behavior:

- Before `MessageLog.append`, `CapabilityValidator.validate({ recipient, message })` is called for every recipient.
- Validation rules:
  1. `threadable === false` and message is a thread `startThread` → `RecipientNotThreadable` (new typed error).
  2. `acceptedSpeechActs` defined and message `speechAct` not in the list → `SpeechActNotAccepted`.
  3. `acceptedContentTypes` defined and any `content[].type` mime not in the list → `ContentTypeNotAccepted`.
  4. `content[].type === 'json'` with `schemaId` matching `jsonSchemas[schemaId]` → JSON-Schema validate; failure → `JsonSchemaValidationFailed`.
- Failures become typed `delivery.failed` observations to the sender; the message is NOT appended (Rule 11).
- For topic posts, validation runs per-recipient; selectively-failing recipients receive `delivery.failed` while accepted recipients still receive the message.

#### 5.4d.9 — Clean API constraints (5.4d)

1. `ConversationApi.readProjection(topic, token)` and `appendSignal(topic, ...)` are first-class; no public `any`; `T` is inferred from `TopicProjectionToken<T>` never passed as a positional generic.

7. Pre-dispatch capability validation produces typed `delivery.failed` observations; never silent acceptance of mismatched messages.
8. `topicPoliciesSupported` consultation is observable; never gates topic creation but stamps the trace.
9. `wakeOnTopicMessage` honored end-to-end; `false` is the default (preserves Phase 2's posture; agents must opt in).

## 11. Isolation and determinism guarantees (normative — applies to all sub-phases)

1. **Selector / stop policies are pure.** `select(...)` / `evaluate(...)` consume `nowIso` from the framework `Clock`; harness `__strict__` mode rejects clock / random calls (5.4a).
2. **Adapter contract tests are deterministic.** Each adapter contract bag uses an injected `Clock` and explicit ack / nack control; no real timeouts. Broker adapters use Testcontainers in CI (5.4c) but the contract is deterministic given the broker is healthy.
3. **Backpressure transitions are observable.** Every `delivered → buffered → throttled → paused → dead-lettered` step emits a `system.policy` observation; no silent state change (5.4b).
4. **Cursor persistence is transactional.** `DurableSubscription.ack` updates the cursor atomically with the durable record's "consumed" marker (5.4b).
5. **Topic archive transitions are atomic.** `topic.closed` + (optional) `topic.archived` ride one DB transaction (5.4a; mirrors thread transition from Phase 3).
6. **Projections are deterministic.** `TopicProjection.reduce` is pure; replaying a fixed log produces byte-identical state. Tests assert this with a replay-twice property test (5.4d).
7. **Capability validation runs before append.** When validation fails for all recipients of a topic post, the message is NOT appended (Rule 11; 5.4d).
8. **No silent message loss.** Cross-adapter contract tests assert at-least-once: every published message is delivered to every subscribed consumer at least once, even under simulated broker disconnects (5.4c).

## 12. No backwards compatibility posture (explicit — enumerated by sub-phase)

## 📜 Mandatory Migration Guides — one per sub-phase

Per the user requirement that **a full migration guide for the end user be created after each change**, Phase 4 ships **four** migration documents under `apps/docs/migration/`. ### Common contents (apply to each sub-phase migration document)

Each document MUST include the following sections (numbering aligned to the Phase 3 migration template):

10. **Examples** — link to the canonical example agents updated in the sub-phase.

## ✅ Acceptance Criteria

### Cross-sub-phase

1. **No public `any`** in any new or modified file under `packages/core/src/public-types/**` or `packages/types/src/**`.
2. **Zod-first** for every new public contract (Rule 2). No hand-written validators / type pairs.
3. **Discriminated unions are closed** (Rule 4): exhaustive `switch` with `default: never` compiles only when every branch is handled.
4. **Each sub-phase's migration document exists** under `apps/docs/migration/` and was committed alongside the corresponding code, not after the fact.
5. **`yarn build` and `yarn test`** pass across all workspaces (broker adapter tests opt-in via `RUN_BROKER_TESTS=1`).
6. **Phase 1 / 2 / 2a / 2b / 3 scenarios pass after their migrations are applied** (regression guard). "Byte-identical" is explicitly NOT required — Phase 4 is a deliberately breaking phase (Rule 14): the `SpeechActSchema` widening, `TopicStopPolicy` required-field, `ThreadNotClosed → ConversationNotClosed` rename, `ArchiveUnsupportedForTopics` deletion, `BusEventSchema` envelope, `DurableSubscription` port, `readProjection` token signature, and `MessageLogAppendParamsSchema.speechAct` narrowing all shift the wire/schema level. The regression guard is: each prior-phase test suite must pass once the prior-phase test fixtures are migrated per the 5.4a–d migration docs, with no semantic regressions inside each already-passing scenario (same observations emitted, same final state, same turn-trace shape for unchanged fields).

### 5.4a-specific

7. `TopicSelector` is a closed union with four kinds (`broadcast`, `round_robin`, `explicit_recipient`, `selector_policy`); adding a fifth is a breaking change.
8. `TopicSelectorPolicyRegistry` resolves `policyId` → policy at runtime; deterministic; `paramsSchema`-validated; pure under `__strict__` harness mode.
9. `selector_policy` with unregistered `policyId` produces typed `SelectorPolicyNotRegistered` (never silent).
10. `ctx.conversation.archive(topicRef)` is a first-class verb; `close(topicRef, { archiveAfter: true })` succeeds and emits `topic.archived`; `ArchiveUnsupportedForTopics` is removed from the typed error union.
11. `ThreadNotClosed` is renamed `ConversationNotClosed`; the old name does not compile.
12. `TopicStopPolicy` has five branches; `'custom'` resolves via `StopPolicyRegistry`; engine triggers `close` on `'stop'` decisions.
13. `communication.threadTtlMs` from the manifest reaches `ConversationService.resolveThreadTtlMs` end-to-end; the hardcoded fallback is removed; `null` disables TTL; undefined falls back to `conversation.thread.defaultTtlMs` (default 1 hour).
14. `TurnTrace` includes `selectorPolicy` stamping on every topic post that resolves a `selector_policy` (success or failure).
15. `TopicLifecycleSweeper` deterministically auto-archives closed topics after `autoArchiveAfterMs` when configured; default `null` (off).

### 5.4b-specific

16. `DurableSubscription` is a public port under `public-types/messageLog/**`; in-process default implementation passes the contract bag.
17. `OutboxPublisher` is constructed exactly once in the composition root with an injected `IEventBus`; the singleton export is deleted; dispatch calls `eventBus.publish`; failed publishes increment `retry_count`; exceeded retries route to `conversation_dead_letter`.
18. `MessageLogDeliverySchema.status` is a closed union with seven values; consumers narrow exhaustively.
19. Backpressure transitions (`delivered → buffered → throttled → paused → dead-lettered`) emit `system.policy` `topic.backpressure.changed` observations and are stamped on `TurnTrace.backpressure`.
20. Cursor persistence is transactional; `setCursor` rewinds; cursor survives `unsubscribe` / re-`subscribe`.

### 5.4c-specific

21. `KafkaEventBus`, `KafkaMessageLog`, `KafkaDurableSubscription` exist as a separate optional package and pass the three contract bags from 5.4c.1 with `RUN_BROKER_TESTS=1`.
22. `NatsJetStreamEventBus`, `NatsJetStreamMessageLog`, `NatsJetStreamDurableSubscription` exist as a separate optional package and pass the three contract bags with `RUN_BROKER_TESTS=1`.
23. `AdapterFactory` resolves runtime config to the adapter triple; unknown ids fail fast with typed `AdapterUnknown`; missing optional package fails fast with typed `AdapterNotInstalled`.
24. **Per-conversation ordering** for Kafka is the default (`partitionKeyStrategy: 'conversation'`) and is asserted by a contract test across strategies.
25. At-least-once delivery is the floor for every adapter; idempotency collapses duplicates downstream via `MessageLog.findByIdempotency`.

### 5.4d-specific

26. `ConversationApi.readProjection(topic, token)` and `appendSignal` are first-class methods; no public `any`; `T` is inferred from `TopicProjectionToken<T>` produced by `defineTopicProjection(...)`; positional-generic calls are explicitly rejected at the type level.
27. `TopicProjectionRegistry` is the single registration point; built-in `TopicTranscript` token is auto-registered unless opted out; `ProjectionNotRegistered`, `ProjectionStateInvalid`, and `InvalidSignalKind` are typed branches of `ConversationErrorSchema`.
27a. Policy reads projections via `M.memory.conversation.topics[id].projections.<name>` (Learning-materialized); Execution reads via `readProjection` (log-folded, optionally cached); both narrow via the same `stateSchema`.
27b. `MessageLogAppendParamsSchema.speechAct` equals `SpeechActSchema` at rest; the previous `z.string().min(1)` lower-level seam is removed.
28. `manifest.communication` carries six new closed-vocabulary capability fields; `.strict()` rejects unknown keys; defaults are explicit; `acceptedSpeechActs` / `acceptedContentTypes` undefined preserves Phase 1–3 "accept all" behavior.
29. Pre-dispatch capability validation produces typed `delivery.failed` observations (`RecipientNotThreadable`, `SpeechActNotAccepted`, `ContentTypeNotAccepted`, `JsonSchemaValidationFailed`); never silent acceptance.
30. `topicPoliciesSupported` consultation produces `topic.policy.unsupported` observations on creation / invite without blocking topic creation; trace stamps the unsupported list.
31. `wakeOnTopicMessage` honored end-to-end; default `false` preserves Phase 2 behavior.
