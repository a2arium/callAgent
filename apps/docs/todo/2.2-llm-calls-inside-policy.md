# 2.2 LLM Calls inside Policy / Module Purity Specification

This document defines the normative specification for removing direct LLM access from pure loop modules (`Policy`, `Attention`, `Perception`, `Learning`, `Shield`, `Transition`, `extrinsicReward`, `intrinsicReward`) to enforce strict cognitive purity.

**REMEMBER: We do not support backwards compatibility.**
After these changes are implemented, final migration instructions will be saved to `apps/docs/migration/2.2-llm-calls-inside-policy-migration.md`.

---

## Problem Statement

The current `oneTurn.ts` implementation passes a `PureLLMPort` to nearly all loop modules. This encourages "inline reasoning" inside modules that are intended to be pure data transformers.

This violates:

1. **APLRET Rule 3 — Single Effect Boundary** (`0-aplret_contracts.md` §3): "Only Execution may perform side effects." The rule explicitly lists "LLM calls" as an Execution-only effect. Passing `PureLLMPort` to other modules violates this boundary.
2. **APLRET Rule 5 — Sync, M-only Policy** (`0-aplret_contracts.md` §5): "Policy is synchronous and reads only `MentalState`." Policy MUST NOT "call LLMs" — listed explicitly in the MUST NOT list.
3. **types-rules.md Rule 1 — Types Must Reflect Runtime Behavior**: The `PureLLMPort` JSDoc (line 38–57 of `LLMTypes.ts`) claims it is for "use in pure modules (Perception, Shield, etc.)" — but calling an LLM is a side effect. The type's documentation exaggerates purity.
4. **types-rules.md Rule 4 — Illegal States Must Not Compile**: The current type signatures *allow* `policy: async (m, mem, llm) => { await llm.call(...) }` to compile. After this change, that code MUST fail at compile time.

### Current Blast vs Actual Usage

The `llm` parameter is **optional** (`llm?: PureLLMPort`) in all module signatures. No agent in the codebase actually uses it, and `loopRunner.ts` calls `oneTurn` **without passing `llm`** (line 656–665). The parameter is dead weight that encourages bad patterns. The real-world migration risk on agent code is **zero** — this is purely a framework type cleanup.

## Arity Dispatch (Critical)

`oneTurn.ts` lines 274–288 contain a **runtime arity-based dispatch** that maps `PolicyFn` overloads to arguments:

```ts
// CURRENT (lines 274-288)
const arity = policyFn.length;
if (arity >= 5) return policyFn(m1, mPrev, o, mem, llm);   // (m, prev, o, mem, llm)
else if (arity === 4) return policyFn(m1, o, mem, llm);     // (m, o, mem, llm)
else if (arity === 3) return policyFn(m1, mem, llm);         // (m, mem, llm)
else return policyFn(m1, mem);                               // (m, mem)
```

### Required Change

After removing `llm`, the arity boundaries shift:

```ts
// TARGET
const arity = policyFn.length;
if (arity >= 4) return policyFn(m1, mPrev, o, mem);   // (m, prev, o, mem)
else if (arity === 3) return policyFn(m1, o, mem);     // (m, o, mem)
else return policyFn(m1, mem);                          // (m, mem)
```

This is the **most dangerous part of the refactor**. The arity check determines which `PolicyFn` overload signature was used. Getting the boundaries wrong silently passes wrong arguments. Tests must cover all three arity branches.

## Specification (Target State)

1. **`oneTurn` signature** → `(ctx, env, mPrev, mods, mem, writer, prevAction?, rPrev?)` — No `llm`.
2. **Module signatures** → All pure modules accept only data (`MentalState`, `Observation`, `MemoryReader`, etc.). No module except `Execution` has access to any LLM port.
3. **`Execution` gets LLM via `ctx`** → `Execution` already receives `ctx: TaskContext`, which has `ctx.llm: ILLMCaller`. This is unchanged.
4. **Purity Enforcement (types-rules.md Rule 4)** → Any agent code that passes `llm` to a pure module will fail at compile time.
5. **`extractPureLLMPort` deleted** → No framework utility for injecting LLM into pure modules. If an Execution sub-function needs a sealed port, call `{ call: ctx.llm.call.bind(ctx.llm) }` inline.

## Migration Strategies

Full migration guide will be created in `apps/docs/migration/2.2-llm-calls-inside-policy-migration.md` post-implementation. Below are the canonical patterns.

### 1. Migrating Inline Policy Reasoning

The canonical intent for LLM reasoning is `answer_with_llm`, defined in `0-aplret_contracts.md` §Intent:

```ts
type Intent =
  | { kind: 'answer_with_llm'; query: string; contextKey?: string }
  // ... other intents
```

**Old (Violating Purity):**
```ts
policy: async (m, mem, llm) => {
  const answer = await llm.call("Should I do X?");
  return answer.includes("Yes") ? { kind: 'do_x' } : { kind: 'do_y' };
}
```

**New (APLRET Canonical — using `answer_with_llm`):**
```ts
// Policy decides it's time to reason — sync, M-only
policy: (m) => {
  const scratch = (m.memory.scratch || {}) as Record<string, unknown>;
  if (!scratch.evalResult) {
    return { kind: 'answer_with_llm', query: 'Should I do X?' };
  }
  return scratch.evalResult === 'yes' ? { kind: 'do_x' } : { kind: 'do_y' };
}

// Execution handles answer_with_llm — sole effect boundary
execution: async (intent, ctx) => {
  if (intent.kind === 'answer_with_llm') {
    const context = intent.contextKey
      ? await ctx.memory.semantic.readItems({ tag: intent.contextKey })
      : [];
    const res = await ctx.llm.call(intent.query);
    return {
      action: { kind: 'internal', done: false },  // re-enters via observation next turn
      result: { status: 'ok', data: { answer: res[0]?.content, query: intent.query } }
    };
  }
  // ...other intents
}

// Transition converts ExecResult into an Observation for the next turn's inbox
transition: (_env, exec) => {
  if (exec.result.data?.answer) {
    return {
      kind: 'continue',
      observations: [{
        source: 'internal',
        kind: 'llm.answered',
        payload: { answer: exec.result.data.answer, query: exec.result.data.query }
      }]
    };
  }
  return { kind: 'continue', observations: [] };
}

// Next turn: Perception normalizes the observation
perception: (env) => {
  const llmObs = env.inbox.current.find(o => o.kind === 'llm.answered');
  return { llmAnswer: llmObs?.payload?.answer };
}

// Learning records the result into MentalState — single writer
learning: (prev, _action, obs) => {
  if (obs?.llmAnswer) {
    const next = { ...prev, memory: { ...prev.memory } };
    const scratch = { ...((next.memory.scratch || {}) as Record<string, unknown>) };
    scratch.evalResult = String(obs.llmAnswer).toLowerCase().includes('yes') ? 'yes' : 'no';
    next.memory.scratch = scratch;
    return next;
  }
  return prev;
}
```

> **Note on `contextKey`**: The optional `contextKey` field in `answer_with_llm` is the canonical way to inject semantic memory context into an LLM query — Execution resolves it via `ctx.memory.semantic.readItems({ tag: contextKey })` before the call. Policy never touches memory reads for this purpose.


### 2. Migrating Perception Extraction

**Old (Violating Purity):**
```ts
perception: async (env, alpha, mem, llm) => {
  const raw = env.inbox.current[0]?.payload?.value;
  const extracted = await llm.call(`Extract name from: ${raw}`);
  return { name: extracted[0]?.content };
}
```

**New (Two-turn flow):**
```ts
// Perception returns raw data — no LLM
perception: (env, alpha) => {
  const raw = env.inbox.current[0]?.payload?.value;
  return { rawInput: raw };
}

// Learning detects unprocessed input, flags it
learning: (prev, _action, obs) => {
  if (obs.rawInput && !prev.worldModel?.extractedName) {
    return {
      ...prev,
      memory: {
        ...prev.memory,
        scratch: { ...prev.memory.scratch, needsExtraction: obs.rawInput }
      }
    };
  }
  return prev;
}

// Policy routes to extraction intent
policy: (m) => {
  const scratch = (m.memory.scratch || {}) as Record<string, unknown>;
  if (scratch.needsExtraction) return { kind: 'extract_name', data: scratch.needsExtraction };
  return { kind: 'continue' };
}

// Execution performs the LLM extraction using a strict output contract
execution: async (intent, ctx) => {
  if (intent.kind === 'extract_name') {
    // 1. Define the exact contract we expect from the LLM using Zod
    const NameSchema = z.object({
      name: z.string().describe("The extracted full name, or null if no name found").nullable()
    });

    // 2. Pass the raw data and the schema to the LLM; callllm auto-parses the JSON
    const res = await ctx.llm.call('Extract the name from the provided data.', {
      data: intent.data,
      jsonSchema: { name: 'NameExtraction', schema: NameSchema }
    });

    // 3. Access the automatically validated and parsed object directly
    return {
      action: { kind: 'internal', done: false },
      result: { status: 'ok', data: { name: res[0]?.contentObject?.name } }
    };
  }
  // ...
}

// Transition packages the result as an observation for the next turn
transition: (env, exec) => ({
  kind: 'continue',
  observations: [{
    source: 'internal',
    kind: 'extraction.completed',
    payload: { name: exec.result.data?.name }
  }]
})

// Next turn Learning consumes the observation and writes to MentalState
learning: (prev, _action, obs) => {
  if (obs?.name) {
    return {
      ...prev,
      worldModel: { ...(prev.worldModel || {}), extractedName: obs.name },
      memory: {
        ...prev.memory,
        scratch: { ...((prev.memory.scratch || {}) as Record<string, unknown>), needsExtraction: undefined }
      }
    };
  }
  return prev;
}
```

### 3. Canonical Data Flow for LLM-as-Effect

The full canonical path for any LLM call:

```
Turn N:
  Policy emits intent   (sync, M-only)
  Execution calls LLM   (ctx.llm — sole effect boundary)
  Transition packages   exec.result → Observation[]

Turn N+1:
  env.inbox.current     ← contains the observation
  Perception normalizes the observation payload
  Learning writes result into MentalState
  Policy reads MentalState — now has the LLM result
```

This is the non-negotiable canonical pattern per `0-aplret_contracts.md` §1 (Turn Discipline) and §3 (Single Effect Boundary). There is no shortcut where Execution produces data that Landing reads in the same turn without going through Transition → inbox.

### 4. Code Compilation

After this change, any agent compiling against the new core framework will receive TypeScript compilation errors at every `llm` usage in pure module signatures. Each must be routed through the `Intent → Execution → Transition → Observation → Learning → MentalState` pipeline as shown above.
