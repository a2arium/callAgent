# How-to: Implement TurnTrace in the Runtime

Use this guide when you maintain the callagent runtime and need to produce a correct TurnTrace for every turn.

## Goal

- Emit **one** TurnTrace record per turn.
- Make it possible to debug and test agents by inspecting TurnTrace alone.
- Preserve APLRET invariants: inbox-only Perception, sync M-only Policy, effect boundary in Execution.

## Non-goals

- Designing the agent’s domain logic.
- Defining user-facing narratives.
- Implementing statecharts or advanced orchestration.

## Prerequisites

You should have:

- the APLRET contract reference
- a stable observation taxonomy (`source` + `kind`)
- a stable `ExecOutcome { action, result }` and `TurnOutcome`

## The TurnTrace contract

TurnTrace is a structured record produced by the runtime.

Minimum required fields:

- `turn`, `turnId`
- `agentCardSource`, `runtimeManifestSource`
- `agentCardHash`, `runtimeManifestHash`
- `stageBefore`, `stageAfter`
- `inboxCurrent` summary (at least source/kind/token presence)
- `intent.kind`
- `shield.action`
- `execAction.kind` (+ token if any)
- `transition.kind` (+ token if any)
- `pendingAfter` summary
- per-module timings + total
- `correlationId`
- optional `traceId` / `spanId`
- optional `usage` (tokens/cost)

## Step-by-step implementation

### Step 0: Resolve manifests and compute provenance

Before running any turns, the runtime MUST:

1. Resolve Agent Card (inline > path > default `./agent-card.json`).
2. Resolve Runtime Manifest (inline > path > default `./agent.runtime.json`).
3. Validate both.
4. Enforce name/version match.

If any step fails, the runtime MUST fail fast and MUST NOT start the loop.

After resolution, compute and store the four provenance fields for the session:

- `agentCardSource`
- `runtimeManifestSource`
- `agentCardHash`
- `runtimeManifestHash`

Hashes MUST be stable under whitespace and object key order. To implement this, canonicalize the JSON before hashing the string. Do not hash raw file bytes.

These values are session-level constants and are copied into each TurnTrace record.

### Step 1: Create a TurnContext at turn start

At the start of each turn, create an in-memory TurnContext that will accumulate fields and timings.

Required:

- `turnId` must be unique per turn
- `turn` increments monotonically for the session
- `agentCardSource`, `runtimeManifestSource`, `agentCardHash`, `runtimeManifestHash` copied from session state
- `stageBefore` captured from control state
- `inboxCurrent` captured as a **snapshot** (or summary)

Rule:

- Snapshot `env.inbox.current` before any module runs.

### Step 2: Start timing and attach correlation context

- Start `totalMs` timer.
- Capture or generate `correlationId`.

Guidance:

- If resuming from a token, use a correlation id derived from that token’s logical operation.
- If starting new work, generate a new correlation id.

If distributed tracing is enabled:

- capture current `traceId` and `spanId`
- make sure correlation is propagated into tool calls, child calls, and log records

### Step 3: Run Attention and record

- Time Attention execution.
- Store the attention output (or a filtered subset) in `trace.attention`.

Rules:

- do not store huge objects
- store enough to explain filtering/focus decisions

### Step 4: Validate inbox and run Perception

Before Perception:

- validate each inbox observation against:
  - source/kind compatibility
  - required token fields
  - payload envelope shape

If invalid:

- produce a structured invariant error
- decide whether to fail the turn or inject a validation-failed internal observation

Run Perception:

- time it
- store normalized output in `trace.perception`

### Step 5: Run Learning and record memory change

- time Learning
- store `mentalStateBeforeHash` and `mentalStateAfterHash`

Hash guidance:

- hash only the stable snapshot representation
- exclude non-deterministic fields such as timestamps if they are not part of the stored state

Optional:

- record a small “memory delta summary” when available (for humans)

### Step 6: Run Policy and record intent

- time Policy
- record intent as a compact object

Rules:

- Policy is sync
- Policy reads only `MentalState`

If the runtime cannot enforce module purity at compile time, enforce it at runtime wiring:

- Policy callback receives only `m`
- do not pass `env` or `ctx` into Policy

### Step 7: Run Shield and record decision

- time Shield
- record shield decision:
  - `action: pass | transform | defer | veto`
  - optional `note` or `reason`

If Shield returns `defer` or `veto`:

- do not execute external effects
- Transition must produce a matching control outcome (`await_input` for defer, or `fail`/`complete` for veto depending on policy)

### Step 8: Run Execution and record outcome

Only when Shield allows execution:

- time Execution
- record `execAction` and `execResult`

Rules:

- Execution must return `{ action, result }` always
- enforce that `action` kind is compatible with `result` status
- if `action` is awaitable, ensure it includes a token

Usage recording:

- capture token usage and cost metadata if LLM calls occurred
- capture retry counts and timeout flags for tools/children

### Step 9: Run Transition and record outcome

- time Transition
- record `transition`
- compute `stageAfter`
- compute `pendingAfter` summary

Validation:

- enforce await invariants:
  - `await_input` requires input token
  - `await_tool` requires tool token
  - `await_child` requires child token
- enforce terminal invariants:
  - terminal state forbids new awaits
- if using StageFacade, apply stage transition, validate control invariants, and apply autoMarks.

Observation propagation rule:

- if Transition returns `continue`, it must include `observations[]`

### Step 10: Persist or emit the TurnTrace

At turn end:

- stop total timer
- finalize `timings`
- emit one TurnTrace record

Emission options:

- append to an in-memory per-session trace list (for harness)
- log as structured JSON (for production)
- export to telemetry pipeline

Rule:

- TurnTrace emission must not fail the turn.
- If TurnTrace cannot be emitted, log a best-effort fallback and continue.

## TurnTrace schema (recommended)

```ts
type TurnTrace = {
  turn: number;
  turnId: string;

  // manifest provenance (required in v2)
  agentCardSource: 'defaultPath' | 'pathOverride' | 'inline';
  runtimeManifestSource: 'defaultPath' | 'pathOverride' | 'inline';
  agentCardHash: string;
  runtimeManifestHash: string;

  stageBefore: string;
  stageAfter?: string;
  stageTransition?: { from: string; to: string };
  stageAutoMarksApplied?: string[];
  stageInvariantChecks?: { required?: string[]; forbidden?: string[]; ok: boolean }[];
  stageInvariantError?: unknown;

  inboxCurrent: unknown[];
  attention?: unknown;
  perception?: unknown;
  mentalStateBeforeHash?: string;
  mentalStateAfterHash?: string;
  intent?: unknown;
  shield?: { action: 'pass' | 'transform' | 'defer' | 'veto'; note?: string; reason?: string };
  execAction?: unknown;
  execResult?: unknown;
  transition?: unknown;
  pendingAfter?: unknown;
  timings?: Record<string, number>;
  usage?: Record<string, unknown>;
  correlationId?: string;
  traceId?: string;
  spanId?: string;
};
```

## Required runtime hooks

To support TurnTrace, the runtime should expose hooks:

- `onTurnStart(ctx)`
- `onModuleStart(name)` / `onModuleEnd(name)`
- `onInvariantError(err)`
- `onExecutionOutcome(execOutcome)`
- `onTransitionOutcome(turnOutcome)`
- `onTurnEnd(trace)`

## Pending snapshot summary

Do not dump raw internal structures into TurnTrace.

Instead, summarize:

- pending input tokens
- pending tool tokens (by tool name if available)
- pending child tokens (by agent id if available)
- current stage

## Acceptance checklist

Implementation is correct when:

- every turn produces exactly one TurnTrace
- every TurnTrace includes the 4 manifest provenance fields
- hashes stay stable across whitespace changes in files
- identity mismatches fail fast before any turns
- await tokens match between execAction and transition
- inbox snapshots reflect what Perception saw
- memory hash changes when Learning should write
- shield decisions are visible
- resume turns show completion observations in inbox
- invariant failures produce structured errors

## Common pitfalls

- capturing inbox after Perception (too late)
- allowing Policy to read runtime config or env (breaks purity)
- missing tokens in await outcomes
- logging raw huge payloads (bloats traces)
- mixing retries and resumes without stable correlation ids
- emitting TurnTrace inconsistently for terminal turns
- hashing raw JSON text without canonicalization
- recomputing hashes per turn unnecessarily
- serving from file while running from inline (must serve resolved card)
