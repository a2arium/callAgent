# 5.2b Conversation Phase 2b — Invite delivery and join lifecycle

> **Internal implementation spec.** This document is for framework contributors and maintainers.
> **For framework users migrating to the new APIs**, create and maintain: **`apps/docs/migration/5.2b-conversation-phase-2b-invite-delivery-and-join-lifecycle-migration.md`**. The migration doc MUST be written incrementally alongside implementation, not at the end.
>
> **No backwards compatibility.** See `apps/docs/todo/types-rules.md` Rule 14. Phase 2b closes the invite lifecycle gap and replaces every ad-hoc token-plumbing pattern used in today's examples with a framework-managed delivery path. There are no dual-shape shims.

**Scope:** Phase 2b completes the topic lifecycle that Phase 2 started and Phase 2a refined. Today, `ctx.conversation.invite` issues an `inviteToken` but the framework does not deliver it anywhere: applications must carry the token out-of-band (env var, hand-off, test scaffolding) before the invitee can call `join`. Phase 2b introduces (a) a transactional invite event emission path, (b) a default **invite delivery coordinator** that routes `topic.invite.received` into the invitee's inbox, (c) typed validation inside `join`, (d) an invite observation taxonomy (`issued` / `received` / `accepted` / `declined` / `expired`), (e) TurnTrace `inviteDelivery` stamping, and (f) an optional `autoJoinInvitedTopics` manifest hint.

**Normative anchor:** [`apps/docs/planned_architecture/multi-agent-communication.md` § Invite delivery and join lifecycle (Phase 2b)](../planned_architecture/multi-agent-communication.md#invite-delivery-and-join-lifecycle-phase-2b).

### Out of scope (still deferred)

- Cross-runtime transport adapters (Kafka/NATS/external brokers). Invite delivery rides **only** the in-process `IEventBus` in Phase 2b; the DB invite row is the durability anchor (startup recovery sweep re-publishes pending rows on boot, §3.5.2). Transport evolution across processes is Phase 4.
- Open/public topics (any-agent self-join without invitation).
- Shared topic documents.
- Advanced trust/approval workflows: human-in-the-loop approvals, capability tokens beyond the existing `inviteToken` string, invite revocation. Phase 2b ships the minimum: one-time-use tokens with expiry. Revocation, reachability pre-flight, and delivery-failure error types are deliberately **not** added in Phase 2b (Rule 1 discipline — no branch without a producer); they arrive when the corresponding APIs / registry abstractions land (Phase 4+).
- Cross-tenant invites.
- `sendTaskToAgent`-style synchronous child-agent invocation (Phase 3 scope). Phase 2b is the asynchronous topic-membership pattern; the two multi-agent patterns are complementary.
- Generalizing `OutboxPublisher` to transport `conversation.*` events (Phase 4 scope — §3.7).

## Problem Statement

Phase 2 delivered `ctx.conversation.invite(topic, invitee) → { token }` and `ctx.conversation.join(topic, { inviteToken })`. Phase 2a refined both to be seat-aware (`memberId`). Neither phase specified how the token reaches the invitee.

Concretely, today:

- `ConversationService.invite` writes an `invite` row (`conversation_topic_invites`) and returns the token to the inviter's execution result.
- The invitee has no framework path that surfaces the invite. There is no observation kind, no inbox entry, no trace stamp.
- Examples work around the gap by reading the token from the inviter's result and injecting it into the invitee by hand (env vars, test harness scaffolding, cross-process glue). Production deployments cannot do this safely.
- `join` accepts any token string with minimal validation (existence + consumed-at + agent/topic match). Expiry, tenant scope, and registry reachability are not enforced; error shapes are flat.
- There is no observability on invite lifecycle (issued, received, accepted, declined, expired). TurnTrace has no invite fields. Debugging an invite that "just didn't arrive" has no framework-visible signal.

The operational consequence: topics are not production-usable. An owner can create one, but new members cannot join without application-level token plumbing. Phase 2b closes this gap.

### 1. Extend public conversation contracts

**Rule enforcement:** Rule 1 (types reflect runtime), Rule 2 (Zod source of truth), Rule 4 (illegal states must not compile), Rule 5 (no public `any`), Rule 11 (typed errors), Rule 12 (avoid overengineering), Rule 14 (breaking type changes require migration doc), Rule 15 (simple + advanced modes).

**Files:**
- `packages/core/src/public-types/conversation/schemas.ts` **(MODIFY)**
- `packages/core/src/public-types/conversation/types.ts` **(MODIFY)**
- `packages/core/src/public-types/conversation/index.ts` **(MODIFY)**

Changes:

- **`InviteTokenSchema` (NEW)** — `z.string().min(1).brand<'InviteToken'>()`. Branded because the token is a capability: passing a plain string where a token is expected must fail at compile time. The brand is applied to both inputs (`TopicJoinOptions.inviteToken`, the future `decline` options, etc.) and outputs (`TopicInviteReceipt.ok.token`). Public callers construct it through the schema; tests and examples ship an `inviteToken(x)` helper (paralleling `memberId(x)` / `agentId(x)`).

  **Rule 4 rationale:** the brand prevents the most common invite-handling bug — accidentally using a token string that came from untyped source (env var, JSON, stale test fixture) where the framework expects a validated, issued invite token.

- **`TopicInviteOptionsSchema` (MODIFY)** — add two optional fields:
  - `ttlSeconds?: z.number().int().positive().max(60 * 60 * 24 * 30).optional()` — default: runtime-configured (`RUNTIME_DEFAULT_TTL_SECONDS = 86400`, see §3.2). `ttlSeconds` is a hint; the framework stores the resolved `expiresAt` on the invite row and rejects post-expiry consumption with `InviteExpired` (typed). The 30-day upper bound caps the expiry-sweep working set; operators who need longer-lived tokens can reissue rather than widen the bound (documented operational recommendation).
  - `idempotencyKey?: IdempotencyKeySchema.optional()` — same Phase 2a semantics as `TopicPostOptionsSchema.idempotencyKey`. When present, the framework guarantees at most one invite row per `(tenantId, conversationId, inviteeAgentId, inviteeMemberId?, idempotencyKey)`. Retried calls return the previously-issued token verbatim (same `expiresAt`, no new outbox row, no new observation). Enforced via a partial unique index on those columns (§4). Without this, a retry storm produces N tokens → N `received` observations → an invitee inbox of phantom invites.

- **`TopicInviteReceiptSchema.ok` (MODIFY)** — extend `{ status: 'ok', token: InviteTokenSchema, expiresAt: z.string().datetime() }`. `expiresAt` becomes a contractual field because callers that surface the invite to operators (test scaffolds, debug UIs) need it.

- **`TopicInviteReceiptSchema.rejected` (MODIFY)** — `error: ConversationErrorSchema` unchanged at the discriminator level; new branches below.

- **`TopicJoinOptionsSchema` (MODIFY)** — `inviteToken: InviteTokenSchema` (branded replaces raw string).

- **`TopicDeclineOptionsSchema` (NEW)** — `{ inviteToken: InviteTokenSchema, reason?: z.string().max(500).optional() }`. Drives `ctx.conversation.decline(...)` (see §3.2). The reason is optional, opaque, capped.

- **`TopicDeclineReceiptSchema` (NEW)** — `z.discriminatedUnion('status', [{ status: 'ok', topic: TopicRefSchema }, { status: 'rejected', error: ConversationErrorSchema }])`.

- **`ConversationApi` (MODIFY)** — add `decline(options: TopicDeclineOptions) => Promise<TopicDeclineReceipt>`. `invite` / `join` signatures unchanged at the top level (internal shape changed by option extensions above).

- **`ConversationErrorSchema` (MODIFY — additive branches only)**:
  - `InviteExpired` — token existed but `expiresAt < now`.
  - `InviteAlreadyConsumed` — token existed and is one-time-use; row has `consumedAt IS NOT NULL`.
  - `InviteTargetMismatch` — token exists but `inviteeAgentId` does not match the caller's `agentId`, OR `conversationId` does not match the `topic` passed to `join`. Replaces the overloaded `InviteInvalid` for that case.
  - `InviteNotFound` — token does not exist (or is not resolvable in the caller's tenant — see §3.3 step 1 lookup semantics). Deterministic, typed; previously collapsed into `InviteInvalid`.

  `InviteInvalid` is **removed** as a top-level branch. Every call site that surfaced it now surfaces one of the four precise branches above. This is a breaking change (Rule 14) listed in §10.

  **Rule 1 discipline — branches deliberately NOT added in Phase 2b:**
  - `InviteRevoked` — there is no revocation API in Phase 2b. Adding a branch with no producer violates Rule 1 (types must reflect runtime). It will be added when the revocation API is added.
  - `InviteDeliveryFailed` — delivery is performed by an internal subscriber (§3.6) that has no caller awaiting a typed return. Delivery exhaustion surfaces to the inviter as a `topic.invite.expired` observation with `expiresAt = now` (see §3.6.2 retry branch), not via `ConversationErrorSchema`. Keeping this off the error union prevents a second, confusing "how do failures surface?" question.
  - `InviteeNotReachable` — see §3.2: Phase 2b does **not** perform a synchronous pre-flight registry check (`globalA2AService.findLocalAgent` is process-local and cannot be trusted in multi-process runtimes). Unreachable invitees surface through the delivery-coordinator failure path (retries → `topic.invite.expired`), not as a typed error on `invite`. Added to the error union when a cross-runtime `IAgentRegistry` abstraction lands in Phase 4.

Public type/contract discipline:

- No `any` anywhere in `public-types/conversation/**`.
- Every invite-lifecycle error is one of the enumerated branches — no string-typed `"InviteInvalid"` catchall.
- Runtime validation uses the same Zod schemas as the inferred types.
- `InviteToken` is branded; assigning a raw `string` is a compile error; assigning a `MemberId` is a compile error (distinct brands). `AgentId` and `ConversationId` remain unbranded in Phase 2b (consistent with the Phase 2a decision that the churn cost exceeds the incremental safety); cross-brand assignment between `InviteToken` and `AgentId` / `ConversationId` is therefore not type-enforced — callers relying on schema validation (the recommended path) still get runtime protection.

Emission rules (normative, per Rule 1 — "by the time an observation leaves `ConversationService`, every field is resolved"):

- **`topic.invite.issued`** — emitted to the **inviter's active seat session** for that topic (owner or moderator — the seat that called `invite`). It is the inviter's audit record.
- **`topic.invite.received`** — emitted to the **invitee's default inbox session** (§3.1). The delivery coordinator (§3.4) is responsible for producing this observation; `ConversationService.invite` itself does NOT call the router for this variant.
- **`topic.invite.accepted`** — emitted to every currently active member seat in the topic (same fan-out as `topic.member.joined`). Produced inside `join` atomically with the member insert.
- **`topic.invite.declined`** — emitted to the **inviter's seat session** (the original caller of `invite`; resolved from the invite row's `inviterMemberId` captured at issuance — see §4). Gives the owner deterministic feedback on decline.
- **`topic.invite.expired`** — emitted to the **inviter's seat session** when a sweep detects `expiresAt < now AND consumedAt IS NULL AND declinedAt IS NULL` (see §3.5).

No invite observation ever carries a payload body beyond the fields above; tokens inside observations are branded strings, not wrapped in secondary objects.

`InboundMessage` is NOT extended for invites — invites are not messages. They are lifecycle observations. This keeps the message path clean (Rule 12).

**`topic.invite.issued` vs `topic.invite.received` — one semantic event, two channels (normative):**

A single invite produces two distinct observations with different payload shapes and different delivery channels:

| Observation | Audience | Channel | Purpose |
|---|---|---|---|
| `topic.invite.issued` | Inviter's own seat session | In-process `ConversationRouter` append (same tenant/process as the `invite` call) | Audit record: "I issued this invite." Also drives `topics[id].pendingInvites` in the inviter's projection. |
| `topic.invite.received` | Invitee's `agent-inbox:<agentId>` session (or `sessionIdOverride`) | `IEventBus` → `InviteDeliveryCoordinator` → `ConversationRouter` (§3.6) | Actionable signal: "you were invited." Drives `invitesInbox` in the invitee's projection and can be auto-joined (§7). |

The `issued` variant carries inviter-centric fields (`invitee`, `inviterAgentId`). The `received` variant carries invitee-centric fields (`inviterAgentId`, `role`, `inviteeMemberId?`) and omits the inviter's seat identity. The coordinator is the **only** component that translates `issued` → `received`. `ConversationService.invite` routes `issued` locally and publishes on the bus; it never produces `received`.

#### 3.1 Default invitee session resolution and activation (normative)

**Rule:** `topic.invite.received` lands in the invitee's **agent default inbox session**.

```
invitee default inbox sessionId = `agent-inbox:${inviteeAgentId}`
```

Rationale: the invitee has no topic seat yet. We need a deterministic, per-agent session whose inbox represents "unsolicited observations addressed to this agent". The default string is simple, does not conflict with any existing session naming convention (topic seat sessions are `topic-<id>:<memberId>`; threads use `thread-<id>`), and is deterministically derivable without any DB lookup. Scope is `(tenantId, 'agent-inbox:<agentId>')`, so the same `agentId` running in two tenants gets two distinct inbox sessions automatically.

**Override rule:** if the inviter supplies `invitee.sessionIdOverride`, the delivery coordinator routes to that override session **instead of** `agent-inbox:<agentId>`. The override path exists so an orchestrator (test scaffolding, platform service) can redirect a specific invite to a pre-existing seat session (e.g., for an agent that manages multiple tenants through distinct sessions). Under override, the invitee receives the observation in the session they already run; under default, the runtime must wake them on `agent-inbox:<agentId>`.

##### 3.1.1 Activation primitive — required change (normative)

Today, the only activation primitive is `taskEngine.ensureConversationActivation(params: ConversationActivateParams)` defined in `packages/core/src/internal/conversation/types.ts`:

```ts
export type ConversationActivateParams = {
    tenantId: string;
    threadId: string;
    routingSessionId: string;
    recipientAgentId: string;
    messageId: string;
    senderSessionId: string;
    senderAgentId: string;
};
```

This shape is thread-centric and cannot represent an invite activation: there is no `threadId`, no `messageId`, and the "sender" is semantically the inviter whose seat the invitee has no reference to yet. The coordinator cannot call this primitive without either (a) stuffing invite fields into mismatched thread fields (Rule 1 violation) or (b) a new activation shape.

**Decision (Phase 2b): option (b) — widen `ConversationActivateParams` into a discriminated union.**

```ts
export type ConversationActivateParams =
    | {
          kind: 'thread';
          tenantId: string;
          threadId: string;
          routingSessionId: string;
          recipientAgentId: string;
          messageId: string;
          senderSessionId: string;
          senderAgentId: string;
      }
    | {
          kind: 'topic';
          tenantId: string;
          topicId: ConversationId;
          routingSessionId: string;
          recipientAgentId: string;
          recipientMemberId: MemberId;
          senderSessionId: string;
          senderAgentId: string;
          senderMemberId: MemberId;
      }
    | {
          kind: 'invite';
          tenantId: string;
          topicId: ConversationId;
          routingSessionId: string;          // `agent-inbox:<agentId>` or sessionIdOverride
          recipientAgentId: AgentId;
          inviterAgentId: AgentId;
          token: InviteToken;
      };
```

Rationale:
- Rule 4 (illegal states must not compile): each `kind` carries only the fields that are meaningful for that activation shape.
- Rule 1: the runtime sees the exact intent of each activation and can route telemetry, tracing, and failure paths accordingly.
- Discriminated union is preferable to a new top-level method because the activation pipeline inside `taskEngine` (plugin lookup, passive context build, `turnRunner.runTurn`) is identical across variants — only the pre-flight validation and the `trigger` label on the turn context differ.

`taskEngine.runConversationActivationBody` gains a `switch (params.kind)` with thread / topic / invite arms. The `trigger` on `runTurn` becomes `'conversation'` for thread+topic variants (unchanged) and `'invite'` for the invite variant, so TurnTrace can distinguish invite-driven turns from normal conversation turns.

**This change is an internal contract change; it is listed as a new required edit in §Summary of Affected Files and §Implementation Order (new step: "Widen `ConversationActivateParams` discriminated union + taskEngine arms").**

##### 3.1.2 Activation degradation mode

If the runtime cannot wake the invitee on `agent-inbox:<agentId>` (e.g., a restricted deployment where only seat sessions are reachable), delivery degrades to **"observation persisted; next external activation of that session observes it"**. This is correct but not immediate. Operators whose runtime has this restriction must supply `invitee.sessionIdOverride` that points to a session the runtime WILL activate.

Phase 4 (cross-runtime transport) generalizes activation across processes; Phase 2b does not try to solve cross-runtime invitee wake-up.

#### 3.2 Service responsibilities — `invite` (extended)

- Validate the topic exists and is `open`; caller is `owner` or `moderator`; invitee is not already a member (exact shape: same checks as Phase 2a).
- **No synchronous registry reachability check.** Phase 2b does **not** call `globalA2AService.findLocalAgent` as a pre-flight. Rationale: that function is process-local; relying on it would false-reject legitimate invites whenever inviter and invitee run in different processes (the exact case Phase 2b's durable delivery path is designed to serve). An invitee that never becomes reachable surfaces through the delivery-coordinator failure budget (§3.6) and the expired-sweep (§3.5) as a `topic.invite.expired` observation on the inviter. Phase 4 (cross-runtime `IAgentRegistry`) is where a trustworthy pre-flight becomes possible.
- **TTL resolution:** `ttlSeconds = options.ttlSeconds ?? RUNTIME_DEFAULT_TTL_SECONDS (86400)` ; `expiresAt = issuedAt + ttlSeconds`.
- **Idempotency key resolution:** if `options.idempotencyKey` is present, attempt an existence lookup on `(tenantId, conversationId, inviteeAgentId, inviteeMemberId?, idempotencyKey)` before issuing. On hit: return the stored row's `{ token, expiresAt }` verbatim; emit nothing new (no observation, no bus publish, no outbox row). On miss: proceed.
- **Inviter seat capture:** resolve the inviter's seat via `listConversationTopicMembersByAgent({ agentId: senderAgentId, activeOnly: true })` + the provided `_senderSessionId` (implicit when unambiguous, ambiguity → `SenderAmbiguous` typed error, reusing Phase 2a semantics). Store `inviterMemberId`, `inviterSessionId` on the invite row — required for correctly routing `topic.invite.declined` / `expired` back to the owner.
- **Transactional write (atomic DB):**
  1. Insert into `conversation_topic_invites` with all columns including `expiresAt`, `inviterAgentId`, `inviterMemberId`, `inviterSessionId`, `idempotencyKey?`, `correlationId?`.
  2. Route `topic.invite.issued` observation to the **inviter's seat session** via `ConversationRouter` (local durable append — same-process path Phase 2 already uses). This is the inviter-side audit record; it is **not** the delivery channel to the invitee.
  3. Commit.
- **After commit (post-commit bus publish):** publish `'conversation.topic.invite.issued'` on the configured `IEventBus` with the issued-variant payload. This is the delivery channel for the `InviteDeliveryCoordinator` (§3.6). Publish is fire-and-forget (no exception propagates back to the caller).
- Return `{ status: 'ok', token, expiresAt }`.

**Durability of the bus publish (normative):**

The bus is in-process and the publish happens **after** DB commit, so a process crash between commit and publish would leave an "issued-but-never-delivered" row. This is recovered by the **startup invite sweep** (§3.5): on runtime boot, a one-time sweep selects rows with `delivered_at IS NULL AND delivery_attempted_at IS NULL AND consumed_at IS NULL AND declined_at IS NULL AND expires_at >= now` and re-publishes `'conversation.topic.invite.issued'` for each. Idempotency at the coordinator level (§3.6) ensures at most one `received` observation lands in the invitee's inbox per invite row, even if a crash caused a redundant publish.

The `Outbox` table is **not** used as the delivery channel in Phase 2b. Rationale:
- The in-memory session manager's `outbox` array is write-only today (nothing drains it); using it as the delivery channel would silently break in-memory tests.
- The existing `OutboxPublisher` runs only against Postgres; coupling Phase 2b delivery to it would make in-memory harness tests (`InMemoryEventBus`-based) structurally impossible.
- Phase 4's cross-runtime transport adapter work is the right place to generalize durable event transport across processes. Phase 2b ships the **in-process** delivery path only; the DB-backed invite row is itself the durability record.

Phase 2b does NOT modify `OutboxPublisher.dispatch`. Conversation-scoped outbox behavior is unchanged (log-only scaffold, untouched).

#### 3.3 Service responsibilities — `join` (rewritten)

All validation is explicit and typed. Order matters (return the most specific error first). Lookup is always **tenant-scoped**: the caller's `tenantId` + `token` together resolve to at most one row. Cross-tenant tokens look identical to non-existent tokens from the caller's perspective (they surface `InviteNotFound`, not a "wrong tenant" error), which is deliberate — we do not leak the existence of tokens across tenant boundaries.

**Validation + atomic consumption (single DB round-trip for the race-critical step):**

1. Look up the invite row by `(tenantId, token)`. Not found → `InviteNotFound`. Because lookup is tenant-scoped, a cross-tenant token surfaces as `InviteNotFound`; no separate cross-tenant branch exists.
2. If `revokedAt IS NOT NULL` → defensive log (not a Phase 2b concern — no revocation API — but the code asserts `revokedAt IS NULL` as an invariant and fails the turn on violation).
3. If `consumedAt IS NOT NULL` → `InviteAlreadyConsumed` (exception: idempotent-same-seat path, below).
4. If `expiresAt < now` → `InviteExpired`. Mark the row `declinedAt = now, declineReason = 'expired'` via conditional UPDATE (same shape as step 7) so the expired-sweep (§3.5) never double-emits.
5. If `inviteeAgentId !== senderAgentId` → `InviteTargetMismatch`.
6. If `conversationId !== topic.id` → `InviteTargetMismatch`.
7. **Atomic one-shot consumption** — a single conditional UPDATE combines the consumable-state check with the write:

   ```sql
   UPDATE conversation_topic_invites
   SET consumed_at = :now
   WHERE token         = :token
     AND tenant_id     = :tenantId
     AND consumed_at   IS NULL
     AND declined_at   IS NULL
     AND expires_at   >= :now
   RETURNING *
   ```

   - `rowCount = 1` → proceed with steps 8–9.
   - `rowCount = 0` → re-read the row (still tenant-scoped) and surface the branch that now applies (`InviteAlreadyConsumed` / `InviteExpired`). This eliminates the step-3/step-7 race: two concurrent `join` calls on the same token cannot both consume.

8. Persist the member row (same as Phase 2a). Same transaction as step 7 (`UPDATE ... RETURNING` + `INSERT member`).
9. Emit both `topic.invite.accepted` and `topic.member.joined` to all active member seats (fan-out via `ConversationRouter`, same primitive Phase 2 uses). Produced atomically with the member insert in the same DB transaction.

Return `{ status: 'ok', topic, member: ResolvedTopicMember }`.

**Idempotent join (normative):** a second `join` call with the **already-consumed** token from the **same caller** (`tenantId + senderAgentId` matches `inviteeAgentId`; stored `inviterMemberId` / `consumedAt` unchanged) returns `{ status: 'ok', topic, member }` byte-identically (no new emission, no new member row). Matches the Phase 2 idempotency posture on `createTopic`. Any other caller gets `InviteAlreadyConsumed`. The "same caller" check happens **before** step 7's conditional UPDATE; if the row is already consumed by this caller, skip directly to the byte-identical return.

**Why no post-consumption registry check:** removed per §3.2 — `findLocalAgent` is not trustworthy across processes. An agent that was registered at issuance but is gone at consumption time simply cannot call `join` (they aren't running); there is no case where the framework needs a reachability check for `join`.

#### 3.4 Service responsibilities — `decline` (NEW)

- Accepts `{ inviteToken, reason? }`. Caller is `ctx.conversation.decline(...)`.
- Same validation chain as `join` steps 1–6 (typed errors, most-specific first).
- Step 7 becomes a different conditional UPDATE (declines, not consumes):

  ```sql
  UPDATE conversation_topic_invites
  SET consumed_at   = :now,
      declined_at   = :now,
      decline_reason = :reason
  WHERE token         = :token
    AND tenant_id     = :tenantId
    AND consumed_at   IS NULL
    AND declined_at   IS NULL
    AND expires_at   >= :now
  RETURNING inviter_agent_id, inviter_member_id, inviter_session_id, conversation_id, correlation_id
  ```

  - `rowCount = 1` → emit `topic.invite.declined` to the **inviter's seat session** (using the returned `inviterSessionId`) via `ConversationRouter`.
  - `rowCount = 0` → re-read and surface the branch that applies (`InviteAlreadyConsumed` / `InviteExpired`).

- Return `{ status: 'ok', topic }`.

Decline does not emit to the invitee's own inbox (it's the caller — they already know). Decline does not fan out to the topic (the invitee never became a member; other members do not need to know).

#### 3.5 Invite sweeps — startup recovery + expiry (normative)

Phase 2b introduces **one dedicated runtime component** that owns all invite sweeps: `InviteSweeper` (new class, colocated with `InviteDeliveryCoordinator` in `packages/core/src/internal/conversation/`). Rationale: a dedicated component keeps sweep scheduling out of `ConversationService` (which is request-scoped) and out of `OutboxPublisher` (which is unrelated). The class is constructed by the runtime wiring code alongside the coordinator; tests instantiate it directly and drive it through harness helpers (§11).

##### 3.5.1 Expiry sweep

Runs on a timer. Default cadence `60s`, configurable through the `InviteSweeper` constructor, disabled by default in `TestHarness`.

On each tick, in a single transaction per batch (default batch size 200):

1. `SELECT` tenant-scoped invites with `expires_at < now AND consumed_at IS NULL AND declined_at IS NULL LIMIT 200`, ordered by `expires_at ASC`.
2. For each row: a conditional UPDATE sets `declined_at = now, decline_reason = 'expired'` guarded by the same `_at IS NULL` clauses, so two concurrent sweepers (or a sweeper racing `join`/`decline`) cannot double-close a row.
3. For rows where the UPDATE succeeded: emit `topic.invite.expired` to the inviter's seat session (`inviterSessionId`) via `ConversationRouter`.

The `declined_at IS NULL` guard makes the sweep idempotent: a retried tick cannot re-emit.

##### 3.5.2 Startup delivery-recovery sweep

Runs **once at process boot**, after `InviteDeliveryCoordinator` has subscribed to the bus. Purpose: recover invites issued before a crash that committed the DB row but never published on the bus (§3.2).

1. `SELECT` tenant-scoped invites with `delivered_at IS NULL AND delivery_attempted_at IS NULL AND consumed_at IS NULL AND declined_at IS NULL AND expires_at >= now`, ordered by `issued_at ASC`, limit 1000.
2. For each row: publish `'conversation.topic.invite.issued'` on the bus with the full issued-variant payload reconstructed from the row. Order-preserving.

The coordinator's internal idempotency (§3.6) ensures a row that WAS published pre-crash but not marked delivered still lands in the invitee inbox at most once after recovery.

##### 3.5.3 Test determinism

- Tests drive expiry via `harness.setInviteClockNow(iso)` + `harness.triggerExpiredInviteSweep()` (§11).
- Tests drive startup recovery via `harness.runInviteStartupSweep()`.
- No test ever sleeps or waits on the real timer. The `InviteSweeper` timer is disabled by default in the harness; production runtimes enable it via the runtime wiring.

#### 3.6 Invite Delivery Coordinator (NEW class)

**File:** `packages/core/src/internal/conversation/InviteDeliveryCoordinator.ts`

A subscriber. Constructor: `{ eventBus: IEventBus, router: ConversationRouter, sessionStore: IWorkingMemorySessionStore, taskEngine: ITaskEngine, now: () => Date }`. On construction it subscribes to the channel `'conversation.topic.invite.issued'` on the bus (same channel `ConversationService.invite` publishes on in §3.2).

##### 3.6.1 Happy-path handler

On each event (called inside the bus `subscribe` handler):

1. **Schema parse** via `ConversationPayloadSchema`. Parse failure → log with the event id and **swallow** (a malformed event is a framework bug; retry will not help and will fill logs).
2. **Re-read the invite row** by `(tenantId, token)` from `sessionStore`. If the row does not exist (coordinator saw an event for a rolled-back transaction — shouldn't happen given §3.2's post-commit publish order, but defensive), swallow.
3. **Idempotency gate:** if `delivered_at IS NOT NULL OR consumed_at IS NOT NULL OR declined_at IS NOT NULL`, swallow. The work is already done (or obsolete).
4. **Resolve target session:**
   - If the invite row has `session_id_override` → use that.
   - Else → `agent-inbox:${inviteeAgentId}`.
5. **Build the `received` payload** by translating the issued-variant fields: keep `topic`, `token`, `expiresAt`, `role`, `inviterAgentId`, `inviteeMemberId?`, `correlationId?`. Drop inviter-seat fields.
6. **Mark `delivery_attempted_at = now`** via the store (`incrementConversationTopicInviteDeliveryAttempt`). This is the idempotency anchor: if delivery is already in progress on another instance, the attempt increment + re-read guard (step 3) makes a concurrent second handler a no-op.
7. **Route the observation** via `router.routeObservation({ tenantId, sessionId, agentId: inviteeAgentId, observation })`.
8. **Activate the invitee** via `taskEngine.ensureConversationActivation({ kind: 'invite', tenantId, topicId, routingSessionId, recipientAgentId: inviteeAgentId, inviterAgentId, token })` (the new invite variant of the activation union, §3.1.1). Fire-and-forget for the coordinator; the task engine returns its own typed result and emits its own failure observation if plugin lookup fails.
9. **Mark `delivered_at = now`** via `markConversationTopicInviteDelivered`. If this update fails (connection blip, row vanished), log and continue — the invitee already has the observation.

Steps 6–9 sit inside `try/catch`. Any thrown error enters the retry branch.

##### 3.6.2 Retry branch (router or activation failure)

On failure between step 6 and step 9:

1. The `delivery_attempted_at` + `delivery_attempts` count is already incremented (step 6).
2. If `delivery_attempts >= MAX_DELIVERY_ATTEMPTS` (default `5`, constructor-configurable): set `delivery_failure_reason = 'delivery_failed'` and emit `topic.invite.expired` (with `expiresAt = now`, `token`, `topic`) to the inviter's seat session — exhaustion is signaled to the inviter via the uniform lifecycle observation (not a typed error, per §1).
3. Otherwise: schedule a **retry with exponential backoff**: attempt `n` waits `min(500ms * 2^(n-1), 30s)` before re-invoking the handler on the same event (`500ms, 1s, 2s, 4s, 8s, ...` capped at `30s`). Backoff is managed by the coordinator; no reliance on external re-publish. Retry uses `setTimeout` scoped to the coordinator's lifecycle (cancelled on `stop()`).

Rationale: bounded retries without a backoff burn the attempt budget in <3s and paint over transient failures as permanent ones. Exponential backoff + a 30s cap gives a ~1min total retry window for 5 attempts, matching typical transient-failure recovery envelopes without pinning the runtime.

##### 3.6.3 Invariants

- **At-most-once delivery to the invitee inbox (with cooperating reducer dedupe).** The coordinator's `delivered_at` + `delivery_attempted_at` gates (step 3) ensure two concurrent handler invocations cannot both route. A third-party re-publish (manual operator intervention) is absorbed by the same gate. The conversation reducer (§8) additionally dedupes `invitesInbox` entries on `token`, providing belt-and-braces at the projection layer.
- **No throws escape the handler.** All failures either retry (with backoff) or resolve into audit writes + a lifecycle observation.
- **No in-memory queues.** Pending work lives in the DB (invite row state); retries live in per-invite timers that are cancelled on `stop()`.
- **No dependency on the outbox.** The coordinator reads from `IEventBus` and persists through `IWorkingMemorySessionStore`. The `Outbox` table is untouched by Phase 2b (§3.2 rationale).

**Runtime registration:** the coordinator and the `InviteSweeper` (§3.5) are constructed by the runtime wiring code alongside `ConversationService`. Lifecycle is bound to the runtime (`start()` / `stop()`). Tests construct them directly; harness helpers expose their methods (`simulateCoordinatorEvent`, `triggerExpiredInviteSweep`, `runInviteStartupSweep`).

#### 3.7 `OutboxPublisher` is NOT modified in Phase 2b (explicit decision)

**File:** `packages/core/src/eventbus/outboxPublisher.ts` **(UNCHANGED)**

Earlier drafts of this spec proposed bridging `conversation.*` outbox rows onto `IEventBus` via a new branch in `OutboxPublisher.dispatch`. That approach is rejected for Phase 2b because:

- The in-memory session manager's `outbox` array is **write-only** in the current codebase (`packages/core/src/orchestration/InMemorySessionManager.ts`) — no component drains it. Any design that routes delivery through the outbox structurally cannot work in the in-memory harness.
- `OutboxPublisher` instantiates its own Prisma client (`packages/core/src/eventbus/outboxPublisher.ts`, lines 13–41) and runs only against Postgres. Coupling invite delivery to it would fork the in-process and SQL-backed code paths.
- `OutboxPublisher.dispatch` is currently a scaffold with the intent of cross-runtime transport (SSE/webhook/Kafka per the existing TODO). Phase 4 is the right phase to generalize that surface; Phase 2b should not pre-commit to a wire protocol.

Phase 2b delivery therefore uses `IEventBus` directly (§3.2 publishes post-commit; §3.6 subscribes). Durability of events the `invite` call committed to the DB before a crash is recovered through the startup sweep (§3.5.2), which re-publishes on the bus from the DB row. The `Outbox` table's conversation-scoped behavior is unchanged by Phase 2b.

#### 7.2 Auto-join helper (when `autoJoinInvitedTopics: true`)

When an agent's manifest declares `communication.autoJoinInvitedTopics === true`, the framework runs a **default auto-join helper** before invoking the agent's `policy` on an `agent-inbox:<agentId>` session:

- For every `topic.invite.received` observation in the current inbox:
  - Call `ConversationService.join({ inviteToken: obs.payload.token, ... })` through the effect boundary (same code path as a policy-emitted join effect — not an internal bypass).
  - On success: TurnTrace stamps `received[i].autoJoinAttempted = true`. The observation stays in the inbox so policy still sees "I got invited." The framework emits `topic.invite.accepted` + `topic.member.joined` to all active seats per §3.3.
  - On typed failure: TurnTrace stamps `received[i].autoJoinAttempted = true, autoJoinError = { type, message }` (§6). Observation stays; policy may still react.

Policy purity is preserved: the helper runs in the framework (effectful), not inside `policy`. Policy receives observations and auto-join outcomes as inbox entries, exactly like any other effect.

Agents that do NOT set `autoJoinInvitedTopics` (or set it to `false`) see `topic.invite.received` in the inbox and decide in their own `policy` / `execution` whether to call `ctx.conversation.join(...)` or `ctx.conversation.decline(...)`. This is the full-control path (Rule 15).

**Rule 4 note:** `autoJoinInvitedTopics: true` never bypasses validation — it still goes through `ConversationService.join` with all typed error paths. It is sugar, not a backdoor.

#### 7.3 Post-join seat activation (normative, addresses the "seat is queued but nobody wakes it" gap)

After a successful `join` (whether driven by auto-join, explicit policy, or any other caller), the framework MUST activate the newly-created seat session once so the agent observes its welcome events (`topic.invite.accepted`, `topic.member.joined`) in a turn on the correct seat.

Why this is required:
- `ConversationService.join` routes `accepted` / `joined` to all active member seats, including the new seat's session (`topic-<topicId>:<memberId>`).
- The call site of `join` (e.g., the auto-join helper on `agent-inbox:<agentId>`) runs on a **different** session; the current turn finishes without seeing those observations.
- Nothing else in the runtime sweeps seat sessions with pending observations. Without post-join activation, the newly-joined seat would remain dormant until some unrelated event routes to it.

Mechanics:
- `ConversationService.join`, after the successful transaction, invokes `taskEngine.ensureConversationActivation({ kind: 'topic', tenantId, topicId, routingSessionId: <new seat session>, recipientAgentId, recipientMemberId, senderAgentId, senderMemberId, senderSessionId })` using the `'topic'` variant of the activation discriminated union (§3.1.1). The sender on this activation is the **inviter** (from the stored invite row); the recipient is the new seat. The turn that runs on the new seat will see `accepted` + `joined` in its inbox plus any same-turn fan-out.
- Failure of this activation does not roll back the `join` (the join is committed; the observations are queued). It emits a `delivery.failed` observation on the new seat session and logs.
- The activation is fire-and-forget from `join`'s perspective — the join receipt returns immediately.

**Idempotency:** a second activation call for the same seat that already ran a turn is a no-op (the activation primitive already tolerates re-entry per Phase 2 semantics).

**Test hook:** `harness.simulateJoinThenActivate(token)` exercises join + seat-activation in one call and returns a snapshot of both the inviter-side and seat-side traces.

#### 7.4 Sequencing rules (normative summary)

For a cold invitee with `autoJoinInvitedTopics: true`:

1. Coordinator receives issued event; routes `received` to `agent-inbox:<agentId>`; activates the agent on `agent-inbox:<agentId>`.
2. Auto-join helper runs, calls `join`.
3. `join` commits the member row and routes `accepted` + `joined` to all seats (including the new one).
4. `join` fires seat activation on `topic-<topicId>:<memberId>`.
5. The `agent-inbox` turn completes; TurnTrace stamps `received[i].autoJoinAttempted = true`.
6. The seat-session turn runs; its inbox has `accepted` + `joined`; policy may emit follow-ups.

For a cold invitee WITHOUT auto-join:

1. Same as step 1 above.
2. No auto-join; policy sees `received` and can call `ctx.conversation.join(...)` from that turn. This is a policy-emitted effect (goes through the standard `join` path), after which step 4 above (post-join seat activation) still fires.

For an invitee that calls `decline`:

1. Same as step 1 above.
2. Policy emits `ctx.conversation.decline(...)` effect. Decline routes `topic.invite.declined` to the inviter's seat only. No seat activation (no seat exists).

## ✅ Acceptance Criteria

1. `ctx.conversation.invite(...)` commits an atomic DB transaction (invite row + inviter-side `topic.invite.issued` observation route) and publishes `'conversation.topic.invite.issued'` on `IEventBus` **after commit**. The `Outbox` table is unchanged by Phase 2b. The invite row has `expires_at`, `inviter_agent_id`, `inviter_member_id`, `inviter_session_id`, `idempotency_key?`, `correlation_id?` populated.
2. Retried `invite` calls with the same `idempotencyKey` return byte-identical `{ token, expiresAt }` and do not emit duplicate observations.
3. `InviteDeliveryCoordinator` consumes the bus event, increments `delivery_attempted_at` / `delivery_attempts`, routes `topic.invite.received` to the invitee's `agent-inbox:<inviteeAgentId>` session (or `sessionIdOverride`), calls `taskEngine.ensureConversationActivation({ kind: 'invite', ... })`, and sets `delivered_at`. Concurrent duplicate handler invocations produce exactly one inbox entry (idempotency gate).
4. `ctx.conversation.join(token)` validates against four typed error branches (`InviteNotFound`, `InviteExpired`, `InviteAlreadyConsumed`, `InviteTargetMismatch`) with deterministic ordering. Cross-tenant tokens surface `InviteNotFound` (not a dedicated cross-tenant branch). The flat `InviteInvalid` branch is removed. `InviteRevoked`, `InviteDeliveryFailed`, `InviteeNotReachable` are NOT in the Phase 2b error union (Rule 1).
5. Two concurrent `join` calls on the same token resolve to exactly one successful member insert; the loser surfaces `InviteAlreadyConsumed` (validated via an atomic conditional UPDATE, §3.3 step 7).
6. On successful `join`, both `topic.invite.accepted` and `topic.member.joined` fan out to active seats atomically with the member insert; **post-join seat activation** (`taskEngine.ensureConversationActivation({ kind: 'topic', ... })`) fires, and the newly-created seat's turn observes those events.
7. `ctx.conversation.decline(token, reason?)` emits `topic.invite.declined` to the inviter's seat and sets `declined_at + decline_reason` on the invite row.
8. Expiry sweep emits `topic.invite.expired` to the inviter; `harness.setInviteClockNow` + `harness.triggerExpiredInviteSweep()` drive this deterministically in tests without affecting wall-clock reads elsewhere in the framework.
9. Startup recovery sweep re-publishes pending invites whose `delivery_attempted_at IS NULL`, re-using the coordinator path; `harness.runInviteStartupSweep()` drives this in tests.
10. Manifest `communication.autoJoinInvitedTopics: true` causes the framework to auto-join pending `topic.invite.received` observations on `agent-inbox` turns before `policy` runs. `false` / absent preserves current behavior. Auto-join never bypasses validation; auto-join failures surface on `TurnTrace.inviteDelivery.received[i].autoJoinError`.
11. `InviteToken` is a branded string; assigning a raw `string` or a `MemberId` to an `InviteToken` is a compile error.
12. `ConversationProjection.topics[id].pendingInvites` and `ConversationProjection.invitesInbox` are populated, ordered by `expiresAt ASC, token ASC`, and stable under observation reordering. Projection scope invariant holds (§8): `pendingInvites` only appears on the inviter's seat projection of the topic; `invitesInbox` only on `agent-inbox:<agentId>` session projections.
13. TurnTrace `inviteDelivery` stamps `issued` / `received` / `accepted` / `declined` / `expired` arrays with the minimal field set; `received[i]` includes `autoJoinAttempted` and `autoJoinError?` when applicable; absent on turns that do not touch invites.
14. Examples demonstrate the end-to-end flow with **no application-level token plumbing** (env vars, hand-offs). Both `autoJoinInvitedTopics: true` and explicit-policy variants are runnable via `yarn run-agent`.
15. `ConversationActivateParams` is a discriminated union `{ kind: 'thread' | 'topic' | 'invite', ... }` with `taskEngine.runConversationActivationBody` arms for all three; compile-time exhaustiveness enforced.
16. One Prisma migration applied cleanly on a fresh DB and on a Phase-2a DB with resolvable inviter seats; **fails loudly with a named-row listing on a Phase-2a DB with unresolved orphan invites** — no silent `agent_id`-as-`member_id` fallback.
17. Zero new public `any`. Branded `InviteToken` and `MemberId` enforced. `AgentId` and `ConversationId` remain unbranded (consistent with Phase 2a).
18. `yarn test` and `yarn build` pass across all workspaces. Type tests enforce discriminated-union exhaustiveness on `ConversationPayload`, `ConversationError`, and `ConversationActivateParams`. Negative type tests assert absence of `InviteRevoked` / `InviteDeliveryFailed` / `InviteeNotReachable` in `ConversationError`.
19. Migration guide at `apps/docs/migration/5.2b-conversation-phase-2b-invite-delivery-and-join-lifecycle-migration.md` is written incrementally alongside implementation, covers every user-visible change, and documents the preflight "drain or ensure seat resolvability" step required before running the migration on a production Phase-2a DB.
