# 5.2a Conversation Phase 2a — Topic member multiplicity (`memberId`)

> **Internal implementation spec.** This document is for framework contributors and maintainers.
> **For framework users migrating to the new APIs**, create and maintain: **`apps/docs/migration/5.2a-conversation-phase-2a-member-multiplicity-migration.md`**.
>
> **No backwards compatibility.** See `apps/docs/todo/types-rules.md` Rule 14. The Phase 2a change is small but breaking at the persistence and selector layers.

**Scope:** Phase 2a closes the multiplicity gap identified after Phase 2: today, topic membership is keyed by `agentId`, so the same agent implementation cannot appear twice in the same topic (two personas, two tenants-behind-one-agent, two customer seats, etc.). Phase 2a introduces **`memberId`** as the topic-scoped member identity, with `agentId` demoted to metadata on the membership row. The simple case (one agent = one seat) stays boilerplate-free by defaulting `memberId` to `agentId`.

**Normative anchor:** [`apps/docs/planned_architecture/multi-agent-communication.md` § Identity model](../planned_architecture/multi-agent-communication.md#identity-model-normative).

### Out of scope (still deferred)

- Cross-runtime transport adapters (Kafka/NATS/external brokers).
- Shared topic documents.
- Advanced voting/consensus selectors, roles beyond `owner | participant`.
- Multi-tenant federation / cross-tenant routing.
- Open/public topics (any-agent self-join without invitation).
- Runtime-level multi-registration of the same `agentId`. Phase 2a resolves multiplicity **at the topic layer**; the registry remains one entry per `agentId`.

---

## Problem Statement

Phase 2 delivered topic primitives but assumed `agentId` is unique within a topic. That assumption is encoded in:

- `TopicMemberSchema` (no per-seat id).
- `conversation_topic_members` PK = `(tenantId, conversationId, agentId)`.
- `conversation_message_deliveries` uniqueness = `(tenantId, conversationId, sequenceNumber, recipientAgentId)`.
- `TopicSelectorSchema.explicit_recipient` = `{ recipientAgentId }`.
- `broadcast` tie-break on `agentId`.
- `outbound.committed` dedupe on `(messageId, senderAgentId)`.
- `ConversationProjection.topics[id].members = Array<{ agentId, role }>`.

Consequences:

- Two seats behind the same `agentId` in one topic is a PK collision at `createTopic` / `join`.
- Fan-out produces at most one delivery per `agentId` per post.
- `explicit_recipient` has no way to disambiguate between seats.
- The Policy projection collapses two seats into one.
- The registry cannot be leaned on for multiplicity: it keys on `agentId`, not seat identity, by design.

Changes:

- `MemberIdSchema` **(NEW)** — `z.string().min(1).brand<'MemberId'>()`. The brand makes `MemberId` non-assignable from raw `string` at compile time and prevents accidental stringly seat usage (Rule 1, Rule 6). Downstream code constructs `MemberId` values via the Zod parser; callers that build identifiers from plain strings must route them through the schema (test fixtures and examples ship with a tiny `memberId(x)` helper in `public-types/conversation/index.ts`).
- `AgentIdSchema` **(NO CHANGE, intentional)** — remains `z.string().min(1)` (unbranded). Phase 2a brands `MemberId` only. Rationale: the incremental safety we need is preventing accidental `string -> MemberId` and enforcing seat identity discipline; branding `AgentId` too would create broad mechanical churn with minimal additional safety value at this phase. The trust boundary remains explicit: `memberId` is nominally distinct, `agentId` is routing metadata.
- `TopicMemberSchema` **(MODIFY)** — add optional `memberId`:
  ```ts
  z.object({
      agentId: AgentIdSchema,
      memberId: MemberIdSchema.optional(),
      role: TopicMemberRoleSchema,
      sessionIdOverride: z.string().min(1).optional(),
  });
  ```
  Semantic: the **effective member identity** is `memberId ?? agentId`. The framework resolves this at `createTopic` / `invite` / `join` time and persists the resolved value as the primary key column. After resolution, every downstream surface uses the resolved `memberId` (never `agentId` as identity).
- `ResolvedTopicMemberSchema` **(NEW)** — the post-resolution shape used on receipts, observations, and projection:
  ```ts
  z.object({
      agentId: AgentIdSchema,
      memberId: MemberIdSchema,
      role: TopicMemberRoleSchema,
      sessionId: z.string().min(1),
  });
  ```
  `TopicCreateReceipt.members`, `TopicJoinReceipt.member`, `topic.member.joined` payload, and the projection member entries all use this resolved shape. Callers never have to reason about `memberId ?? agentId` after receipt.

  **Input/output asymmetry (normative):** input uses `sessionIdOverride?` (an optional hint). Output uses `sessionId` (always present, resolved by the framework from `override ?? default`). `sessionId` is **not** a public input on any schema — it is only produced by the framework.
- `TopicSelectorSchema.explicit_recipient` **(MODIFY)** — closed discriminator on addressing mode:
  ```ts
  z.object({
      kind: z.literal('explicit_recipient'),
      recipient: z.discriminatedUnion('by', [
          z.object({ by: z.literal('agentId'), agentId: AgentIdSchema }),
          z.object({ by: z.literal('memberId'), memberId: MemberIdSchema }),
      ]),
  });
  ```
  - `by: 'agentId'` resolves to exactly one seat iff the topic has exactly one seat with that `agentId`; zero → `RecipientNotMember`; more than one → `RecipientAmbiguous`.
  - `by: 'memberId'` resolves to exactly one seat; zero → `RecipientNotMember`.
- `DeliverySummarySchema` **(MODIFY)** — add `memberId`:
  ```ts
  z.object({
      memberId: MemberIdSchema,
      recipientAgentId: AgentIdSchema,
      sessionId: z.string().min(1),
      messageId: MessageIdSchema,
      sequenceNumber: z.number().int().positive(),
      dedupeHit: z.boolean(),
      correlationId: CorrelationIdSchema.optional(),
  });
  ```
  `recipientAgentId` remains (useful for registry-level dispatch and existing test assertions), but **`memberId` is authoritative**.
- `FanoutSendReceiptSchema.partial.rejected[]` **(MODIFY)** — each entry carries `{ memberId, recipientAgentId, error }`.
- `OutboundTopicMessageSchema` **(MODIFY)** — `senderMemberId?: MemberIdSchema`. Optional; the framework resolves it from the calling `(agentId, topic)` at `post` time (exactly one seat per `agentId` in the topic is required unless `senderMemberId` is supplied). If the caller has two seats in the topic and omits `senderMemberId`, the framework returns `SenderAmbiguous` (new typed error, see below).

  **Rule 1 note (runtime-only invariant):** the "required when multi-seat, optional when single-seat" relationship cannot be expressed in the type system without forcing every single-seat caller (99% of Phase 2 callers) to disambiguate. Encoding it as a mandatory field would regress the simple-case ergonomics protected by Rule 15. The typed `SenderAmbiguous` error compensates: the runtime surface remains honest because every ambiguity returns a deterministic typed error rather than throwing or silently picking a seat.
- `ConversationErrorSchema` **(MODIFY — additive branches only)**:
  - `RecipientAmbiguous` — `explicit_recipient { by: 'agentId' }` matched more than one seat.
  - `SenderAmbiguous` — sender has more than one seat in the topic and did not specify `senderMemberId`.
  - `RecipientNotResolvable` — member exists in the topic but its `agentId` is not registered / not reachable. Deterministic, typed; replaces any ad-hoc runtime failure in this situation.
  - `RecipientNotMember` — unchanged semantics (member not in topic), now evaluated against `memberId`.
- `ConversationApi.post` signature is unchanged at the type level (the new `senderMemberId` lives on `OutboundTopicMessageSchema`).
- `ConversationApi.leave` **(MODIFY)** — gains optional `TopicLeaveOptionsSchema.memberId` so a single `agentId` with two seats can pick which seat leaves. If omitted and the caller has exactly one seat, the framework resolves implicitly; if two, `SenderAmbiguous`.
- `ConversationProjection` **(MODIFY)** — `topics[id].members: Array<{ agentId, memberId, role }>`. Consumer code that pattern-matches `{ agentId, role }` must narrow to the new shape.

Public type/contract discipline:

- No `any` anywhere in `public-types/conversation/**`.
- Effective identity resolution happens exactly once (at member creation); nothing downstream deals in `memberId ?? agentId`.
- Runtime validation uses Zod schemas in the same module as the inferred types.

### 3. Introduce member multiplicity to the internal conversation service

**Rule enforcement:** Rule 1, Rule 4, Rule 5, Rule 12.

**Files:**
- `packages/core/src/internal/conversation/types.ts` **(MODIFY)**
- `packages/core/src/internal/conversation/ConversationService.ts` **(MODIFY)**
- `packages/core/src/internal/conversation/TopicSelector.ts` **(MODIFY)**

#### 3.1 Default `sessionId` resolution (normative)

**Default sessionId rule:** for any seat without `sessionIdOverride`, the default is:

```
sessionId = `topic-${topicId}:${memberId}`
```

Rationale: two seats with the same `agentId` in the same topic MUST land in distinct `sessionId`s — otherwise `ConversationRouter` would read/write the same inbox snapshot for both seats and silently corrupt multi-seat behavior. Keying the default on `memberId` is the minimal, deterministic, collision-free rule. When `memberId` defaults to `agentId` (single-seat case), the resulting `sessionId` is byte-identical to Phase 2, so single-seat inbox topology is preserved.

**Override rule:** callers may still supply `sessionIdOverride` for any seat. The framework rejects `createTopic` / `invite` / `join` with `AlreadyMember` if two seats resolve to the same effective `sessionId` (i.e., two overrides collide, or an override collides with a default).

#### 3.2 Service responsibilities

- **`createTopic`**:
  - For every member, resolve `effectiveMemberId = member.memberId ?? member.agentId`.
  - Enforce uniqueness of `effectiveMemberId` across the members array. Collision → `TopicCreateReceipt.status === 'rejected'` with a typed error (reuse `AlreadyMember`).
  - Resolve `sessionId` per §3.1 and enforce uniqueness of resolved `sessionId` across the members array; collision → `AlreadyMember`.
  - Persist `(tenantId, conversationId, memberId, agentId, role, sessionId, registeredAt)`.
  - Emit `topic.member.joined` with `member: ResolvedTopicMember` (not raw input).
- **`invite` / `join`**:
  - `invite` accepts a `TopicMember` (with optional `memberId`); stores the invitee seat shape alongside the invite token. Collision against existing members (on `memberId` OR effective `sessionId`) → `AlreadyMember`.
  - `join(topic, { inviteToken })` consumes the invite, inserts the member row with the invite's resolved `memberId` and resolved `sessionId`. Joining a second seat for an existing `agentId` is allowed iff `memberId` differs and `sessionId` differs.
- **`leave`**:
  - If the caller has exactly one seat in the topic, resolve implicitly.
  - If the caller has two seats and `options.memberId` is omitted → `SenderAmbiguous`.
  - Emit `topic.member.left` with both `memberId` (required) and `agentId` in the payload.
- **`post`**:
  1. Resolve sender seat: look up seats via `listConversationTopicMembersByAgent({ tenantId, conversationId, agentId: senderAgentId, activeOnly: true })`. Zero → `NotAMember`; one → implicit; multiple → `message.senderMemberId` required else `SenderAmbiguous`; if `senderMemberId` is supplied but does not match any seat for this `agentId` → `NotAMember`.
  2. Apply selector:
     - `broadcast`: deterministic ordering `(role asc, registeredAt asc, memberId asc)`.
     - `round_robin`: rotation cursor persists the last-delivered `memberId` (not `agentId`); next post picks the next active member in registration order.
       - **Edge case (normative):** if the persisted cursor points to a `memberId` that is no longer active (left the topic, or null after migration), rotation restarts from the first active member in registration order. The cursor is advisory, not authoritative — correctness is guaranteed by "next active after persisted cursor, restart on miss."
     - `explicit_recipient`: resolve via the inner discriminator:
       - `by: 'agentId'` → resolve to the unique active seat; multiple → `RecipientAmbiguous`; zero → `RecipientNotMember`.
       - `by: 'memberId'` → resolve to the unique active seat (exact match — never falls back to `agentId`); zero → `RecipientNotMember`.
     - For any resolved seat whose `agentId` is not registered/reachable, the per-recipient delivery is `RecipientNotResolvable`. The message row is still committed so replay is stable, mirroring Phase 2 idempotency rules.
  3. Append one row to `conversation_messages` with `senderMemberId = resolved sender seat memberId` (atomic with per-recipient delivery rows).
  4. Record deliveries keyed on `memberId` (unique `(tenantId, conversationId, sequenceNumber, memberId)`).
  5. Fan out with `memberId` as the recipient identity; each `DeliverySummary` has both `memberId` and `recipientAgentId`.
  6. Inject the single `outbound.committed` observation to the **sender seat's** inbox (resolved `sessionId`); dedupe key is `(messageId, senderMemberId)`.
- **`ConversationRouter`** — per-target triple is still `(tenantId, sessionId, agentId)`; `memberId` resolves upstream in `ConversationService`. No router signature change beyond threading `memberId` through `DeliverySummary` metadata.

#### 3.3 Deterministic contracts (Phase 2a MUST)

- All selector outputs stable and reproducible under multiplicity (ordering by `memberId`; rotation by persisted `memberId` cursor with the restart-on-miss rule).
- `MAX_TOPIC_MEMBERS = 64` remains the bound and is evaluated against the count of seats (not distinct `agentId`s).
- Idempotency replay: same `(tenantId, conversationId, senderMemberId, idempotencyKey)` returns the original verdict byte-for-byte. The existing `(tenantId, conversationId, senderAgentId, idempotencyKey)` unique index is **swapped** for `(tenantId, conversationId, senderMemberId, idempotencyKey)` in one irreversible migration step (see §4).

#### 3.4 Member-lookup API split (normative)

Phase 2's `getConversationTopicMember({ agentId })` becomes ambiguous under multiplicity. The internal lookup surface splits:

- `getConversationTopicMemberByMemberId({ tenantId, conversationId, memberId })` — exact. Returns at most one row.
- `listConversationTopicMembersByAgent({ tenantId, conversationId, agentId, activeOnly? })` — returns zero, one, or many seats for a given `agentId` in the topic.

The old `getConversationTopicMember({ agentId })` signature is **removed**. Every caller (`post`, `invite`, `leave`) is rewritten to the correct pair above. This split is a prerequisite for any correct multi-seat dispatch — without it, every service-level lookup has to deal with "which of N seats?" at its callsite.

Changes:

- `conversation_topic_members`:
  - Add column `member_id TEXT NOT NULL`.
  - Drop PK `(tenant_id, conversation_id, agent_id)`; add PK `(tenant_id, conversation_id, member_id)`.
  - Add non-unique index `(tenant_id, conversation_id, agent_id)` for "list seats for this agent in this topic" queries (backs `listConversationTopicMembersByAgent`).
  - Add unique index `(tenant_id, conversation_id, session_id)` — every seat MUST land in a distinct session (§3.1 default + override rule). Violation → the insert fails, surfaced as `AlreadyMember` at the service layer.
  - Backfill: `UPDATE conversation_topic_members SET member_id = agent_id` before applying the new PK (single irreversible migration step, documented).
- `conversation_topic_invites`:
  - Add column `invitee_member_id TEXT NULL` (nullable for historical invites; backfill `invitee_member_id = invitee_agent_id` in the same migration).
  - On new invites, `invitee_member_id` is required by the store API (enforced at the `issueConversationTopicInvite` level).
- `conversation_message_deliveries`:
  - Add column `member_id TEXT NOT NULL`.
  - Drop unique `(tenant_id, conversation_id, sequence_number, recipient_agent_id)`.
  - Add unique `(tenant_id, conversation_id, sequence_number, member_id)`.
  - Backfill: `UPDATE conversation_message_deliveries SET member_id = recipient_agent_id` prior to the constraint swap.
  - `recipient_agent_id` stays NOT NULL (registry dispatch still uses it).
- `conversation_messages`:
  - Add column `sender_member_id TEXT NOT NULL` (backfill from `sender_agent_id` for all existing rows; thread rows continue to have `sender_member_id = sender_agent_id` going forward because threads are always 1:1). Non-null invariant is mandatory so the new idempotency index holds.
  - `sender_agent_id` stays.
  - **Idempotency index swap (normative, A2):**
    - Drop `@@unique([tenantId, conversationId, senderAgentId, idempotencyKey])`.
    - Add `@@unique([tenantId, conversationId, senderMemberId, idempotencyKey])`.
    - This is the ONLY way the `post` replay contract in §3.3 is honored. Without it, two seats sharing `agentId` that reuse an `idempotencyKey` collide on the old unique constraint instead of each dedupe'ing against their own seat's prior post.
- `conversation_topics.rotation_cursor`:
  - Repurpose from "last-delivered registration index" (integer) to "last-delivered `member_id`" (`TEXT NULL`). Migration backfills by mapping the old integer cursor (if any) to the corresponding `member_id` at the current registration order; documented as best-effort (the cursor is advisory — the restart-on-miss rule in §3.2 guarantees correctness, so a wrong mapping costs at most one uneven rotation tick on the next post).

Store interface changes (`IWorkingMemorySessionStore`):

- `createConversationTopic(..., members: Array<ResolvedTopicMember & { registeredAt: string }>)` — accepts resolved members (never raw `TopicMember`).
- `addConversationTopicMember({ tenantId, conversationId, memberId, agentId, role, sessionId, registeredAt })`.
- `leaveConversationTopicMember({ tenantId, conversationId, memberId, leftAt })` — **keyed on `memberId`** (was `agentId`).
- `getConversationTopicMemberByMemberId({ tenantId, conversationId, memberId })` **(NEW)** — replaces the old `getConversationTopicMember({ agentId })`.
- `listConversationTopicMembersByAgent({ tenantId, conversationId, agentId, activeOnly? })` **(NEW)** — returns zero/one/many seats for a given `agentId`. Required by `post` sender-seat resolution and by `invite` collision checks.
- `listConversationTopicMembers({ tenantId, conversationId, activeOnly? })` — returns `Array<ResolvedTopicMember & { registeredAt; leftAt }>`.
- `issueConversationTopicInvite({ ..., inviteeMemberId })` — required. `consumeConversationTopicInvite(...)` returns `{ ..., inviteeMemberId, sessionIdOverride }` so the service can resolve and insert the row.
- `appendConversationMessage({ ..., senderAgentId, senderMemberId, ... })` — `senderMemberId` required; for thread rows the service passes `senderMemberId = senderAgentId`.
- `findConversationMessageByIdempotencyKey({ tenantId, conversationId, senderMemberId, idempotencyKey })` — **parameter renamed** from `senderAgentId` to `senderMemberId`. Callers rewrite mechanically. This is the runtime half of the index swap above.
- `recordConversationMessageDeliveries({ ..., rows: Array<{ memberId, recipientAgentId, sessionId, ... }> })` — both `memberId` and `recipientAgentId` are required on every row.
- `listConversationMessageDeliveries(...)` — returns `Array<ConversationMessageDeliveryRecord>` where each row carries both `memberId` and `recipientAgentId`.
- `getConversationTopicRotationCursor`, `setConversationTopicRotationCursor` — cursor type is `string | null` (the resolved `memberId` of the last-delivered recipient, or `null` to force restart-from-first on the next post).

The old `getConversationTopicMember({ agentId })` is **removed** (not deprecated) — there is no correct behavior for it under multiplicity, and leaving it as a "returns any one seat" method would encode a bug.

Atomicity: unchanged from Phase 2 (all multi-row writes stay in one transaction each).

When `memberId === agentId` (single-seat) the redundancy is explicit and honest; when they differ it is essential. The duplication is bounded (two short strings per recipient) and the alternative (a "differs only" encoding) complicates consumers.

- `ConversationMessageSummarySchema` gains `senderMemberId` and `recipientMemberId` fields. **For topic summaries these are required; for thread summaries they are unused (equal to `senderAgentId` / `recipientAgentId`).** The schema makes them optional for source-level compatibility, but topic emission always stamps them.

- No raw payloads.

### 7. Policy-safe conversation read surface

**Rule enforcement:** Policy purity rule, Rule 1, Rule 4, Rule 5, Rule 12.

**Files:**

- `packages/core/src/public-types/conversation/projection.ts` **(MODIFY)**

Changes:

- `ConversationProjection.topics[id].members` **(MODIFY)** — `Array<{ agentId, memberId, role }>`.
  - **Shape decision (B3):** kept as an `Array` (not `Record<MemberId, MemberEntry>`) because Policy code iterates over members more often than it looks them up by id, and an array is easier to narrow/filter in the ergonomic Policy style.   - **Ordering invariant (B2, normative):** the reducer sorts the members array by `memberId` ascending on every pass. This guarantees:

### 9. No backwards compatibility posture (explicit)

Phase 2a ships with zero compatibility shims:

- `MemberIdSchema` is branded; `AgentIdSchema` remains unbranded by design (see §1 rationale). No mechanical literal rewrite for `agentId` call sites is required in Phase 2a.
- `TopicSelectorSchema.explicit_recipient` replaces `recipientAgentId` with the closed `recipient` discriminator. Mechanical rewrite in callers.
- `DeliverySummary` gains required `memberId`.
- `ConversationProjection.topics[id].members` entries gain required `memberId`; ordering invariant applies.
- `TurnTrace.topicSelectorDecision.resolvedRecipients` renamed to `resolvedMembers` with a wider element shape.
- `conversation_topic_members` PK changes; unique `(tenant, conversation, session_id)` added. Single irreversible migration; backfill fills `member_id = agent_id`.
- `conversation_message_deliveries` unique constraint changes. Single irreversible migration.
- `conversation_messages` idempotency index changes from `(..., sender_agent_id, idempotency_key)` to `(..., sender_member_id, idempotency_key)`. Single irreversible migration; backfill fills `sender_member_id = sender_agent_id`.
- `rotation_cursor` column type changes from `INTEGER` to `TEXT NULL`.
- `IWorkingMemorySessionStore` loses `getConversationTopicMember`; adds `getConversationTopicMemberByMemberId` and `listConversationTopicMembersByAgent`.
- `findConversationMessageByIdempotencyKey` parameter renamed from `senderAgentId` to `senderMemberId`.
- New `ConversationError` branches: `RecipientAmbiguous`, `SenderAmbiguous`, `RecipientNotResolvable`.

**Operational posture (A2, A4):** the migration involves a primary-key shift on `conversation_topic_members`, a unique-constraint swap on `conversation_message_deliveries`, and a unique-constraint swap on `conversation_messages`. On standard PostgreSQL these cannot be performed safely with concurrent writers without additional choreography (shadow-table + cutover). The migration guide therefore instructs operators to **stop writers, apply the migration, then resume**. Framework runtimes do not attempt online migration; this is called out explicitly in the migration doc.

### 10. Clean API constraints (MUST hold after implementation)

1. `memberId` is the single identity used by selectors, deliveries, idempotency, outbound-committed dedupe, projection, and TurnTrace.
2. `agentId` on a topic-member row is metadata: it selects the registry target for dispatch and remains on `DeliverySummary` / observations for registry-level assertions.
3. Supplying `memberId` is optional at input; the framework resolves once and all output shapes carry the resolved value.
4. `explicit_recipient { by: 'agentId' }` is typed-safe for the unambiguous case and returns a deterministic typed error otherwise.
5. A single `agentId` with two seats in a topic MUST be able to `post`, `leave`, and be addressed independently.
6. Zero new public `any` in Phase 2a contracts, payloads, receipts, errors, projection, or trace fields.
7. `MAX_TOPIC_MEMBERS = 64` continues to apply (seat count).
8. Default `sessionId` is `topic-<topicId>:<memberId>` (§3.1); every seat lands in a distinct session.
9. `getConversationTopicMemberByMemberId` is the only exact-match lookup; `listConversationTopicMembersByAgent` is the only `agentId`-keyed lookup.
10. Projection member array is sorted by `memberId` ascending on every reducer pass.
11. `conversation_messages` idempotency index is keyed on `sender_member_id` (not `sender_agent_id`).
12. Rotation cursor is `memberId | null`; restart-from-first when the persisted id is no longer active.

### 11. Isolation guarantees (A4, normative)

Phase 2a allows N distinct `sessionId`s per `agentId` inside one topic. The following guarantees hold so implementors and users can reason about concurrency:

1. **Snapshot isolation.** Each seat has its own `(tenantId, sessionId)`. Inbox, mental state, learning projection, and TurnTrace are stored and loaded per-session. Observations routed to seat `S1` never appear in seat `S2`'s snapshot, even when `S1.agentId === S2.agentId`.
2. **Activation isolation.** `ConversationActivateParams` carries a `routingSessionId` already (Phase 2). Phase 2a relies on this: each cold turn runs against exactly one seat's session. Two concurrent activations for two seats of the same `agentId` run as two independent sessions of the same agent runtime.
3. **Registry cardinality.** The runtime registry remains one entry per `agentId`. Multiplicity is resolved entirely at the topic layer (seat table). The agent's code is re-entered N times in N sessions; any in-process caches inside the agent implementation MUST be keyed by `sessionId` (or `ctx.sessionId` in the public API) to remain correct. This is a framework constraint that cleanly extends Phase 2's existing "session is the unit of state" rule.
4. **No cross-seat communication shortcuts.** A seat cannot read another seat's inbox, snapshot, or M.memory — even seats with the same `agentId`. All cross-seat information flow goes through topic messages (observable, logged, auditable).
5. **Fan-out atomicity.** One `post` produces one `conversation_messages` row, N `conversation_message_deliveries` rows (one per resolved seat), and one `outbound.committed` observation to the sender seat's inbox — all in a single transaction. Per-seat delivery failures do not roll back the message row; they are captured in the delivery rows and in the `FanoutSendReceipt.partial.rejected` array.
6. **No agent-level locking.** Phase 2a does NOT introduce any cross-seat lock, queue, or serialization at the agent level. Two seats of the same `agentId` can process concurrently (subject to the existing per-session `isInflight` queue semantics).

These guarantees are what make "same `agentId`, multiple seats" safe and useful. They are enforced by tests in §Testing 2 (new `conversation.topic.multiplicity.isolation.test.ts`).

## ✅ Acceptance Criteria

1. A single `agentId` can appear as N distinct members in one topic via distinct `memberId`s, boundable only by `MAX_TOPIC_MEMBERS`.
2. **Single-seat Phase 2 semantics are preserved** when `memberId` defaults to `agentId`. Source-level changes are mechanical and exhaustively listed in §9 (`MemberId` branding, `explicit_recipient` selector shape, `DeliverySummary.memberId`, projection member shape, `resolvedMembers` rename, store API split, `findConversationMessageByIdempotencyKey` rename). No semantic regression under single-seat usage.
3. Selectors, deliveries, idempotency (index + service lookup), outbound-committed dedupe, projection, and TurnTrace all key on `memberId`.
4. `explicit_recipient { by: 'agentId' }` returns `RecipientAmbiguous` when more than one seat matches; `by: 'memberId'` addresses a single seat directly and **never** falls back to `agentId` matching (namespace safety).
5. `post` from an `agentId` with two seats requires `senderMemberId`; omission yields typed `SenderAmbiguous`; a `senderMemberId` that does not match any seat for this `agentId` yields typed `NotAMember`.
6. Default `sessionId = topic-<topicId>:<memberId>`; two seats sharing `agentId` run in distinct sessions with independent snapshots and inboxes (isolation guarantees §11 hold).
7. Reference agents demonstrate the two-seats-one-agent scenario end-to-end (create, broadcast, round-robin, explicit-by-member, projection narrowing, idempotent replay).
8. `getConversationTopicMember` is removed; `getConversationTopicMemberByMemberId` and `listConversationTopicMembersByAgent` are the exclusive lookup paths.
9. Projection member array is sorted by `memberId` ascending; reducer is idempotent and observation-order-independent.
10. Round-robin rotation restarts from the first active seat when the persisted cursor points to a non-active `memberId`.
11. `conversation_messages` unique index on idempotency is `(tenantId, conversationId, senderMemberId, idempotencyKey)` post-migration; pre-migration rows replay byte-identically.
12. One Prisma migration applied cleanly on a fresh and on a Phase-2 database; backfill correctness verified by test. Operational posture (writers stopped during migration) is stated in the migration guide.
13. Zero new public `any`; branded `MemberId` is non-interchangeable with `AgentId` at compile time; zero stringly errors.
14. `yarn test` and `yarn build` pass; type tests enforce the new constraints.
15. Migration guide at `apps/docs/migration/5.2a-conversation-phase-2a-member-multiplicity-migration.md` is written incrementally alongside implementation and covers every user-visible change.
16. `apps/docs/0-aplret_contracts.md`, `11-how_to_test_aplret_agents.md`, and `12-how_to_debug_with_turn_trace.md` are updated to reflect **Phase 2 + Phase 2a** (topics, fan-out, `topic.*` observations, `outbound.committed`, `ConversationProjection`, `topicSelectorDecision`, `fanoutSummary`, multi-seat). Phase 2 debt is cleared as part of Phase 2a — no "Phase 2 gap" remains in the canonical contract doc after this work.
