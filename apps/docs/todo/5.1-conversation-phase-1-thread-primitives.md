# 5.1 Conversation Phase 1 — Thread Primitives, Typed Contracts, and Trace Stamping

> **Internal implementation spec.** This document is for framework contributors and maintainers.
> **For framework users migrating to the new APIs**, create and maintain: **`apps/docs/migration/5.1-conversation-phase-1-thread-primitives-migration.md`**.

**Scope:** Phase 1 implements the first shippable slice from `apps/docs/planned_architecture/multi-agent-communication.md`:

1. Thread-only conversation primitives (`startThread`, `send`, typed receipts/errors).
2. Conversation observation ingestion (`source: 'conversation'`) through the existing observation pipeline.
3. Idempotency and queue/reject semantics for thread sends.
4. TurnTrace stamping for conversation metadata in turns that consume/emit conversation messages.
5. Canonical evolving example agent in `apps/examples/conversation-reference-agent/` with deterministic harness coverage.
6. Public type/schema exports for conversation contracts (Zod-first, no public `any`).

Out of scope (deferred to later phases):

- Topic runtime (`createTopic`, membership, fan-out, turn-taking policies).
- Cross-runtime transport adapters (Kafka/NATS).
- Selector policies and shared topic documents.

---

## Problem Statement

The architecture doc now defines conversation as a first-class primitive, but the runtime still only exposes child delegation (`sendTaskToAgent`) and does not provide thread-native APIs, thread message persistence, or conversation-specific trace fields.

### 3. Add internal conversation runtime service (thread-only slice)

**Rule enforcement:** Rule 1, Rule 4, Rule 5, Rule 12.

**Files:**
- `packages/core/src/internal/conversation/types.ts` **(NEW)**
- `packages/core/src/internal/conversation/ConversationService.ts` **(NEW)**
- `packages/core/src/internal/conversation/ConversationRouter.ts` **(NEW)**

Responsibilities:

- `startThread` atomic semantics:
  - create thread record + append initial message in one transactional boundary,
  - if append fails, thread is not created.
- `send` behavior for existing thread:
  - validate participant authority,
  - apply idempotency,
  - apply queue mode (`queue` or `reject`) when in-flight turn exists.
- Produce typed `SendReceipt` for all outcomes.
- Route accepted messages into the recipient’s inbox as normalized conversation observations:
  - `source: 'conversation'`
  - `kind: 'message.received'`
- Emit typed delivery failures as:
  - `source: 'conversation'`
  - `kind: 'delivery.failed'`

Deterministic queue/reject contract (Phase 1 MUST):

- Default `queueMode` for `send` is `reject` unless explicitly set to `queue`.
- `in-flight` means the recipient session currently has an unresolved await state for the same thread (token still pending in control-plane state).
- `queue` mode uses FIFO ordering per thread.
- `queue` mode has bounded depth (configurable via runtime setting; default must be documented and test-covered).
- When queue is full, return typed `rejected` receipt with explicit `ConversationError` (no silent drop).
- Sequence numbers are assigned only when a message is durably appended; queued (not yet appended) messages do not receive committed sequence numbers until accepted.
- Replay with the same idempotency key must return the previously committed outcome and set `dedupeHit: true`.

> [!NOTE]
> Phase 1 does not introduce topic runtime behavior. Topic contracts may exist internally for forward design, but public Phase 1 methods must not accept topic-only inputs.

### 4. Persist conversation messages and idempotency metadata

**Rule enforcement:** Rule 1, Rule 8 (end-to-end safety), Rule 9 (DB authority), Rule 10.

**Files:**
- `packages/memory-sql/prisma/schema.prisma` **(MODIFY)**
- `packages/memory-engine/src/stores/SessionStore.ts` **(MODIFY)**
- `packages/memory-sql/src/WorkingMemorySessionStore.ts` **(MODIFY)**
- `packages/core/src/orchestration/InMemorySessionManager.ts` **(MODIFY)**

Add durable conversation storage model with:

- `conversation_threads` (or equivalent lifecycle table):
  - tenant id
  - conversation id
  - status (`open|closed|archived`)
  - owner/participants metadata required by authority checks
  - created/updated timestamps
- `conversation_messages` append-only log:
  - tenant id
  - conversation id
  - sequence number (monotonic per conversation)
  - message id
  - sender id
  - idempotency key (nullable)
  - payload JSON
  - timestamps
- indexes/uniques:
  - `conversation_threads`: `(tenantId, conversationId)` unique
  - `conversation_messages`: `(tenantId, conversationId, sequenceNumber)` unique
  - `conversation_messages`: `(tenantId, conversationId, senderAgentId, idempotencyKey)` unique when key present

Update store interfaces with typed methods for:

- create/open thread
- close/archive thread
- append conversation message
- list/replay by conversation id and sequence
- idempotency lookup
- thread status updates (`open|closed|archived`)

Atomicity requirement:

- `startThread` commit must write thread lifecycle row and first message row in one transaction.
- `close` commit must update lifecycle state atomically with any required terminal observation staging.
