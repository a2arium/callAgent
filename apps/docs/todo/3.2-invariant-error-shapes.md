# Runtime Reference: Turn Lifecycle and Enforcement

This document is normative. It defines the runtime obligations for loop-mode APLRET execution.

## Scope

- turn lifecycle
- inbox semantics
- enforcement points
- error contracts
- public vs internal runtime surface

## Definitions

- **Turn**: one iteration of APLRET module execution producing one `TurnOutcome`.
- **Inbox current**: observations staged for the upcoming turn only.
- **Inbox all**: append-only observation log.
- **Pending**: control state for awaited inputs/tools/children.

## Turn lifecycle (normative)

### Rule: Pre-flight manifest resolution

Before the first turn, the runtime MUST:
1. Resolve Agent Card (inline > path > default)
2. Resolve Runtime Manifest (inline > path > default)
3. Validate schemas and enforce identity match (name/version)
4. Compute and store stable JSON hashes for both

If any step fails, the loop MUST NOT start.

### Turn execution order

For each turn, the runtime MUST execute modules in this order:

1. Attention
2. Perception
3. Learning
4. Policy
5. Shield
6. Execution
7. Transition

### Rule: inbox snapshot timing

- The runtime MUST snapshot `env.inbox.current` before Perception runs.
- Perception MUST see only `env.inbox.current`.
- After the turn ends, the runtime MUST clear `env.inbox.current`.
- The runtime MUST append the staged batch to `env.inbox.all` in order.

## Module I/O contracts (normative)

### Policy

- Policy MUST be synchronous.
- Policy MUST receive only `MentalState`.
- Policy MUST NOT receive `env` or `ctx`.

### Execution

- Execution MUST return `ExecOutcome`:

```ts
type ExecOutcome<Data = unknown, Err = unknown> = {
  action: ExecAction;
  result: ExecResult<Data, Err>;
};
```

### Transition

- Transition MUST consume the `ExecOutcome` shape above.
- Transition MUST produce a `TurnOutcome`.

### Continue outcomes

- If Transition returns `continue`, it MUST include `observations: Observation[]`.

## Resume mechanics (normative)

### Await outcomes

- `await_input` MUST include an input token.
- `await_tool` MUST include a tool token.
- `await_child` MUST include a child token.

### Token matching

When resuming:

- completion observations MUST carry the same token as the awaited token
- the runtime MUST reject completions with unknown tokens
- the runtime MUST reject completions whose token does not match the pending category

### Injection rule

All resumes MUST re-enter through `env.inbox.current` as observations.

- tool completion -> `source: 'tool', kind: 'tool.completed'`
- child completion -> `source: 'child', kind: 'child.completed'`
- user input -> `source: 'user', kind: 'input.provided'`

## Enforcement points (normative)

The runtime MUST enforce these before modules run:

- observation source/kind validity
- presence of required tokens
- payload envelope validation (at least shallow)

The runtime MUST enforce these at Transition boundary:

- await outcomes require tokens
- terminal outcomes forbid new awaits
- `continue` includes observations

The runtime SHOULD enforce these structurally by wiring:

- Policy receives only `m`
- Perception receives only `env` and `attention` output

## Error contracts (normative)

### Invariant errors

Invariant errors MUST be structured.

```ts
type InvariantError = {
  code: string;
  message: string;
  stage?: string;
  required?: string[];
  forbidden?: string[];
  pendingSnapshot?: unknown;
  inboxSummary?: {
    count: number;
    entries?: Array<{ source: string; kind: string }>;
  };
  correlationId?: string;
};
```

### Observation validation errors

If an observation is invalid, the runtime MUST:

- fail the turn with an invariant error, OR
- inject a `source: 'internal', kind: 'validation.failed'` observation and continue

The runtime MUST choose one of these behaviors and document it as part of the public contract.

## Public vs internal runtime surface

### Public surface (stable)

- module execution order
- inbox semantics (current vs all)
- observation taxonomy and envelope rules
- `ExecOutcome` and `TurnOutcome` shapes
- await/resume behavior and token rules
- invariant error shape
- TurnTrace existence and minimum required fields (if TurnTrace is documented)

### Internal surface (unstable)

- internal snapshot layout details
- raw `controlVars` structure if not explicitly documented
- internal validator helper names
- internal telemetry exporter implementation

## TurnTrace (normative)

If TurnTrace is enabled, the runtime MUST:

- emit exactly one TurnTrace per turn
- include manifest provenance: `agentCardSource`, `runtimeManifestSource`, `agentCardHash`, `runtimeManifestHash`
- include control flow and decisions: at least `turn`, `turnId`, `stageBefore`, `stageAfter`, inbox summary, intent kind, shield action, execAction kind, transition kind, pending summary

## Compatibility

If the runtime changes any documented public behavior above, it is a breaking change unless explicitly versioned and migrated.
