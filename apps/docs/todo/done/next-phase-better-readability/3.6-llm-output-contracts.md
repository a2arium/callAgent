# 3.6 Canonical LLM Output Contracts (Enforced)

> **Internal implementation spec.** This document is for implementers (framework contributors and maintainers). It describes file-level changes, type redesigns, and acceptance criteria.
> **For framework users migrating their agents**, see the end-user migration guide: **[apps/docs/migration/3.6-llm-output-contracts-migration.md](../migration/3.6-llm-output-contracts-migration.md)** (to be created as part of this task).

**Scope:** This document covers enforcing canonical LLM output contracts at the framework level: typed `ILLMCaller` / `PureLLMPort` interfaces (eliminate all `any`), Zod-backed `LLMCallOptions` / `ExecOutcome` schemas, framework-level output contract enforcement in Execution, canonical `internal/llm.responded` and `internal/validation.failed` observation emission for LLM results and contract failures, `LLMCallTrace` enrichment with contract metadata, and elimination of all `as any` casts in LLM-related code paths.

Out of scope: test harness helpers (`expectLLMCall`, `expectExecOutcome`) — those are owned by 3.7. This task produces the typed APIs and observations that 3.7 will consume.

---

## Problem Statement

The APLRET contracts (`0-aplret_contracts.md`, §LLM output contract requirements, §Canonical execution shape) and the LLM usage guide (`10-how_to_use_llm_in_aplret.md`) mandate that:

1. **Structured LLM output must be contracted** — Execution MUST supply an explicit Zod / JSON Schema output contract when expecting structured (non-free-text) output.
2. **Contract failures must be handled explicitly** — failures MUST produce structured `ExecResult` errors, Transition MUST emit observations, Learning MUST write durable facts.
3. **LLM calls are effects** — they belong exclusively in Execution. Results flow through: `Execution → Transition (observations) → inbox → Perception → Learning → MentalState`.
4. **`ExecOutcome` is the canonical execution shape** — `{ action: ExecutableAction; result: ExecResult }`.
5. **Type system rules** — no `any` in public APIs (Rule 5), schemas as source of truth (Rule 2), illegal states must not compile (Rule 4).

> [!NOTE]
> **Naming: `ExecAction` vs `ExecutableAction`.** `0-aplret_contracts.md` uses the name `ExecAction` in the `ExecOutcome` definition. The codebase uses `ExecutableAction` (defined via `ExecutableActionSchema` in `intent.ts`). This task canonicalizes on **`ExecutableAction`** (the name that exists in code and matches the Zod schema). `0-aplret_contracts.md` must be updated to use `ExecutableAction` as part of this task (see §Documentation, item 12).

The codebase violates every one of these rules.

## 🏗 Requirements

### 1. Define `LLMCallOptionsSchema` and `LLMSettingsSchema` as Zod-backed schemas

**Rule enforcement: Rule 2 (Schemas Are Source of Truth), Rule 4 (Illegal States Must Not Compile), Rule 5 (No `any`), Rule 6 (APIs Guide Autocomplete)**

File: `packages/core/src/types/llmContracts.ts` **(NEW)**

Define the canonical type for LLM call options. This replaces all `Record<string, any>` option parameters.

```typescript
import { z, type ZodType } from 'zod';

/**
 * Output contract for structured LLM responses.
 * `schema` accepts either a Zod type (preferred) or a plain JSON Schema object.
 * At runtime, callllm handles both; the framework validates the shape here.
 */
export const LLMOutputContractSchema = z.object({
    name: z.string().min(1),
    schema: z.union([
        z.instanceof(z.ZodType),
        z.record(z.string(), z.unknown()),
    ]),
});
export type LLMOutputContract = {
    name: string;
    schema: ZodType | Record<string, unknown>;
};

export const LLMSettingsSchema = z.object({
    temperature: z.number().min(0).max(2).optional(),
    maxTokens: z.number().int().positive().optional(),
    topP: z.number().min(0).max(1).optional(),
    seed: z.number().int().optional(),
    stop: z.union([z.string(), z.array(z.string())]).optional(),
}).passthrough();
export type LLMSettings = z.infer<typeof LLMSettingsSchema>;

/**
 * LLMCallOptions composes LLMSettings (shared fields) and adds
 * call-specific options. Uses .pick() to avoid duplicating field
 * definitions from LLMSettingsSchema.
 */
export const LLMCallOptionsSchema = LLMSettingsSchema
    .pick({ temperature: true, seed: true })
    .extend({
        data: z.unknown().optional(),
        jsonSchema: LLMOutputContractSchema.optional(),
        schema: z.union([
            z.instanceof(z.ZodType),
            z.record(z.string(), z.unknown()),
        ]).optional(),
        telemetryNodeId: z.string().optional(),
    })
    .passthrough();
export type LLMCallOptions = z.infer<typeof LLMCallOptionsSchema>;
```

> [!IMPORTANT]
> **Deliberate Rule 4 trade-off: `.passthrough()`.** Both `LLMSettingsSchema` and `LLMCallOptionsSchema` use `.passthrough()`, which means unknown keys pass both compile-time and runtime validation. This is a deliberate trade-off: the `callllm` library accepts provider-specific options (e.g., OpenAI's `logprobs`, Anthropic's `thinking`) that the framework cannot enumerate. Without `.passthrough()`, every provider-specific option would require a framework update. The typed fields (`temperature`, `seed`, `jsonSchema`, `data`) provide autocomplete and validation for framework-owned options; provider-specific options flow through unchecked. **Consequence:** a typo like `{ temprature: 0.5 }` will compile and pass validation silently. This is the accepted cost of supporting an open provider ecosystem at the adapter boundary.

> [!NOTE]
> **`LLMOutputContract.schema` typing.** The `schema` field accepts `ZodType | Record<string, unknown>` — this distinguishes "Zod schema object" from "plain JSON Schema object" from "random garbage" (e.g., `schema: 42` will be rejected at runtime). Perfect compile-time safety is impossible here because Zod types are runtime values, but this is significantly better than `z.unknown()`. The manually-written TypeScript type mirrors the Zod schema but uses the imported `ZodType` from Zod for better DX — `z.infer` of `z.instanceof(z.ZodType)` produces the runtime class type, which is correct but less ergonomic.

**Acceptance criteria:**
- Types exported from `packages/core/src/index.ts`.
- `LLMCallOptions` used in `ILLMCaller.call()` and `ILLMCaller.stream()` — replaces `Record<string, any>`.
- `LLMSettings` used in `ILLMCaller.updateSettings()` and `LLMConfig.defaultSettings`.
- `LLMOutputContract` provides typed `jsonSchema` for autocomplete.

### 2. Define `ExecOutcomeSchema` and `ExecResultSchema` as Zod-backed schemas

**Rule enforcement: Rule 2, Rule 4, Rule 5**

File: `packages/core/src/types/llmContracts.ts` (append) or `packages/core/src/types/execOutcome.ts` **(NEW)**

The APLRET contracts define `ExecOutcome<Data, Err> = { action: ExecutableAction; result: ExecResult<Data, Err> }` but this type does not exist in the codebase. Define it with Zod backing.

> [!IMPORTANT]
> **Deliberate Rule 2 exception — dual-purpose design.** `ExecResult` and `ExecOutcome` have **both** a Zod schema and a separate generic TypeScript type. This is a deliberate exception to Rule 2 ("schemas are single source of truth") because Zod cannot express TypeScript generics. The two serve different roles:
>
> - **Zod schema (`ExecResultSchema`, `ExecOutcomeSchema`):** the *runtime validation floor*. Used at framework boundaries (TurnTrace construction, loopRunner validation, test assertions). Validates structural shape with `data: z.unknown()`.
> - **Generic TypeScript type (`ExecResult<Data, Err>`, `ExecOutcome<Data, Err>`):** the *compile-time contract* for agent authors. Provides type-safe `data?: Data` and `error?: Err` narrowing inside `Modules.execution` and `Modules.transition`.
>
> `z.infer<typeof ExecResultSchema>` produces `{ data?: unknown; ... }` — this is intentionally wider than the generic type. Agent code uses the generic; framework internals validate with the schema. **The Zod schema must be kept structurally compatible with the generic type** (same field names, same optionality). Tests in `execOutcome.test.ts` must verify this compatibility.

```typescript
import { z } from 'zod';
import { ExecutableActionSchema } from './intent.js';
import type { ExecutableAction } from './intent.js';
import { ExecErrorPayloadSchema } from './observation.js';
import type { ExecErrorPayload } from './observation.js';

// Runtime validation floor — used at framework boundaries
export const ExecResultSchema = z.object({
    status: z.enum(['ok', 'error']),
    data: z.unknown().optional(),
    error: ExecErrorPayloadSchema.optional(),
    receipts: z.unknown().optional(),
    correlationId: z.string().optional(),
    toolId: z.string().optional(),
    ts: z.number().optional(),
});

// Compile-time contract — used by agent authors (see design note above)
export type ExecResult<Data = unknown, ErrorPayload extends ExecErrorPayload = ExecErrorPayload> = {
    status: 'ok' | 'error';
    data?: Data;
    error?: ErrorPayload;
    receipts?: unknown;
    correlationId?: string;
    toolId?: string;
    ts?: number;
};

export const ExecOutcomeSchema = z.object({
    action: ExecutableActionSchema,
    result: ExecResultSchema,
});

export type ExecOutcome<Data = unknown, ErrorPayload extends ExecErrorPayload = ExecErrorPayload> = {
    action: ExecutableAction;
    result: ExecResult<Data, ErrorPayload>;
};
```

**Acceptance criteria:**
- `ExecOutcome` exported from `packages/core/src/index.ts`.
- `ExecResultSchema` provides runtime validation for execution results (used in `oneTurn` and `loopRunner`).
- `ExecResult` type in `oneTurn.ts` replaced with import from this file (single source of truth).
- `Modules.execution` return type updated to `Promise<ExecOutcome<ExecData, ExecError>>`.
- Tests verify that any value satisfying `ExecResult<SomeData>` also passes `ExecResultSchema.safeParse()` (structural compatibility).

### 8. Produce canonical `internal/llm.responded` and `internal/validation.failed` observations

**Rule enforcement: APLRET contracts §LLM output contract requirements, §Observation model**

Files: `packages/core/src/loop/loopRunner.ts`, `packages/core/src/types/observation.ts`

**Problem:** The observation taxonomy declares `internal/llm.responded` and `internal/validation.failed`, but neither is produced by the framework for LLM call results. Default transition emits only `internal/state.noted`.

**Changes:**

1. **Default transition:** When `ExecResult.data` contains LLM response data (identifiable via `toolId: 'language'` or a new structured marker from execution), emit `internal/llm.responded` instead of `internal/state.noted`.

2. **Default transition (error path):** When `ExecResult.status === 'error'` and the error comes from an LLM contract failure (identifiable via error code like `'schema_mismatch'`, `'contract_failed'`, or a new structured marker), emit `internal/validation.failed` with a payload containing:
   - `reason: 'llm_contract_failed'`
   - `schemaName`: the name of the contracted schema (if available from exec data)
   - `error`: the structured error from `ExecResult.error`

3. **Define typed observation payload schemas** for both `llm.responded` and `validation.failed` in `observation.ts`:

```typescript
export const LLMRespondedPayloadSchema = z.object({
    model: z.string().optional(),
    contentSummary: z.string().optional(),
    hasStructuredOutput: z.boolean().optional(),
    schemaName: z.string().optional(),
    tokenCount: z.number().optional(),
});
export type LLMRespondedPayload = z.infer<typeof LLMRespondedPayloadSchema>;

export const ValidationFailedPayloadSchema = z.object({
    reason: z.string(),
    schemaName: z.string().optional(),
    error: ExecErrorPayloadSchema.optional(),
    zodError: z.unknown().optional(),
    originalPayload: z.unknown().optional(),
});
export type ValidationFailedPayload = z.infer<typeof ValidationFailedPayloadSchema>;
```

> [!IMPORTANT]
> **Integration with `ObservationSchema`.** The current `ObservationSchema` uses `payload: z.unknown()` for all observation kinds. These new payload schemas are **not** integrated into `ObservationSchema` as a discriminated union (that would be a separate, larger refactoring of the observation system). Instead:
>
> - **Default transition:** When constructing `internal/llm.responded` or `internal/validation.failed` observations, the transition code **must** build the payload using `LLMRespondedPayloadSchema.parse(...)` or `ValidationFailedPayloadSchema.parse(...)` to ensure the payload shape is correct at the point of emission.
> - **Consumer code** (Learning, tests, 3.7 test harness): Can use the typed schemas to narrow `observation.payload` via `LLMRespondedPayloadSchema.safeParse(observation.payload)` when `observation.kind === 'llm.responded'`.
> - **`ObservationSchema.payload` remains `z.unknown()`** for now. A future task may introduce a discriminated union on `kind` → payload, but that is out of scope here.
>
> This means the typing is **point-of-use**, not **schema-level**. Consumers that don't know about these payload schemas will still see `unknown` and must validate.

**Acceptance criteria:**
- Successful LLM calls in default execution produce `internal/llm.responded` observations in default transition, with payloads validated against `LLMRespondedPayloadSchema`.
- LLM contract failures produce `internal/validation.failed` observations in default transition, with payloads validated against `ValidationFailedPayloadSchema`.
- Custom agent execution/transition can override this behavior (as always).
- Existing `normalizeObservationInbox` `validation.failed` injection for malformed envelopes continues to work unchanged.
- The `LLMRespondedPayload` and `ValidationFailedPayload` types are exported from `packages/core/src/index.ts`.

### 10. Fix default `answer_with_llm` execution to actually call LLM

**Rule enforcement: APLRET contracts §LLM usage model — Pattern 1: answer with LLM**

File: `packages/core/src/loop/loopRunner.ts`

**Problem:** The default `answer_with_llm` execution (line 577–583) calls `ctx.reply(query)` — it echoes the raw query text to the user without calling the LLM. This is misleading and violates the APLRET canonical pattern.

**Fix:** Change default `answer_with_llm` execution to actually call `ctx.llm.call()`, **with explicit handling for unconfigured/stubbed LLMs**.

> [!IMPORTANT]
> **Risk: `ctx.llm` may be a stub.** `TaskEngine.createContext` creates a stub LLM (no-op or echo) when no `LLMConfig` is provided. Changing `answer_with_llm` to call `ctx.llm.call()` would silently invoke the stub, which could return empty/echo responses that are worse than the current explicit echo. The implementation must detect and handle this case.

```typescript
if (a.kind === 'answer_with_llm') {
    // Guard: check if LLM is configured (not a stub)
    const isLLMConfigured = typeof ctx.llm?.getHistoryMode === 'function'
        || (ctx as InternalTaskContext).__llmConfigured === true;

    if (!isLLMConfigured) {
        // Fallback: echo with explicit status indicating no LLM was available
        await ctx.reply(a.query);
        return {
            action: { kind: 'answer_with_llm', echoed: true } as ExecutableAction,
            result: {
                ...base,
                status: 'error' as const,
                error: { code: 'llm_not_configured', message: 'No LLM configured; echoed query as fallback.' },
                data: { text: a.query, query: a.query, echoed: true },
            }
        };
    }

    const responses = await ctx.llm.call(a.query);
    const text = responses[0]?.content ?? 'No LLM response.';
    await ctx.reply(text);
    return {
        action: { kind: 'answer_with_llm', echoed: false } as ExecutableAction,
        result: {
            ...base,
            data: { text, query: a.query },
            toolId: 'language'
        }
    };
}
```

> [!NOTE]
> **The exact stub detection mechanism** (`__llmConfigured` flag vs. checking for a marker method) is an implementation detail. The key requirement is that the default execution **never silently invokes a no-op LLM**. The chosen detection mechanism must be documented in `internalContext.ts`.

**Acceptance criteria:**
- `answer_with_llm` default execution calls `ctx.llm.call()` when LLM is configured.
- If `ctx.llm` is not configured (stub), returns a structured `ExecResult` with `status: 'error'`, `error.code: 'llm_not_configured'`, and echoes the query as fallback.
- Response text is sent via `ctx.reply()` in both cases.
- Default transition emits `internal/llm.responded` observation for successful LLM calls.
- Default transition emits `internal/validation.failed` (or `internal/state.noted` with error detail) for the `llm_not_configured` case.
- Tests cover both paths: configured LLM and stubbed LLM.

## 📋 Migration Guide

**File: `apps/docs/migration/3.6-llm-output-contracts-migration.md`** (to be created as part of this task)

The migration guide must cover:

### Breaking changes

1. **`ILLMCaller` signature change** — `call()` and `stream()` now use typed `LLMCallOptions` instead of `Record<string, any>`. Agent code passing undocumented options may need to use the `.passthrough()` escape hatch or add options to the schema.

2. **`ILLMCaller` is now a `type` (not `interface`)** — agents using `implements ILLMCaller` must switch to satisfies or structural typing.

3. **`LLMConfig.defaultSettings` type changed** — from `Record<string, any>` to `LLMSettings`. Only standard model settings are typed; others flow through `.passthrough()`.

4. **`updateSettings()` parameter changed** — from `Record<string, any>` to `LLMSettings`.

5. **`ExecResult` import location changed** — canonical source is now `types/execOutcome.ts`. Re-export from `oneTurn.ts` remains for backward compatibility.

6. **New `ExecOutcome` type** — `Modules.execution` now returns `Promise<ExecOutcome<...>>`. Structurally compatible — no code changes needed unless you explicitly referenced the inline type.

7. **Default `answer_with_llm` now calls LLM** — agents relying on the old echo behavior must override `execution` (they should have been doing this anyway).

8. **Default transition now emits `internal/llm.responded`** — agents with custom `perception`/`learning` that pattern-match on observation kinds should handle this new kind. Agents with custom `transition` are unaffected.

9. **Default transition emits `internal/validation.failed` for LLM errors** — same consideration as above.

10. **`LLMCallTrace` has new optional fields** — `hasOutputContract`, `outputContractName`, `outputContractStatus`. These are additive (optional) — no breakage expected, but tests asserting exact trace shapes may need updating.

### Migration steps (to be detailed in the file)
