# 3.1 The Planning Model (`M.plans`)

This document defines the normative specification for implementing the explicitly sequenced cognitive layout for multi-step reasoning via `M.plans` across the `CallAgent` framework.

**REMEMBER: We do not support backwards compatibility.**
After these changes are implemented, final migration instructions will be saved to `apps/docs/migration/3.1-planning-model-migration.md`.

---

## Architectural Review & Problem Statement

The APLRET framework introduces an explicitly sequenced cognitive layout for multi-step reasoning capabilities via `M.plans`. Currently, `goalState` exists, but there is no mechanism tying it to a hierarchical, executed plan with a cursor. The framework lacks the single source of truth for planning cognition.

Furthermore, as per **Rule 2: Schemas Are the Single Source of Truth** (`types-rules.md`), all runtime validation and static typing must derive from Zod schemas. Currently, we lack Zod schemas for `Plan`, `PlanStep`, and their associated types.

Finally, we must ensure **Execution** handles the effect of plan generation/repair, and **Learning** strictly acts as the single writer for `M.plans` based on validated observations (`internal/plan.proposed`, `internal/plan.updated`), conforming to **Rule 1: Types Must Reflect Runtime Behavior**.

Every file and location that must change. Nothing may be omitted during implementation.

### 1. Schemas & Types (`packages/core/src/loop/types.ts` & `packages/core/src/types/`)

| # | File | What Must Change |

| 1.1 | `packages/core/src/types/plan.ts` (NEW) | **Create** this file. Define Zod schemas for `PlanId`, `PlanStatus`, `StepStatus`, `StepKind`, `PlanStep`, and `Plan`. Export the inferred types (e.g., `export type Plan = z.infer<typeof PlanSchema>;`). |
| 1.2 | `packages/core/src/types/plan.ts` (NEW) | **Enforce** invariants via Zod `.refine()` (e.g., `cursor` must be between `0` and `steps.length`). |

| 1.4 | `packages/core/src/types/observation.ts` | **Update** `ObservationSchema` to correctly model payloads for `'plan.proposed'`, `'plan.updated'`, and `'plan.step.updated'` using the new Zod schemas from `plan.ts`. Do not use `z.any()` or `z.unknown()` for these specific internal kinds. |

### 2. Module Execution & Transition (`packages/core/src/orchestration/` & `packages/core/src/loop/loopRunner.ts`)

| # | File | What Must Change |
|---|------|-----------------|
| 2.1 | `loopRunner.ts` (Execution module) | **Implement** handlers for `create_plan`, `execute_next_step`, and `repair_plan` intents. These must invoke LLM/tools or state changes and return appropriate results (`{ data: { plan: ... } }`). |
| 2.2 | `loopRunner.ts` (Transition module) | **Implement** conversion of execution results from planning intents into explicit `internal/plan.proposed`, `internal/plan.updated`, and `internal/plan.step.updated` observations. |

### 3. Agent Implementation Layer (Perception & Learning)

| # | What Must Change |
|---|-----------------|
| 3.1 | **Perception**: When receiving `internal/plan.proposed` or `internal/plan.updated`, the perception module MUST validate the payload against `PlanSchema` (from `plan.ts`) to ensure structural integrity before passing it to Learning. |
| 3.2 | **Learning**: Must act as the single writer. When processing `plan.proposed` / `updated` observations, it must initialize `M.plans`, set `activePlanId`, bump `revision`, and safely update `cursor`/`status` immutably. |

## Type Safety Requirements (types-rules.md Compliance)

| Rule | Requirement |
|------|-------------|
| **Rule 1: Types reflect runtime** | The `PlanSchema` must strictly enforce `cursor` bounds and `revision` monotonicity across turns via runtime validation during perception. |
| **Rule 2: Schemas are the source of truth** | All plan types MUST be inferred from Zod schemas defined in `packages/core/src/types/plan.ts`. No duplicate interface definitions. |
| **Rule 5: No `any`** | Plan types must be cleanly exported. The payload for internal plan observations must be strongly typed using `PlanSchema`, completely avoiding `z.any()`. |

## Migration Plan

Following implementation, `apps/docs/migration/3.1-planning-model-migration.md` must be created. It must explicitly formulate instructions for end-users:

1. **New Dependency**: Agents explicitly attempting to track multi-step sequences MUST migrate from ad-hoc `ctx.vars` usage to the highly-structured `M.plans` state.
2. **Type Changes**: Inform developers extending `MentalState` that the `plans` property is now part of the base type, and detail the strict Zod validation it enforces.
3. **Execution Routing**: Explain that "planning" logic inside `policy()` is forbidden. Plan generation implies LLM effects, which must strictly occur in the generic `Execution` module, resolving via inbox `Observations`.
