# 3.3.1 Migrate vars to worldModel

> **Internal implementation spec.** This document is for implementers (framework contributors and maintainers). It describes file-level changes, function deletions, and acceptance criteria.  
> **For framework users migrating their agents**, see the end-user migration guide: **[apps/docs/migration/3.3.1-remove-memory-vars-migration.md](../migration/3.3.1-remove-memory-vars-migration.md)**. That guide explains how to replace `ctx.vars` and mutable `ctx.world` in your code, with examples and FAQs.

**Scope:** This document covers removal of `ctx.vars` / `memory.vars`, enforcement of read-only `ctx.world`, and related public-API type cleanup (no `any`, single TaskContext contract). Snapshot type drift beyond `vars` (e.g. `inbox`, `meta.turn`) is out of scope and should be addressed separately.

## Problem Statement

The codebase uses `M.memory.vars` and `(ctx as any).vars` as a catch-all for state that doesn't fit into the structured mental state. This violates multiple APLRET contracts and type rules:

1. **Single Writer for Cognition (Rule 2)**: `ctx.vars` allows any module—Execution, Transition, orchestration code—to bypass Learning and write directly into `MentalState`. Only Learning may update `MentalState`.
2. **Cognition vs Control Separation (Rule 7)**: Control flags, pending tokens, retry counters, and generic scratchpads live alongside cognitive structures in `memory.vars`.
3. **Schemas Are Source of Truth (types-rules Rule 2)**: `vars` is not backed by any Zod schema. It is an untyped `Record<string, unknown>` bag that doesn't appear in the `MentalState` type definition but exists at runtime via `as any` casts.
4. **No `any` in Public APIs (types-rules Rule 5)**: Accessing `vars` requires `(M as any).memory.vars`, `(ctx as any).vars`, and similar casts throughout the codebase.
5. **Illegal States Must Not Compile (types-rules Rule 4)**: Because `vars` is not in the type, the compiler cannot catch incorrect usage—it is invisible to TypeScript.
6. **ctx.vars contract in 0-aplret_contracts.md**: The normative contract states that if `ctx.vars` exists, it is an Execution-only scratchpad that is non-persisted, non-authoritative, and MUST NOT influence Policy. The actual runtime proxies `ctx.vars` into `M.memory.vars` and persists it across turns—a direct contradiction.
7. **ctx.world mutability**: `ctx.world` currently exposes `update()` and `patch()` methods that allow any module to mutate `worldModel` directly, violating the Single Writer rule. The normative contract defines `ctx.world` as `{ read: () => Readonly<WorldModel> }`.

**REMEMBER: We do not support backwards compatibility.** After each change is implemented, full migration instructions for end users must be created in `apps/docs/migration/`.

### 2. Fix `ctx.world` to be read-only

**Rule enforcement: Rule 2 (Single Writer), Rule 1 (types reflect runtime), 0-aplret_contracts.md §ctx and working memory**

The APLRET contract defines:
```ts
world?: { read: () => Readonly<WorldModel> };
```

The `TaskContext` type in `shared/types/index.ts` already matches this. However, `taskEngine.ts` line ~3019 assigns a mutable version at runtime (`update` / `patch`), and a **shallow** clone+freeze is not sufficient: `WorldModel` is `Record<string, unknown>`, so nested objects would remain mutable and Execution could still mutate cognition indirectly. The runtime must enforce true read-only semantics.

**Required changes:**

| # | File | Change |
|---|------|--------|
| 1 | `packages/core/src/orchestration/taskEngine.ts` (restoreCtx, ~line 3019) | Replace mutable `ctx.world` with a read-only facade. **Do not** use `read: () => Object.freeze({ ...ctx.__mental?.worldModel })` alone—that leaves nested references mutable. Use one of: (a) a deep clone (e.g. `structuredClone` or equivalent) then freeze the result, or (b) a JSON round-trip clone so no shared references escape, or (c) a narrow read API that returns only primitive/safe views. Ensure no path allows Execution to mutate `MentalState.worldModel` through the returned value. |
| 2 | Any other location that creates `ctx.world` | Same read-only pattern; no `update` or `patch` methods. |

Writes to `worldModel` go through `MemoryWriter.world.set()` in Learning only. This path already exists in `loopRunner.ts` line ~239 (`patches.worldReplace`).

**Migration:** Include in `apps/docs/migration/3.3.1-remove-memory-vars-migration.md` — section on `ctx.world` API change.

## Clean API constraints

These constraints MUST hold after implementation:

1. **No backwards compatibility** — old `ctx.vars` usage results in a compile error, not a runtime fallback.
2. **No `any` in public APIs** — every `as any` cast related to vars access must be removed. `MinimalSourceTaskContext` fields must be typed.
3. **Zod-first schemas** — `WorldModel` is already `Record<string, unknown>` which is correct. No new Zod schema needed for `WorldModel` itself, but `MentalState` field access must go through typed paths.
4. **Illegal states must not compile** — `TaskContext` must not have a `vars` property. `MentalState` must not have a `memory.vars` property. Any code that tries to access these must fail at compile time.
5. **APIs guide autocomplete** — `ctx.world.read()` returns `Readonly<WorldModel>`. `MemoryWriter.world.set()` accepts `WorldModel`.
6. **Single Writer enforced** — only `MemoryWriter.world.set()` in Learning can mutate `worldModel`. `ctx.world` is read-only at the type and runtime level.
7. **Typed error classes** — any new error thrown during migration (e.g., if a deprecated path is hit) must use `InvariantError` with a proper code.
