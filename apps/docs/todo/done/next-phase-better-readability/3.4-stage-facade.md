# 3.4 Stage Facade Support

> **Internal implementation spec.** This document is for implementers (framework contributors and maintainers). It describes file-level changes, type redesigns, and acceptance criteria.
> **For framework users migrating their agents**, see the end-user migration guide: **[apps/docs/migration/3.4-stage-facade-migration.md](../migration/3.4-stage-facade-migration.md)** (to be created as part of this task).

**Scope:** This document covers promoting `createStageFacade` from a thin helper into a first-class, runtime-enforced control-plane primitive: Zod-backed configuration schemas, typed control keys, restricted `onEnter` context, **plumbing** for TurnTrace (data collection via `__stageTrace`; full emission is 3.5), atomic stage + autoMarks transitions, and elimination of all `as any` casts. Consolidation of scattered control-var sync utilities is in scope. Test harness helpers (e.g. `expectStage`, `seedControlState`) are **not** in scope; they are owned by 3.7 and will consume the stage data this task exposes.

## Problem Statement

StageFacade exists today as a lightweight helper (`createStageFacade` in `stageHelpers.ts`) that provides `getStage`, `setStage`, and `assertStage`. While it enforces invariants (require/forbid) and applies autoMarks, it has significant gaps relative to the APLRET contracts (`0-aplret_contracts.md`, §Intent and stage models; §Invariants and enforcement), the StageFacade framework guide (`5-how_to_use_stage_facade_in_aplret.md`), and the type system rules (`types-rules.md`).

## 🏗 Requirements

### 1. Define `StageFacadeConfigSchema` as a Zod-backed schema

**Rule enforcement: Rule 2 (Schemas Are Source of Truth), Rule 4 (Illegal States Must Not Compile), Rule 5 (No `any`)**

File: `packages/core/src/types/stageFacade.ts` **(NEW)**

Define a generic Zod schema for the StageFacade configuration that validates at creation time. The schema must enforce that:

- `initial` is provided and is a valid stage
- `invariants` keys are valid stages
- `autoMarks` keys are valid stages
- `onEnter` keys are valid stages
- `stageKey` is optional with a default

```typescript
import { z } from 'zod';

export const StageInvariantRuleSchema = z.object({
    require: z.array(z.string()).optional(),
    forbid: z.array(z.string()).optional(),
}).strict();

export type StageInvariantRule = z.infer<typeof StageInvariantRuleSchema>;

export const StageFacadeConfigSchema = <St extends string>(stages: readonly St[]) => {
    const stageEnum = z.enum(stages as unknown as [string, ...string[]]);
    return z.object({
        stageKey: z.string().min(1).default('stage'),
        initial: stageEnum,
        invariants: z.record(stageEnum, StageInvariantRuleSchema).optional(),
        autoMarks: z.record(stageEnum, z.record(z.string(), z.unknown())).optional(),
        onEnter: z.record(stageEnum, z.function()).optional(),
    }).strict();
};
```

> [!NOTE]
> **Rule 2 / Rule 4:** The schema provides **runtime** validation at creation time (startup). It does not provide compile-time exhaustiveness for stage keys; that is achieved via the generic `<St extends string>` and the `stages` array. Distinguish "illegal states cannot compile" (type-level) from "invalid config is rejected at creation" (runtime).

Additionally, define the **public types** for the StageFacade return value:

```typescript
export type StageEnterContext = {
    progress: (pct: number, message: string) => void;
    complete: (pct: number, message: string) => void;
};

export type StageFacade<St extends string> = {
    get: (ctx: TaskContext) => St;
    set: (ctx: TaskContext, stage: St) => StageTransitionResult<St>;
    is: (ctx: TaskContext, stage: St) => boolean;
    assert: (ctx: TaskContext, stage?: St) => void;
    summary: (ctx: TaskContext) => StageSummary<St>;
};

export type StageTransitionResult<St extends string> = {
    from: St;
    to: St;
    autoMarksApplied: string[];
    invariantChecks: StageInvariantCheckResult[];
};

export type StageInvariantCheckResult = {
    required?: string[];
    forbidden?: string[];
    ok: boolean;
    failedKey?: string;
};

/** Written to InternalTaskContext.__stageTrace by StageFacade.set(); consumed by oneTurn/loopRunner for TurnTrace. */
export type StageTraceEntry = {
    stageBefore: string;
    stageAfter: string;
    stageTransition: { from: string; to: string };
    stageAutoMarksApplied: string[];
    stageInvariantChecks: StageInvariantCheckResult[];
};

/** Normalized, non-leaky shape for trace/harness. Does not expose raw control keys. */
export type StageSummary<St extends string> = {
    current: St;
    hasPendingInput: boolean;
    hasPendingTool: boolean;
    hasPendingChild: boolean;
    markCount: number;
};
```

### 2. Create unified `InternalTaskContext` shared type

**Rule enforcement: Rule 5 (no `any`), Rule 1 (types reflect runtime)**

File: `packages/core/src/loop/internalContext.ts` **(NEW)**

Replace the two duplicate `InternalTaskContext` definitions in `stageHelpers.ts` and `stageInvariants.ts` with a single shared type. This type is internal to the framework (not exported publicly) and represents the extended `TaskContext` that includes loop-runtime properties.

Import `StageTraceEntry` from `../types/stageFacade.js` (defined in requirement 1).

```typescript
// loop/internalContext.ts
import type { StageTraceEntry } from '../types/stageFacade.js';
import type { TaskContext } from '../shared/types/index.js';
import type { EnvironmentState, ControlState, MentalState } from './types.js';

export type InternalTaskContext = TaskContext & {
    controlVars?: Record<string, unknown>;
    __activeLoopEnv?: EnvironmentState;
    env?: { control?: ControlState };
    M?: MentalState;
    currentTurnNodeId?: string;
    telemetry?: { nodeId?: string };
    /** Stage transition trace for TurnTrace. StageFacade writes here on set(); oneTurn/loopRunner read and clear. */
    __stageTrace?: StageTraceEntry;
};
```

> [!IMPORTANT]
> This is NOT a public API type. It is an internal extension interface for framework code that needs typed access to runtime-attached properties. The `controlVars` property is typed as `Record<string, unknown>` — the Map support in the current code is dead code (no callsite creates a Map for controlVars) and should be removed.

### 3. Restrict `onEnter` to `StageEnterContext`

**Rule enforcement: APLRET contracts §Step 4 (Restrict what onEnter may do), 5-how_to_use_stage_facade.md §Keep onEnter safe**

File: `packages/core/src/loop/stageHelpers.ts` **(MODIFY)**

The `onEnter` callback signature must change from receiving full `TaskContext` to receiving `StageEnterContext`:

**Current:**
```typescript
onEnter?: Partial<Record<St, (ctx: TaskContext, stage: St) => void>>;
```

**New:**
```typescript
onEnter?: Partial<Record<St, (ctx: StageEnterContext, stage: St) => void>>;
```

The framework constructs a `StageEnterContext` from the full `TaskContext` at the call site, exposing only `progress()` and `complete()`:

```typescript
const makeStageEnterContext = (ctx: TaskContext): StageEnterContext => ({
    progress: (pct: number, message: string) => ctx.progress(pct, message),
    complete: (pct: number, message: string) => ctx.complete(pct, message),
});
```

This is the **strong restriction** approach (Option B from the guide). It prevents `onEnter` from performing tool calls, LLM calls, child dispatch, user replies, or any other side effects.

### 4. Make stage transitions atomic with `StageTransitionResult`

**Rule enforcement: APLRET contracts §Step 3 (Apply stage transitions atomically)**

File: `packages/core/src/loop/stageHelpers.ts` **(MODIFY)**

**Atomicity model (decided):**

- **Stage + autoMarks** are committed atomically. Use "validate before commit": compute what the control state would look like after applying stage + autoMarks, validate against invariants, then apply all changes in one go. If invariant validation fails, do not write stage or marks.
- **`onEnter` is post-commit and non-transactional.** Once stage and autoMarks are committed, run `onEnter` with restricted `StageEnterContext`. If `onEnter` throws, the runtime does **not** roll back the stage or marks (telemetry emissions such as `progress()`/`complete()` cannot be undone). The error propagates; the control state remains in the new stage. This avoids over-promising: we guarantee that stage + marks are never partially applied, but we do not guarantee rollback of observable side effects from `onEnter`.

Rewrite `setStage` to perform in order:

1. Read current stage (before).
2. Validate invariants for the **new** stage (against the state that would exist after stage + autoMarks are applied).
3. If validation fails, throw and do not modify state.
4. Apply new stage and autoMarks to control vars (atomic commit).
5. Run `onEnter` with restricted `StageEnterContext` (post-commit; if it throws, state is already committed).
6. Return `StageTransitionResult` with transition details.

**New return type for `setStage`:**

```typescript
setStage(ctx: TaskContext, stage: St): StageTransitionResult<St>;
```

### 5. Add `is()` and `summary()` methods

**Rule enforcement: APLRET contracts §Required capabilities**

File: `packages/core/src/loop/stageHelpers.ts` **(MODIFY)**

Add two new methods. `summary()` returns a **normalized, non-leaky** shape so the public API does not expose raw `controlVars` structure (per §Public vs internal surfaces in `0-aplret_contracts.md`):

```typescript
const isStage = (ctx: TaskContext, s: St): boolean => getStage(ctx) === s;

const summary = (ctx: TaskContext): StageSummary<St> => {
    const iCtx = ctx as InternalTaskContext;
    const controlVars = resolveControlVars(iCtx);
    const current = getStage(ctx);
    let markCount = 0;
    if (controlVars) {
        for (const k of Object.keys(controlVars)) {
            if (k !== stageKey) markCount++;
        }
    }
    const pending = iCtx.__activeLoopEnv?.pending ?? {};
    return {
        current,
        hasPendingInput: Object.keys(pending.inputs ?? {}).length > 0,
        hasPendingTool: Object.keys(pending.tools ?? {}).length > 0,
        hasPendingChild: Object.keys(pending.children ?? {}).length > 0,
        markCount,
    };
};
```

The returned facade becomes:

```typescript
return { get: getStage, set: setStage, is: isStage, assert: assertStage, summary };
```

### 8. Add explicit stage tracing mechanism

**Rule enforcement: APLRET contracts §TurnTrace, 5-how_to_use_stage_facade.md §TurnTrace expectations**

> [!NOTE]
> Full TurnTrace emission is owned by **3.5** (turn-trace-provenance). Test harness helpers (`currentStage()`, `expectStage()`, etc.) are owned by **3.7** (test-harness). This task only adds the **plumbing** so stage data can be collected and consumed by 3.5/3.7.

**Explicit mechanism:**

1. **`InternalTaskContext.__stageTrace`** — Optional field. When `StageFacade.set()` runs, the facade writes a single `StageTraceEntry` to `(ctx as InternalTaskContext).__stageTrace` (overwriting any previous value for the turn).
2. **`oneTurn` / loopRunner** — After the turn (or after transition), read `ctx.__stageTrace`. If present, copy it into the turn output (e.g. `stageTrace` on the return value or a trace collector). Then clear `ctx.__stageTrace` so the next turn starts clean.

After a successful transition, set `(ctx as InternalTaskContext).__stageTrace = { stageBefore, stageAfter, stageTransition, stageAutoMarksApplied, stageInvariantChecks }` using the same data as `StageTransitionResult`.

File: `packages/core/src/loop/oneTurn.ts` **(MODIFY)**

Before returning, if `(ctx as InternalTaskContext).__stageTrace` is set, include it in the return value (e.g. `stageTrace?: StageTraceEntry`) and clear `ctx.__stageTrace`. The loop runner (or 3.5) will then include this in the emitted TurnTrace.

### 12. Validate stage config at creation time

**Rule enforcement: Rule 2 (Schemas Are Source of Truth)**

File: `packages/core/src/loop/stageHelpers.ts` **(MODIFY)**

**Single definitive API (no backwards compatibility):**

Use one config object that includes `stages` for runtime validation. This is easier to extend than a positional two-argument form.

```typescript
export type CreateStageFacadeOptions<St extends string> = {
    stages: readonly St[];
    stageKey?: string;
    initial: St;
    invariants?: Partial<Record<St, StageInvariantRule>>;
    autoMarks?: Partial<Record<St, Record<string, unknown>>>;
    onEnter?: Partial<Record<St, (ctx: StageEnterContext, stage: St) => void>>;
};

export function createStageFacade<St extends string>(
    options: CreateStageFacadeOptions<St>
): StageFacade<St>;
```

At creation time:
1. Validate `initial` is in `options.stages`
2. Validate all `invariants` keys are in `options.stages`
3. Validate all `autoMarks` keys are in `options.stages`
4. Validate all `onEnter` keys are in `options.stages`
5. Validate that any `awaiting_*` stage has a `require: [...]` invariant (per APLRET contract §Stage rules)

> [!IMPORTANT]
> **No backwards compatibility.** The old `createStageFacade(opts)` with optional `stages` (or without `stages`) is removed. Callers must pass `{ stages, initial, ... }`.

### 13. Clean API Constraints

These constraints MUST hold after implementation:

1. **No backwards compatibility** — `createStageFacade` now accepts a single options object that **must** include `stages`. Old form without `stages` is removed. `onEnter` callbacks receiving full `TaskContext` will fail at compile time.
2. **No `any` in public APIs** (Rule 5) — every `as any` cast in `stageHelpers.ts`, `stageInvariants.ts`, `ControlVars.ts`, `TaskStateUtils.ts`, and `controlHelpers.ts` stage-related code is eliminated.
3. **Zod-first schemas** (Rule 2) — `StageInvariantRuleSchema` and stage config validation are Zod schemas with inferred TypeScript types.
4. **Illegal states cannot compile** (Rule 4) — `onEnter` receives `StageEnterContext` (not `TaskContext`). `StageInvariants` type requires only valid stage keys. `createStageFacade` validates config at creation time.
5. **Typed error classes** (Rule 11) — Stage invariant failures use `InvariantError` with `detail.type === 'stage_invariant'` (already implemented in 3.3).
6. **Public vs Internal Separation** (Rule 10) — `InternalTaskContext` is not exported. `StageEnterContext`, `StageFacade`, `StageTransitionResult` are exported.
7. **APIs guide autocomplete** (Rule 6) — `StageFacade<St>` methods provide autocomplete on stage names. `defineControlKeys()` provides typed key constants.

- Reads from `__activeLoopEnv.pending.controlVars` fallback

**`set()` method:**
- Sets stage and applies autoMarks atomically
- Returns `StageTransitionResult` with correct `from`, `to`, `autoMarksApplied`
- Throws `InvariantError` with `detail.type === 'stage_invariant'` when required key is missing
- Throws `InvariantError` with `detail.type === 'stage_invariant'` when forbidden key is present
- Does NOT apply stage or autoMarks if invariant validation fails (atomicity)
- Calls `onEnter` with `StageEnterContext` (not full `TaskContext`)
- `onEnter` context only has `progress()` and `complete()` methods
- If `onEnter` throws, the error propagates; stage and marks remain committed (post-commit, no rollback)

**`is()` method:**
- Returns `true` when current stage matches
- Returns `false` when current stage does not match

**`assert()` method:**
- Passes silently when invariants are satisfied
- Throws `InvariantError` when required key is missing
- Throws `InvariantError` when forbidden key is present
- Validates current stage invariants when called without explicit stage arg

**`summary()` method:**
- Returns normalized shape: `current`, `hasPendingInput`, `hasPendingTool`, `hasPendingChild`, `markCount` (no raw control keys)
- When no control state exists, booleans are false and markCount is 0

**Stage transition atomicity:**
- After a failed **invariant** check, `get()` still returns the previous stage; no stage or marks are written
- After a successful transition, stage and marks are committed; if `onEnter` then throws, state is not rolled back

## 📜 Mandatory Migration Guide

**Action:** Create `apps/docs/migration/3.4-stage-facade-migration.md`

The migration guide must include:

1. **Overview**: `createStageFacade` has been promoted to a first-class control-plane primitive. The API has changed: single options object with required `stages`, restricted `onEnter` context, new return type from `set()`, and new methods (`is`, `summary` with normalized shape).

2. **`createStageFacade` signature change**:

    ```typescript
    // Before (options without stages)
    const Stage = createStageFacade<AgentStage>({
        initial: 'idle',
        invariants: { ... },
        autoMarks: { ... },
        onEnter: { ... }
    });

    // After (single options object with required stages)
    const stages = ['idle', 'awaiting_fetch', 'analyzing', 'completed'] as const;
    type AgentStage = (typeof stages)[number];

    const Stage = createStageFacade<AgentStage>({
        stages,
        initial: 'idle',
        invariants: { ... },
        autoMarks: { ... },
        onEnter: {
            idle: (ctx) => ctx.progress(5, 'idle'),           // ctx is StageEnterContext
            completed: (ctx) => ctx.complete(100, 'completed')
        }
    });
    ```

3. **`onEnter` callback migration** (breaking change):

    ```typescript
    // Before: onEnter receives full TaskContext
    onEnter: {
        idle: (ctx) => {
            ctx.progress(5, 'idle');
            ctx.reply('Starting...');  // THIS WAS ALLOWED BEFORE
        }
    }

    // After: onEnter receives StageEnterContext (only progress + complete)
    onEnter: {
        idle: (ctx) => {
            ctx.progress(5, 'idle');
            // ctx.reply('Starting...');  // COMPILE ERROR — reply is not on StageEnterContext
        }
    }
    ```

    If your `onEnter` hook performs side effects (replies, tool calls, etc.), move those effects into Execution or Transition.

4. **Method renaming and additions**:

    ```typescript
    // Before
    Stage.getStage(ctx);
    Stage.setStage(ctx, 'analyzing');
    Stage.assertStage(ctx, 'idle');

    // After
    Stage.get(ctx);
    const result = Stage.set(ctx, 'analyzing');  // returns StageTransitionResult
    Stage.assert(ctx, 'idle');

    // New methods
    Stage.is(ctx, 'analyzing');   // boolean
    Stage.summary(ctx);           // { current, hasPendingInput, hasPendingTool, hasPendingChild, markCount }
    ```

5. **`setStage` return value**: `setStage` (now `set`) returns a `StageTransitionResult` instead of `void`. This contains `{ from, to, autoMarksApplied, invariantChecks }`. If you ignored the return value before, no change needed. If you need transition details for logging/tracing, use the returned value.

6. **Type imports migration**:

    ```typescript
    // Before
    import { createStageFacade } from '@a2arium/callagent-core';
    import type { StageInvariants } from '@a2arium/callagent-core';

    // After
    import { createStageFacade, defineControlKeys } from '@a2arium/callagent-core';
    import type { StageFacade, StageEnterContext, StageInvariantRule, StageInvariantMap } from '@a2arium/callagent-core';
    ```

7. **Control key pattern** (recommended, not required):

    ```typescript
    import { defineControlKeys } from '@a2arium/callagent-core';

    export const CK = defineControlKeys({
        fetchToken: 'fetch.token',
        completedCalled: 'completed.called',
        awaitingFetchCalled: 'awaiting_fetch.called'
    });

    // Use in invariants
    const Stage = createStageFacade({
        stages,
        initial: 'idle',
        invariants: {
            awaiting_fetch: { require: [CK.fetchToken] },
            completed: { forbid: [CK.fetchToken] }
        },
        autoMarks: {
            completed: { [CK.completedCalled]: true }
        }
    });
    ```

8. **New exports**: `StageFacade`, `StageEnterContext`, `StageTransitionResult`, `StageInvariantCheckResult`, `StageTraceEntry`, `StageSummary`, `StageInvariantRule`, `StageInvariantMap`, `ControlKeyMap`, `CreateStageFacadeOptions`, `defineControlKeys`, `readControlVar`, `writeControlVar`, `deleteControlVar`, `resolveControlVars` are now available from `@a2arium/callagent-core`.

9. **Removed exports**: `StageInvariants` type (replaced by `StageInvariantMap`).
