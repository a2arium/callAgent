# 4.3 Framework readability helpers & reference examples

> **Internal implementation spec** for framework contributors and maintainers. Complements [4.1](./4.1-flow-md-standard.md) and [4.2](./4.2-agent-repository-layout-and-patterns.md).

---

## Problem

Two issues remain after 4.1/4.2 groundwork:

1. Repetitive literals for observations, execution outcomes, and transition outcomes still encourage copy-paste and inconsistent naming.
2. Reference examples are not yet fully curated as a single style baseline across docs and repo entrypoints.

This stream introduces optional readability helpers **only where they remove real duplication** and hardens reference examples as canonical training data for humans and AI assistants.

---

## Current baseline (audit)

### What already exists

- Strong base APIs and schemas are exported from core (`ExecOutcome`, observation schemas, harness utilities, etc.).
- Scaffold + examples exist (`hello-agent` minimal, `flow-reference-agent` non-trivial subset).
- Docs corpus already includes behavioral guidance in:
  - [How-to: Test](../11-how_to_test_aplret_agents.md)
  - [How-to: Debug with TurnTrace](../12-how_to_debug_with_turn_trace.md)
  - [How-to: Agent repository layout](../14-agent_repository_layout_for_aplret.md)

### Gaps this task must close

- No dedicated readability helper APIs (observation/exec/turn builder style) are shipped yet.
- No explicit repo-level pointer that one non-trivial example is the style baseline.
- Test/how-to snippets are not yet explicitly anchored to the chosen reference baseline where useful.

---

## Scope

### In scope

1. **Optional readability helpers** (ship only if duplication reduction is material):
   - observation builders tied to closed unions
   - exec/turn outcome builders tied to typed outcomes
   - tiny utilities that reduce literal noise without weakening types
2. **Reference-example curation**:
   - designate one primary non-trivial reference agent
   - ensure style baseline is linked from repo docs
3. **Documentation alignment**:
   - connect helper docs to doc 12/doc 14 narratives
   - align doc 11 snippets where clearer with baseline layout
4. **Test and verification requirements** for helper/example changes.

### Out of scope

- Large abstraction layers over `oneTurn` / `TaskEngine`.
- Helper APIs that hide effect boundaries, Policy purity, or transition ownership.
- Compatibility shims for deprecated style patterns.

---

## No backwards compatibility

Per [4.0](./4.0-readability-phase-overview.md), this stream does **not** preserve deprecated patterns.

- If helper APIs replace old ad-hoc literal patterns in examples/tests, old patterns are not preserved for compatibility.
- Public type/API shape changes are treated as breaking and require migration docs.
- No legacy aliases that reintroduce weak typing or ambiguous patterns.

---

## Type and API requirements

All helper work must follow [Type system rules](./types-rules.md):

- no exported `any`
- schema-first where runtime validation is involved (`zod` + `z.infer`)
- illegal states should not compile (closed unions, discriminated shapes)
- public/internal separation is explicit
- type-level tests (`tsd`) for new public exports

If new helper exports are added, update:

- `packages/core/src/index.ts`
- [APLRET contracts public API inventory](../0-aplret_contracts.md)
- relevant type tests under `packages/core/tests/*.test-d.ts`

### Public API lifecycle (required)

New helpers MUST follow a staged lifecycle to avoid accidental permanent surface area:

1. **Stage 0 (internal/provisional):** implement in an internal module and validate ergonomics in core tests/examples.
2. **Stage 1 (promote):** export from public barrel only after criteria in this doc are met.
3. **Stage 2 (stabilize):** add contracts inventory row + migration note + type/runtime tests.

Do not export helpers directly to stable public surface without Stage 0 validation.

---

## Helper design constraints (if shipped)

### Principles

- Helpers must be **small, explicit, and optional**.
- Prefer constrained builders over generic magic.
- Builders should encode vocabulary from agent-local closed unions and framework enums.

### Candidate helper families

1. **Observation builders**
   - build source/kind-valid envelopes
   - keep payload typing explicit
2. **Exec outcome builders**
   - reduce repetitive `{ action, result }` literals
   - preserve typed status/data/error branches
3. **Transition outcome builders**
   - typed constructors for `continue`, `await_*`, `complete`, `fail`
   - enforce required tokens where needed

### Objective ship criteria (must be measurable)

Ship a helper family only if all conditions hold:

1. Removes repeated literal construction in **at least 3 distinct call sites** across core tests/examples/scaffold templates.
2. Preserves or improves compile-time safety versus direct literals (no type widening).
3. Adds no new `any` and does not weaken existing discriminated unions.
4. Includes both runtime tests (where behavior exists) and type tests (`tsd` / compile assertions).
5. Improves readability in examples (fewer structural lines while keeping intent explicit).

If these are not met, helper stays unshipped and the doc records deferral rationale.

### Rejection criteria

Do not ship helpers if they:

- obscure module boundaries
- reduce readability of explicit intent/transition semantics
- duplicate existing clear APIs without measurable reduction in noise
- permit states that should be unrepresentable by type system (Rule 4 / illegal states must not compile)

---

## Reference example requirements

A single non-trivial example must be maintained as style baseline and documented as such.

Baseline requirements:

- closed unions and domain-named intents
- selectors/reducers/normalizers split
- `flow.md` kept in sync with behavior
- tests cover golden/resume/failure/invariant paths
- if helper APIs ship, example demonstrates usage in at least one realistic path

Discoverability requirements:

- root repo docs should point to:
  - minimal baseline example
  - non-trivial baseline example
- docs should clearly describe when to copy minimal vs non-trivial shape

---

## Implementation plan

### Phase 1: duplication audit and helper decision

- Identify repeated literal patterns across:
  - core tests
  - reference examples
  - scaffold output templates
- Decide per helper family: ship now vs defer, using objective ship criteria in this doc.

### Phase 2: helper implementation (conditional)

If shipped:

- implement focused helper modules in core
- run Stage 0 internal validation first
- export from public barrel
- add unit + type tests
- document usage and boundaries

If deferred:

- document why (duplication not high enough or API would over-abstract)
- close this phase with examples/docs-only improvements.

### Phase 3: reference example hardening

- Choose and document one primary non-trivial baseline.
- Align example README and repo-level docs pointers.
- Ensure example and tests match doc 14 style.

### Phase 4: docs + migration + verification

- update contracts/how-to footnotes where needed
- ship migration notes for any user-facing change
- run required commands

---

## Tests impacted and required updates

Any change in this stream must review impacted tests, update or remove outdated assertions, and add tests for new functionality.

### Potentially impacted suites

- `packages/core/tests/*` where literals or helper wrappers are introduced
- `packages/core/tests/*.test-d.ts` when exports/types change
- `apps/examples/hello-agent/tests/*`
- `apps/examples/flow-reference-agent/tests/*`
- scaffold tests if generated templates adopt helpers

### Required for new helper APIs

1. Unit tests for each helper family.
2. Type tests proving compile-time constraints.
3. Integration coverage in at least one reference example or scaffold smoke.
4. Negative tests for illegal states where relevant.

---

## Migration documentation plan (mandatory)

For each merged user-visible change in this stream:

1. Create/update migration docs in `apps/docs/migration/` in the same PR.
2. Include:
   - what changed
   - affected users
   - adoption/rewrite steps
   - before/after code snippets
   - verification commands
3. Cross-link from:
   - this todo doc
   - [4.0 overview](./4.0-readability-phase-overview.md)
   - affected how-to docs

Suggested migration file path when helper APIs ship:

- `apps/docs/migration/4.3-framework-readability-helpers-migration.md`

## Acceptance criteria

1. If helper APIs ship, they are exported from the documented package, strongly typed, schema-aligned where needed, and covered by runtime + type tests.
2. Helper exports followed staged lifecycle (internal validation before public promotion), with documented rationale.
3. Public API inventory in [APLRET contracts](../0-aplret_contracts.md) reflects new helper exports (if any).
4. One primary non-trivial reference agent is clearly documented as style baseline in repo docs.
5. [How-to: Test](../11-how_to_test_aplret_agents.md) snippets are aligned with baseline layout where it improves clarity.
6. Any new helper docs link to [doc 12](../12-how_to_debug_with_turn_trace.md) and [doc 14](../14-agent_repository_layout_for_aplret.md).
7. Migration docs exist for each user-visible change.
8. Required verification commands pass.
