# 3.3 Invariant Error Shapes & Enforcement

## Problem Statement

The codebase currently throws **plain `Error` objects with string-only messages** at every invariant enforcement point. There are no structured error codes, no typed detail payloads, and no ability for callers to programmatically inspect what went wrong. This violates:

- **APLRET contracts** (`0-aplret_contracts.md`, §Invariant error shape, lines 1119–1139): invariant errors MUST be structured with `code`, `message`, `stage`, and contextual detail.
- **Error model** (`0-aplret_contracts.md`, §Error model, lines 1277–1314): perception errors, invariant errors, and execution errors MUST all be structured and inspectable.
- **types-rules.md** Rule 2 (schemas as source of truth), Rule 4 (illegal states must not compile), Rule 5 (no `any`), Rule 6 (APIs guide autocomplete), Rule 11 (errors must be typed), Rule 13 (types must be tested).

**Specific problems:**

1. **No `InvariantError` type or class exists.** The APLRET contracts define a normative `InvariantError` shape, but the codebase has no implementation of it.
2. **`FrameworkError.details` is `Record<string, unknown>`** — no type safety, no programmatic inspection. Callers cannot switch on error code or kind.
3. **`BaseError.details` is `any`** — violates Rule 5 (no `any` in public APIs).
4. **Stage invariant failures** (`stageInvariants.ts`, `stageHelpers.ts`) throw plain `Error` with a string message. They contain useful information (stage name, required/forbidden keys) but it's only accessible via string parsing.
5. **Module failure wrappers** in `oneTurn.ts` re-throw as plain `Error` with `"${module} module failed: ${msg}"`. They lose the original error type, stack, and structured details. Note: these are **runtime execution failures**, not invariant violations — they should use a separate typed error class (see §8).
6. **Goal API errors** in `goals.ts` throw bare code strings like `'GOAL_NOT_FOUND'` — no typed error class, no detail payload.
7. **Token validation errors** in `taskEngine.ts` throw code strings like `'INPUT_TOKEN_NOT_FOUND'`, `'INPUT_TOKEN_EXPIRED'` — no structured context.
8. **No observation validation errors.** The runtime silently drops invalid observations in `normalizeObservationInbox()` (with optional debug log). The APLRET contracts require either failing the turn with an invariant error OR injecting a `validation.failed` observation.
9. **`ctx.throw` is untyped.** `TaskContext.throw` accepts `(code: string, message: string, details?: unknown)` — `string` code has no autocomplete, `unknown` details has no structure.

### 1. Define `InvariantErrorDetailSchema` as a Zod-backed discriminated union

**CRITICAL RULE ENFORCEMENT (Rule 2: Schemas Are the Single Source of Truth, Rule 4: Illegal States Must Not Compile, Rule 11: Errors Must Be Typed):**

File: `packages/core/src/types/invariantError.ts` **(NEW)**

> [!IMPORTANT]
> This is a Zod schema first, with the TypeScript type inferred from it. This follows the same pattern
> established by `ManifestErrorDetail` in `packages/types/src/agent/manifestErrors.ts` and the
> `ObservationSchema` in `packages/core/src/types/observation.ts`.

```typescript
import { z } from 'zod';

// ── Error code enum (Rule 4 + Rule 6: closed union, autocomplete) ──
export const InvariantErrorCodeSchema = z.enum([
  // Stage invariants
  'STAGE_REQUIRES_KEY',
  'STAGE_FORBIDS_KEY',

  // Token validation
  'INPUT_TOKEN_NOT_FOUND',
  'INPUT_TOKEN_EXPIRED',
  'TOOL_TOKEN_NOT_FOUND',
  'CHILD_TOKEN_NOT_FOUND',
  'TOKEN_MISMATCH',

  // Observation validation
  'OBSERVATION_VALIDATION_FAILED',

  // Transition invariants
  'CONTINUE_WITHOUT_OBSERVATIONS',
  'AWAIT_MISSING_TOKEN',
  'TERMINAL_WITH_PENDING',

  // Goal invariants
  'GOAL_NOT_FOUND',
  'GOAL_HAS_ACTIVE_CHILDREN',
  'GOAL_PRIORITY_OUT_OF_RANGE',

  // Budget enforcement
  'BUDGET_TURNS_EXCEEDED',
  'BUDGET_LATENCY_EXCEEDED',
  'BUDGET_COST_EXCEEDED',

  // Session / configuration
  'SESSION_NOT_FOUND',
  'LIMIT_MAX_PROMPTS_EXCEEDED'
]);

export type InvariantErrorCode = z.infer<typeof InvariantErrorCodeSchema>;

// ── Inbox summary sub-schema ──
export const InboxSummarySchema = z.object({
  count: z.number().int().nonneg(),
  entries: z.array(z.object({
    source: z.string(),
    kind: z.string()
  })).optional()
});

export type InboxSummary = z.infer<typeof InboxSummarySchema>;

// ── Discriminated union of invariant error detail types ──
// Each discriminant carries ONLY its own context — no redundant top-level fields (Rule 4).
export const InvariantErrorDetailSchema = z.discriminatedUnion('type', [
  // Stage invariant violations (require/forbid)
  z.object({
    type: z.literal('stage_invariant'),
    stage: z.string(),
    required: z.array(z.string()).optional(),
    forbidden: z.array(z.string()).optional(),
    pendingSnapshot: z.unknown().optional()
  }),

  // Token validation failures (missing, expired, mismatch)
  z.object({
    type: z.literal('token_validation'),
    category: z.enum(['input', 'tool', 'child']),
    token: z.string().optional(),
    expectedToken: z.string().optional(),
    reason: z.enum(['missing', 'expired', 'mismatch', 'unknown_token']),
    pendingSnapshot: z.unknown().optional()
  }),

  // Observation validation failures (invalid source/kind, schema failure)
  z.object({
    type: z.literal('observation_validation'),
    source: z.string().optional(),
    kind: z.string().optional(),
    reason: z.string(),
    observationIndex: z.number().int().optional(),
    inboxSummary: InboxSummarySchema.optional()
  }),

  // Transition invariant violations (continue without observations, await without token, terminal with pending)
  z.object({
    type: z.literal('transition_invariant'),
    transitionKind: z.string(),
    reason: z.string(),
    pendingSnapshot: z.unknown().optional()
  }),

  // Goal API invariant violations
  z.object({
    type: z.literal('goal_invariant'),
    goalId: z.string().optional(),
    reason: z.enum([
      'goal_not_found', 'goal_has_active_children', 'priority_out_of_range'
    ])
  }),

  // Budget enforcement failures
  z.object({
    type: z.literal('budget_exceeded'),
    budget: z.enum(['turns', 'latency', 'cost']),
    limit: z.number(),
    actual: z.number()
  })
]);

export type InvariantErrorDetail = z.infer<typeof InvariantErrorDetailSchema>;

// ── Full InvariantError payload shape ──
// No redundant fields — all context lives in the `detail` discriminant (Rule 4).
export const InvariantErrorPayloadSchema = z.object({
  code: InvariantErrorCodeSchema,
  message: z.string(),
  stage: z.string().optional(),
  detail: InvariantErrorDetailSchema,
  correlationId: z.string().optional(),
  turnId: z.string().optional()
});

export type InvariantErrorPayload = z.infer<typeof InvariantErrorPayloadSchema>;
```

> [!NOTE]
> **Design decisions (from architect review):**
> - **No `generic` catch-all discriminant.** If a new invariant type is needed, a proper discriminant MUST be added. Escape hatches undermine the structured error contract.
> - **`code` is a closed enum**, not `z.string()`. This prevents typos, enables autocomplete (Rule 6), and makes illegal codes fail at compile time (Rule 4).
> - **No redundant top-level fields.** `required`, `forbidden`, `pendingSnapshot`, `inboxSummary` live only inside their respective detail discriminants. A `budget_exceeded` error with `required: ['foo']` at the top level is an impossible state that must not compile (Rule 4).
> - **`budget_exceeded` remains as an invariant.** While it's an operational limit, it's still a framework-enforced precondition check that behaves identically to other invariants: structured error, typed payload, programmatic inspection.

### 2. Create `InvariantError` error class

File: `packages/core/src/utils/errors.ts` **(MODIFY)**

> [!IMPORTANT]
> **Naming convention (from architect review):** The payload type is named `InvariantErrorPayload`
> (the data shape). The error class is named `InvariantError` (the throwable). This avoids the
> collision between type and class names and keeps the most natural name for the class users
> will actually `catch` and `instanceof` check.

```typescript
import type { InvariantErrorPayload } from '../types/invariantError.js';

export class InvariantError extends FrameworkError {
  public readonly invariant: InvariantErrorPayload;

  constructor(invariant: InvariantErrorPayload) {
    super(invariant.message, { code: invariant.code, ...invariant.detail });
    this.invariant = invariant;
    Object.setPrototypeOf(this, InvariantError.prototype);
  }
}
```

### 3. Create `ModuleExecutionError` for module failures (separate from invariants)

File: `packages/core/src/utils/errors.ts` **(MODIFY)**

> [!IMPORTANT]
> **Design decision (from architect review):** Module failures in `oneTurn.ts` are **runtime execution
> errors**, not invariant violations. An invariant is a precondition/postcondition the framework
> enforces (e.g., "stage X requires token Y"). A module throwing because the LLM returned garbage
> is a runtime error. These get a separate typed error class to preserve semantic clarity.

```typescript
export const ModuleNameSchema = z.enum([
  'attention', 'perception', 'learning',
  'policy', 'shield', 'execution', 'transition'
]);

export type ModuleName = z.infer<typeof ModuleNameSchema>;

export class ModuleExecutionError extends FrameworkError {
  public readonly module: ModuleName;
  public readonly originalMessage: string;
  public readonly originalCode?: string;

  constructor(module: ModuleName, originalMessage: string, originalCode?: string) {
    super(`${module} module failed: ${originalMessage}`, { module, originalMessage, originalCode });
    this.module = module;
    this.originalMessage = originalMessage;
    this.originalCode = originalCode;
    Object.setPrototypeOf(this, ModuleExecutionError.prototype);
  }
}
```

### 5. Create `throwInvariantError()` factory function

File: `packages/core/src/utils/invariantError.ts` **(NEW)**

A single factory function that constructs and throws an `InvariantError`. All enforcement sites call this instead of `throw new Error(string)`.

```typescript
import type { InvariantErrorCode, InvariantErrorDetail } from '../types/invariantError.js';
import { InvariantError } from './errors.js';

export function throwInvariantError(
  code: InvariantErrorCode,
  message: string,
  detail: InvariantErrorDetail,
  context?: {
    stage?: string;
    correlationId?: string;
    turnId?: string;
  }
): never {
  throw new InvariantError({
    code,
    message,
    detail,
    ...context
  });
}
```

> [!TIP]
> This factory centralizes error construction and ensures all invariant errors are structured.
> It also makes it easy to add global hooks (telemetry, logging) in a single place.

### 15. Clean API Constraints

- **NO backwards compatibility**: Plain `new Error(string)` throws at enforcement sites are removed entirely.
- **NO `any` usage** (Rule 5): All `as any` casts in `stageInvariants.ts`, `stageHelpers.ts`, and `BaseError.ts` are eliminated. Internal extension interfaces are used where `TaskContext` needs extended access.
- **Zod-first schemas** (Rule 2): `InvariantErrorDetailSchema`, `InvariantErrorPayloadSchema`, and `InvariantErrorCodeSchema` are Zod schemas with inferred TypeScript types.
- **Illegal states cannot compile** (Rule 4): Error codes are a closed enum, detail discriminants carry only their own context fields, and the top-level payload has no redundant optional fields.
- **Typed error classes** (Rule 11): `InvariantError` carries a full `InvariantErrorPayload`, `ModuleExecutionError` carries typed module name. Neither uses `Record<string, unknown>` as primary payload.
- **Public vs Internal Separation** (Rule 10): The schemas and types are in `packages/core/src/types/` and exported publicly.
- **APIs guide autocomplete** (Rule 6): `InvariantErrorCode` enum provides IDE suggestions for error codes. `throwInvariantError()` and `ctx.throw()` accept only valid codes.

> [!NOTE]
> **Roadmap for remaining untyped `FrameworkError` subclasses:**
> After this task + 3.2, `ManifestError` and `InvariantError` have typed detail payloads.
> `TaskExecutionError`, `AgentError`, and `ConfigurationError` still use `Record<string, unknown>`.
> These should receive typed detail unions in future tasks to achieve full Rule 11 compliance
> across the error hierarchy.

- `await_tool` without token → throws `InvariantError` with `detail.type === 'transition_invariant'`
- `await_child` without token → throws `InvariantError` with `detail.type === 'transition_invariant'`
- `complete` with pending await tokens → throws `InvariantError` with `detail.type === 'transition_invariant'`

## 📜 Mandatory Migration Guide

**Action:** Create `apps/docs/migration/3.3-invariant-error-shapes-migration.md`

The migration guide must include:

1. **Overview**: All invariant enforcement points now throw `InvariantError` instead of plain `Error`. Module failures throw `ModuleExecutionError`. Error payloads are structured and typed.

2. **Error catching migration**:

    ```typescript
    // Before
    try {
      facade.setStage(ctx, 'awaiting_tool');
    } catch (e) {
      if (e instanceof Error && e.message.includes('requires')) {
        // string parsing...
      }
    }

    // After
    import { InvariantError } from '@a2arium/callagent-core';

    try {
      facade.setStage(ctx, 'awaiting_tool');
    } catch (e) {
      if (e instanceof InvariantError) {
        const { code, detail } = e.invariant;
        if (detail.type === 'stage_invariant') {
          console.log(`Stage ${detail.stage} requires: ${detail.required?.join(', ')}`);
        }
      }
    }
    ```

3. **Goal API error handling migration**:

    ```typescript
    // Before
    try { await updateGoal(ctx, id, patch); }
    catch (e) { if ((e as Error).message === 'GOAL_NOT_FOUND') { ... } }

    // After
    try { await updateGoal(ctx, id, patch); }
    catch (e) {
      if (e instanceof InvariantError && e.invariant.detail.type === 'goal_invariant') {
        switch (e.invariant.detail.reason) {
          case 'goal_not_found': ...
          case 'goal_has_active_children': ...
        }
      }
    }
    ```

4. **Module execution error migration**:

    ```typescript
    // Before
    catch (e) { if (e.message.startsWith('Attention module failed')) { ... } }

    // After
    import { ModuleExecutionError } from '@a2arium/callagent-core';
    catch (e) {
      if (e instanceof ModuleExecutionError) {
        console.log(`Module '${e.module}' failed: ${e.originalMessage}`);
      }
    }
    ```

5. **`ctx.throw` migration**:

    ```typescript
    // Before
    ctx.throw('SOME_CODE', 'message', { arbitrary: 'data' });

    // After
    ctx.throw('GOAL_NOT_FOUND', 'Goal not found', {
      type: 'goal_invariant', goalId: 'g1', reason: 'goal_not_found'
    });
    ```

6. **Observation validation behavioral change**: Invalid observations are no longer silently dropped. Agents will receive `source: 'internal', kind: 'validation.failed'` observations in their inbox. Agent Perception and Learning modules should handle this kind if not already doing so.

7. **New exports**: `InvariantError`, `ModuleExecutionError`, `throwInvariantError`, `InvariantErrorPayload`, `InvariantErrorDetail`, `InvariantErrorCode`, `InboxSummary` are now available from `@a2arium/callagent-core`.

8. **`BaseError.details` type change**: `any` → `Record<string, unknown>`. Any code passing non-object details to `BaseError` constructor will fail at compile time.
