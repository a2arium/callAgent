# 2.4 `Intent` vs `ProposedAction` Naming & Shape

## Problem Statement

The typing for agent intentions across the codebase is disjointed from the APLRET contract payload envelopes as defined in `0-aplret_contracts.md`. Currently, `oneTurn.ts` (in both `packages/core` and externally copied to `packages/memory-engine`) uses an ambiguously defined `ProposedAction` type bridging internal actions (`subagent`, `language`) with standard interactions (`tool`).

This violates the canonical definitions of `Intent` introduced in the latest APLRET architectural rewrite, creating inconsistencies in the Policy, Shield, and Execution modules. Furthermore, it completely lacks runtime validation mapping, violating the single source of truth rule from `types-rules.md`.

---

## 🏗 Requirements

### 1. Deprecate `ProposedAction` and Introduce `Intent` via Zod
Replace all instances of `ProposedAction` with a strictly discriminated `Intent` type. 

**CRITICAL RULE ENFORCEMENT (Rule 2: Schemas Are the Single Source of Truth):**
We must NOT define `type Intent` manually. The `Intent` structure spans the LLM boundary (when dynamic LLM planners generate Intents), so it must be defined as a Zod schema first to guarantee runtime safety and to be compatible with `calllm`'s `jsonSchema` parsing parameters.

**Required Schema (to be placed in a dedicated public types file per Rule 10):**
```typescript
import { z } from 'zod';

export const IntentSchema = z.discriminatedUnion('kind', [
  // User interaction
  z.object({ kind: z.literal('prompt_user'), prompt: z.string() }),
  z.object({ kind: z.literal('answer_with_llm'), query: z.string(), contextKey: z.string().optional() }),
  
  // Tools / children
  z.object({ 
    kind: z.literal('call_tool'), 
    toolName: z.string(), 
    args: z.record(z.unknown()), 
    mode: z.enum(['sync', 'async']) 
  }),
  z.object({ kind: z.literal('delegate_to_child'), agentId: z.string(), input: z.unknown() }),
  
  // Planning
  z.object({ kind: z.literal('create_plan'), goalId: z.string() }),
  z.object({ kind: z.literal('execute_next_step'), planId: z.string() }),
  z.object({ kind: z.literal('repair_plan'), planId: z.string(), reason: z.string() }),
  
  // Terminal / idle
  z.object({ kind: z.literal('complete'), result: z.unknown() }),
  z.object({ kind: z.literal('wait') })
]);

export type Intent = z.infer<typeof IntentSchema>;
```

### 2. Affected Modules Refactoring
Update the type signatures, variable namings, and logic handling in:
- **`packages/core/src/loop/oneTurn.ts`**:
  - Remove `ProposedAction` completely. Import `Intent` from the dedicated schema file.
  - Update `Modules.policy`, `Modules.shield`, `Modules.execution`, and `Modules.learning` generic signatures and implementations.
  - Enforce schema validation on Policy output if the engine implements safeguards against hallucinated Intents.
- **`packages/core/src/loop/loopRunner.ts`**:
  - Update the fallback default module implementations (e.g. `execution`, `shield`) to parse `Intent` structures correctly. Re-map `kind === 'call_tool'`, `kind === 'delegate_to_child'`, etc.
- **`packages/memory-engine/src/...`**:
  - Ensure the duplicate `oneTurn.ts` declarations match exactly or deduplicate by importing the core type depending on workspace topology constraints.

### 3. Execution Module Routing & `ExecutableAction` Refactor
`ExecutableAction` must also align with `Intent` using strict discriminant types (Rule 4: Illegal States Must Not Compile).

```typescript
export const ExecutableActionSchema = z.discriminatedUnion('kind', [
    z.object({ kind: z.literal('prompt_user'), token: z.string() }),
    z.object({ kind: z.literal('delegate_to_child'), token: z.string().optional() }),
    z.object({ kind: z.literal('call_tool'), token: z.string().optional() }),
    z.object({ kind: z.literal('answer_with_llm'), echoed: z.boolean() }),
    z.object({ kind: z.literal('internal'), done: z.boolean() })
]);

export type ExecutableAction = z.infer<typeof ExecutableActionSchema>;
```
Refactor how `loopRunner.ts` maps `Intent` to `ExecResult` and `ExecutableAction`. Ensure the default `modules.execution` block enforces strict properties.

### 4. Clean API Constraints
- **NO backwards compatibility**: The framework will not support old `ProposedAction` schemas.
- **NO `any` usage (Rule 5)**: Strictly define schemas utilizing `z.unknown()` for opaque payloads (like tool `args` or child `input`) which will be validated down the line. Keep the boundary strict.
- **Public vs Internal Separation (Rule 10)**: Define `IntentSchema` in a designated shared interface file (e.g. `packages/core/src/types/intent.ts`) rather than burying it inside `oneTurn.ts`.
