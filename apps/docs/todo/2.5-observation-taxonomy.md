# 2.5 Observation Source/Kind Taxonomy Tweaks

## Problem Statement

The system uses a generic `SynthesizeObservation` pattern that lacks exact topological schema boundaries laid out in the APLRET contract (`0-aplret_contracts.md`), occasionally drifting source formats (like `child` token versus `agentId` envelopes). The current observation types in `packages/core/src/loop/oneTurn.ts` use loose generic boundaries that are not properly exported as standalone safe Zod schemas.

Furthermore, the framework currently depends on a complex `ObservationConfig` generic parameter that bleeds across the entire engine (`TaskEngine`, `TurnRunner`, `oneTurn`, `EnvironmentState`). This deeply violates Type System Rule 12 (Avoid Type-Level Overengineering) and forces the framework (the pipe) to know the specific payload shapes of the agent (the brain), violating APLRET architectural boundaries.

This violates the explicitly defined Observation model contracts and makes the system prone to type looseness across boundaries.

---

## 🏗 Requirements

### 1. Kill `ObservationConfig` and Introduce Strict Zod Schemas
Remove the `ObservationConfig` generic parameter from the entire codebase. The framework framework handles the envelopes, but from the framework's perspective, payloads are always `unknown`. 

Define rigid Zod schemas for `UserEnvelope`, `ToolEnvelope`, `ChildEnvelope`, and construct a flat, non-generic `Observation` type. Export these cleanly in a dedicated public types file (e.g. `packages/core/src/types/observation.ts`).

**Required Schema Examples:**
```typescript
import { z } from 'zod';

export const ObservationProvenanceSchema = z.object({
    ts: z.number(),
    turn: z.number(),
    id: z.string().optional(),
    toolId: z.string().optional(),
    correlationId: z.string().optional()
});

export const ExecErrorPayloadSchema = z.object({
    code: z.string(),
    message: z.string()
});

export const ToolEnvelopeSchema = z.object({
    token: z.string(),
    tool: z.string(),
    result: z.unknown().optional(), // Perception will validate this later
    error: ExecErrorPayloadSchema.optional()
});

// To provide IDE support and avoid complex nested discriminated unions, 
// build the base Observation schema discriminated by `source`:
export const ObservationSchema = z.discriminatedUnion('source', [
    z.object({ source: z.literal('user'), kind: z.enum(['input.provided', 'input.cancelled']), payload: z.unknown(), provenance: ObservationProvenanceSchema.optional(), error: ExecErrorPayloadSchema.optional() }),
    z.object({ source: z.literal('tool'), kind: z.enum(['tool.completed', 'tool.failed', 'tool.progress']), payload: ToolEnvelopeSchema, provenance: ObservationProvenanceSchema.optional(), error: ExecErrorPayloadSchema.optional() }),
    // ... complete for child, internal, and env
]);

export type Observation = z.infer<typeof ObservationSchema>;
```

### 2. Enforce Strict Union Payload Fields
- Reformat `ToolEnvelope` to enforce matching tracking fields strictly (must contain `token`, `tool`, `result`/`error`).
- Reformat `ChildEnvelope` to fix drifting formats (must mandate `token`, distinguish properly between `result` and `error`, and explicitly type `agentId` / `childTaskId`).
- Disambiguate and document all `internal` observations correctly (e.g., `internal/validation.failed`, `internal/plan.proposed`).
- Ensure `env` observations (`config.updated`, `clock.tick`, `snapshot.available`) are strictly typed and bounded to the exact string literals defined in APLRET contracts.
- **Rule 11 Enforcement:** All errors embedded in observations MUST be strictly typed (e.g., using `ExecErrorPayloadSchema`), never `unknown`.

### 3. Enforce Runtime Validation Boundaries (Rule 2 & 4)
Types alone do not provide runtime safety.
- **Framework Edge Validation**: The `Transition` module and the Inbox ingestion pipeline **must** explicitly call `ObservationSchema.safeParse()` (or `.parse()`) when formatting or receiving new observations into the engine. Invalid envelopes must fail immediately.
- **Agent Boundary Validation**: The `Perception` module is strictly responsible for parsing the `unknown` payloads into the agent's concrete types.

### 4. Affected Modules Refactoring
- **`packages/core/src/loop/oneTurn.ts` & `loopRunner.ts`**: Strip all `<ObservationPayload extends ObservationConfig>` generics. Replace current loose type definitions with the standard Zod-inferred `Observation` and `TransitionOut` types.
- **`packages/memory-engine/src/shared/types/observation.ts`**: Update the `ChildCompletedObservation` and `ChildCompletedPayload` derivations to use the newly standardized types without copying internal core logic.
- **`packages/core/src/helpers/childObservations.ts`**: Refactor type guards (`isChildCompletedObservation`) to use Zod schema validation (`.safeParse`) instead of manual property checking.
- Update `ObservationInbox` properties to utilize the non-generic `Observation` array.

### 5. Required Documentation Updates
- **`apps/docs/0-aplret_contracts.md`**: Remove all references to generic payload variations (e.g. `UserObservation<T>`) and replace them with the flat, strict `Observation` Zod schema examples representing the framework's single contract.
- **`apps/docs/1-tutorial_build_your_first_aplret_agent.md`**: Remove the definition and usage of `ObservationConfig`. Update the `createAgent` signature and `Obs` type definition to align with the framework dropping generic configuration for specific payload types.

### 6. Clean API Constraints
- **NO backwards compatibility**: The framework will not support old non-compliant observation layouts.
- **NO `any` usage**: Strictly define schemas utilizing `z.unknown()` for opaque payloads which will be validated down the line. Let the framework pass opaque data safely.
- **Public vs Internal Separation**: Define schemas in a designated shared interface file (`packages/core/src/types/observation.ts`) rather than burying it inside `oneTurn.ts`.
