# 4.0 Readability phase overview

> **Internal implementation spec** for framework contributors.  
> **Author-facing canonical references:** [APLRET contracts](../0-aplret_contracts.md), [How-to: `flow.md`](../13-flow_md_for_aplret_agents.md), [How-to: Agent repository layout](../14-agent_repository_layout_for_aplret.md), [How-to: Test](../11-how_to_test_aplret_agents.md), and [Type system rules](./types-rules.md).

## Problem

Phase 2.x and 3.x aligned runtime semantics, but readability and maintainability still depend on conventions that are not consistently enforced in code, exports, scaffolds, and tests.  
The framework now needs a single requirements baseline for:

- behavioral legibility (`flow.md`, branch vocabulary, stage/transition readability),
- repository legibility (types-first layout, selectors/reducers/normalizers/effects split),
- API legibility (clean public exports, explicit stable type surfaces),
- type-system strictness (**removing existing** `any` from public surfaces where touched, not only avoiding new ones; closed unions; schema-first contracts per [types-rules](./types-rules.md)),
- test legibility (branch-level turn-script coverage aligned to docs and flow maps).

## Scope

This phase governs implementation work tracked in:

- [4.1 `flow.md` standard](./4.1-flow-md-standard.md)
- [4.2 agent repository layout & patterns](./4.2-agent-repository-layout-and-patterns.md)
- [4.3 framework readability helpers & reference examples](./4.3-framework-readability-helpers-and-examples.md)

It also defines cross-cutting gates that **every 4.x change** must pass (migration docs, tests, type checks, and build verification).

## Non-negotiable global requirements

1. **No backwards compatibility (with explicit legacy reconciliation)**
   - Legacy shapes and transitional aliases MAY be removed when replaced by canonical APLRET behavior.
   - Do not preserve deprecated readability-unfriendly patterns only to keep old user code compiling.
   - **Reconcile documented/runtime legacy explicitly:** if the codebase or schemas still expose compatibility paths (for example `runMode: 'legacy'` on the runtime manifest, or sugar fields on `createAgent` that bypass typed `loop`), each removal or narrowing MUST ship in a dedicated change with a migration in `apps/docs/migration/` and updates to [Manifest spec](../2-manifest_spec_agent_card_runtime_manifest.md) / [APLRET contracts](../0-aplret_contracts.md) when the public contract changes.
   - Do not leave “no compatibility” stated globally while silent legacy knobs remain; either remove them with migration or document a time-boxed exception in this file and in `0-aplret_contracts.md` until removed.

2. **Migration docs are mandatory after each delivered change**
   - Every merged 4.x change MUST include end-user migration instructions in `apps/docs/migration/`.
   - Existing migrations:
     - [4.0 TaskContext goals / guards / createAgent typing](../migration/4.0-taskcontext-goals-and-createagent-typing.md)
     - [4.1 flow.md adoption](../migration/4.1-flow-md-adoption-migration.md)
  - [4.1 scaffold tooling](../migration/4.1-scaffold-agent-tooling.md)
     - [4.2 repository layout](../migration/4.2-agent-repo-layout-migration.md)
   - New migration files MUST be created whenever behavior, API shape, file layout expectations, or testing workflows change for users.
   - For 4.3 (and any 4.x sub-step), add new migration docs in the same PR as code changes.

3. **Comprehensive testing per change**
   - For each change, review all affected existing tests.
   - Update tests that remain valid.
   - Remove tests tied to deprecated behavior and replace with canonical APLRET assertions.
   - Add new tests for any new functionality (runtime, types, or tooling).
   - **Type-level tests:** any change to exported types or public signatures MUST add or extend compile-time coverage (`tsd` under `packages/core` where present, `packages/types/tests/type-exports.test.ts`, or equivalent). This implements [types-rules](./types-rules.md) Rule 13.

4. **Mandatory verification before completion (CI-executable)**
   - From repository root, the following MUST succeed before a 4.x task is marked done (adjust only if the root `package.json` scripts change — then update this doc in the same PR):
     - `yarn test` — full Jest suite (`jest.config.cjs` roots under `packages/`).
     - `yarn build` — monorepo build via Turbo.
   - When a change touches `@a2arium/callagent-core` public types, also run:
     - `yarn workspace @a2arium/callagent-core test:types` — existing `tsd` checks (see `packages/core/package.json`).
   - When a change touches `@a2arium/callagent-types` exports, ensure `packages/types` tests pass (they run under root `yarn test` via `jest.config.cjs` roots; optionally also `yarn workspace @a2arium/callagent-types test` for a focused run).
   - PR description MUST list the exact commands run and their outcome (pass).

## Alignment with [types-rules](./types-rules.md)

This phase MUST treat `types-rules` as binding for framework code touched by 4.x:

| Rule (summary) | 4.x requirement |
|----------------|-----------------|
| **Rule 5** — no `any` in public APIs | Eliminate `any` from **exported** types and values on surfaces this phase modifies; do not add new `any` on any public export. |
| **Rule 10** — public vs internal | Maintain or introduce a clear boundary: stable exports from `packages/core/src/index.ts` and `packages/types`; internal helpers stay out of barrel exports unless explicitly listed in the public API inventory (below). |
| **Rule 13** — types must be tested | Add/update `tsd` or type-export tests for every public type or signature change. |
| **Rule 14** — type changes are breaking | Document breaking type changes in migration files; update contracts/how-tos when author-visible types change. |
| **Schemas as source of truth (Rule 2)** | Prefer Zod (or existing schema) + `z.infer` for new contract shapes; avoid duplicate parallel `type` definitions. |
| **New contracts use `type` (project convention)** | Use `type` aliases, not `interface`, for new exported contract shapes unless matching an external spec that requires `interface`. |

## Recommended milestone sequencing

1. **Public API inventory + export hygiene** — freeze or document the allowed export list; remove accidental re-exports if any.
2. **Core context and plugin entrypoints** — tighten `TaskContext` / `AgentTaskContext`, `createAgent`, `CreateAgentPluginOptions` without `any` on touched paths.
3. **Loop + harness** — `runLoop`, `oneTurn`, `createTestHarness` typing and internal helpers (`mergeDeep`, synthetic traces) aligned with `TurnTrace` / schemas.
4. **4.1 / 4.2 / 4.3 deliverables** — templates, scaffolds, optional helpers on top of the tightened core.

Skipping (1)–(3) while adding helpers risks compounding untyped surfaces.

## Public API inventory (required deliverable)

Before or during the first substantive 4.x typing PR, add a **single source of truth** for what is public:

- **Location:** a section in [APLRET contracts](../0-aplret_contracts.md) under “Public API discipline” **or** a short `apps/docs/` reference page linked from contracts — chosen in the PR that introduces the inventory.
- **Content:** table or list of: symbol name, package (`@a2arium/callagent-core` / `@a2arium/callagent-types`), stability (`stable` / `experimental`), and migration notes if renamed.
- **Rule:** new exports require an inventory row + type test + migration if user-facing.

### Typing debt and readability debt to track in 4.x

- Current core runtime, orchestration, **shared `TaskContext`**, and plugin code still includes broad `any` usage and unsafe casts (including `createAgent` module sugar, `loopRunner`, orchestration, testing helpers, and guard/type-narrowing helpers).
- **Remediation scope:** any file this phase edits for readability or API clarity MUST leave **no new** `any` on public exports and SHOULD remove existing `any` on those same surfaces before merge (not only “do not add”).
- All new helper/tooling APIs introduced in 4.x must be strongly typed, schema-driven when applicable, and documented in the same change.

### High-priority hotspots (non-exhaustive)

Use these as the default order when tightening types without a broader refactor PR:

1. `packages/core/src/shared/types/index.ts` — `TaskContext` helpers (`goals`, `episodic`, guards using `(x as any)`).
2. `packages/core/src/plugin/createAgent.ts` — sugar merge and `loop` construction typed without `(options as any)`.
3. `packages/core/src/testing/TestHarness.ts` — `mergeDeep`, synthetic `TurnTrace` objects; prefer schema-safe partials or builders.
4. `packages/core/src/loop/loopRunner.ts` — memory reader/writer and default modules: replace `any` with `unknown` + narrowing or typed MentalState paths.

## API and type requirements for this phase

1. **Public API cleanliness**
   - `@a2arium/callagent-core` and `@a2arium/callagent-types` exports must match the **public API inventory** (see above).
   - New readability helpers must have explicit exported types, usage docs in the same PR, and type tests where the export is part of the stable surface.

2. **No `any` on public APIs (remediate when touched)**
   - Do not introduce `any` on any exported symbol.
   - When modifying a module, **remove `any` from exported types and from types that flow into exported signatures** on that module’s public path (per [types-rules](./types-rules.md) Rule 5).
   - Prefer `unknown`, discriminated unions, generics, and `z.infer` from Zod schemas.
   - Use `type` for new exported contract shapes (project convention).

3. **Closed vocabularies**
   - Intents, observation kinds, transition kinds, stage unions, and flow vocabulary must remain closed and synchronized across code/docs/tests.

4. **Schema-first contracts**
   - Any new structured output or config surface should have a runtime schema and inferred `type` — no parallel hand-written duplicates.

5. **Dependency typing (`callllm` and similar)**
   - If stricter checking (`skipLibCheck: false` or expanded `tsd`) surfaces upstream `.d.ts` gaps, track fixes per [external fix request](../external/callllm-declaration-emit-fix-request.md) or document the constraint in the migration + contracts until resolved.

At minimum, readability-phase changes may impact tests across:

- loop behavior and invariants:
  - `oneTurn.coverage`, `loopRunner.coverage`, `runLoop.policy`, `runLoop.shield`, budget/invariant suites
- stage and control semantics:
  - `stageFacade`, `stageInvariants`, `stageEnterContext`, control var accessor tests
- turn trace and telemetry:
  - `turnTrace`, `turnTrace.telemetry`, `turnTrace.subcalls`, `manifestProvenance`
- test harness and stubs:
  - `testHarness`, `testContext`, deterministic stub suites, typed harness tests
- plugin/agent setup and manifests:
  - `manifestResolver`, `PluginManager`, `RunnerAgentRegistration`, runtime manifest schema tests
- type-level surfaces:
  - `packages/types/tests/type-exports.test.ts`
  - existing `tsd` tests where applicable

Every 4.x PR must explicitly state:

- which suites were reviewed,
- which tests were updated/removed/replaced,
- which new tests were added,
- and the executed commands/results for tests and build.

## Migration documentation plan (required)

For every implemented change in 4.x:

1. Create or update a dedicated migration file in `apps/docs/migration/`.
2. Include:
   - what changed and why,
   - who is affected,
   - step-by-step migration actions,
   - before/after examples,
   - verification checklist.
3. Cross-link migration from:
   - the corresponding todo file (`4.1`, `4.2`, `4.3`, or later),
   - relevant how-to docs (`11`, `13`, `14` at minimum when affected).

## Delivery and verification gates

A 4.x change is acceptable only if all are true:

1. Requirements in the corresponding todo spec are met.
2. Migration docs for that specific change are present in `apps/docs/migration/` (or an existing migration is updated with a new subsection for that change).
3. Affected tests are updated/replaced and new tests are added as needed, including **type tests** for public API changes.
4. **`yarn test`** and **`yarn build`** pass from repo root; **`yarn workspace @a2arium/callagent-core test:types`** passes when core public types change.
5. Documentation and implementation are kept in sync in the same delivery.
6. If contracts or manifest behavior change, [APLRET contracts](../0-aplret_contracts.md) and/or [Manifest spec](../2-manifest_spec_agent_card_runtime_manifest.md) are updated in the same delivery (see companion updates below).

## Out of scope

- Introducing compatibility shims for deprecated pre-APLRET patterns **without** a migration and inventory update.
- Deferring migration docs, type tests, or test updates to follow-up PRs.
- Shipping readability tooling without documenting its public usage.

## Exit criteria (phase)

- 4.1–4.3 acceptance criteria are met.
- Public API inventory exists and matches exports.
- Migration docs exist for each delivered 4.x behavior/API/layout change.
- Readability-oriented surfaces are documented, typed, and covered by runtime + type tests where public.
- Final phase validation: **`yarn test`**, **`yarn build`**, and **`yarn workspace @a2arium/callagent-core test:types`** (when core types were touched) all pass.
