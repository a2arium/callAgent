# 5.2 Conversation Phase 2 — Topics, Fan-out Delivery, and Policy-safe Surfaces

> **Internal implementation spec.** This document is for framework contributors and maintainers.
> **For framework users migrating to the new APIs**, create and maintain: **`apps/docs/migration/5.2-conversation-phase-2-topics-fanout-and-policy-safe-surfaces-migration.md`**.
>
> **No backwards compatibility.** See `apps/docs/todo/types-rules.md` Rule 14. Phase 2 ships without dual-shape shims for pre-Phase-2 conversation contracts.

**Scope:** Phase 2 implements the next shippable slice from `apps/docs/planned_architecture/multi-agent-communication.md`, layering on top of the delivered Phase 1 thread primitives:

1. **Topic runtime** — typed `TopicRef`, `ctx.conversation.createTopic / join / leave / post / close`, multi-participant membership model.
2. **Fan-out delivery** — deterministic, atomic per-post fan-out to every current member inbox; typed delivery summary receipts.
3. **Selector / turn-taking policy** — pluggable (`round_robin | broadcast | explicit_recipient`) selector applied at post time, deterministic and test-covered.
4. **Topic observations** — new `source: 'conversation'` kinds: `topic.message.received`, `topic.member.joined`, `topic.member.left`, `topic.closed`, plus framework-only `outbound.committed`. All normalized through the canonical inbox pipeline.
5. **Policy-safe read surface** — read-only `M.memory.conversation` projection (thread state + topic membership + last sequence per conversation) populated by the framework Learning path, so Policy can reason about conversations without calling effectful APIs. Always-on; no opt-in flag.
6. **Durable persistence** — `conversation_topics`, `conversation_topic_members`, and fan-out delivery metadata on `conversation_messages` + a new `conversation_message_deliveries` table; typed store methods.
7. **TurnTrace topic stamping** — extend the Phase 1 compact conversation fields with topic id/kind, selector decision, and fan-out summary without inlining payloads.
8. **Phase 2 example evolution** — upgrade existing `apps/examples/conversation-reference-agent/` and `apps/examples/conversation-responder-agent/` in place to demonstrate topic membership, post fan-out, round-robin turn-taking, and policy-safe read-surface usage. Example agents evolve phase-to-phase; they are the living evidence of the current framework contract.
9. **Public type/schema exports** — Zod-first, inferred types, no public `any`.

### Out of scope (deferred to later phases)

- Cross-runtime transport adapters (Kafka/NATS/external brokers).
- Shared topic documents (collaborative mutable state scoped to a topic).
- Advanced voting/consensus selectors, role-based access control policies.
- Multi-tenant federation / cross-tenant routing.
- Open/public topics (any-agent self-join without invitation).

---

## Problem Statement

Phase 1 established thread primitives: 1-to-1, point-to-point conversation with idempotent sends, queue/reject semantics, and conversation observations. The architecture doc and the Phase 1 spec explicitly deferred topics, fan-out, turn-taking selectors, and policy-safe surfaces.

Agents today cannot:

- address more than one recipient under a single conversation identity,
- participate in a shared channel,
- query conversation state from pure Policy without reading through each observation individually,
- express "post to the room; runtime picks the next responder" behavior.

### 1. Extend public conversation contracts (Zod-first, no `any`)

**Rule enforcement:** Rule 1 (types reflect runtime), Rule 2 (Zod source of truth), Rule 4 (illegal states must not compile), Rule 5 (no public `any`), Rule 10 (public type separation), Rule 11 (typed errors), Rule 12 (avoid overengineering), Rule 14 (breaking type changes require migration doc), Rule 15 (simple + advanced modes).

**Files:**
- `packages/core/src/public-types/conversation/schemas.ts` **(MODIFY)**
- `packages/core/src/public-types/conversation/types.ts` **(MODIFY)**
- `packages/core/src/public-types/conversation/index.ts` **(MODIFY)**

Define and export (Zod + inferred `type`) at minimum:

- `TopicRef` = `z.object({ kind: z.literal('topic'), id: ConversationIdSchema })`. **No new `TopicId` brand** — `ConversationId` is the shared keyspace; `kind` is the discriminator (Rule 12).
- `ConversationRef` = discriminated union of `ThreadRef | TopicRef` with `kind` discriminator.
- `TopicMemberRoleSchema` = `z.enum(['owner', 'participant'])` (Phase 2 closed set).
- `TopicMemberSchema` = `{ agentId, role, sessionIdOverride? }`. `sessionIdOverride`, if present, is persisted directly into `conversation_topic_members.sessionId` at `createTopic` / invite-accepted time; otherwise a deterministic default `"topic-<topicId>:<agentId>"` is used.
- `TopicSelectorSchema` = `z.discriminatedUnion('kind', [ ... ])` with closed kinds:
  - `{ kind: 'broadcast' }` — deliver to all members except sender. **Deterministic delivery ordering** is part of this selector's contract: ascending by `(role asc, registeredAt asc, agentId asc)`.
  - `{ kind: 'round_robin' }` — deterministic rotation across non-sender members by registration order; rotation cursor is persisted on the topic row.
  - `{ kind: 'explicit_recipient', recipientAgentId }` — 1-of-many fan-out with membership check. Single recipient in Phase 2; multi-explicit targeting is deferred.
- `OutboundTopicMessageSchema` — `{ sender, speechAct, content, correlationId? }`. **No `recipientAgentIds[]` field** — recipient selection lives exclusively on the selector (Rule 2 single source of truth).
- `InboundMessageSchema` — **MODIFY**: `conversation: ConversationRefSchema` (thread or topic). `recipientAgentId` semantics: for a topic fan-out, it is the specific inbox owner receiving that delivery copy (not an authoring field).
- `TopicCreateOptionsSchema` — `{ topicId?, members[], defaultSelector?: TopicSelectorSchema, idempotencyKey? }`. `defaultSelector` defaults to `{ kind: 'broadcast' }` when omitted (Rule 15 — simple case: `createTopic({ members })`).
- `TopicInviteOptionsSchema` — owner-initiated invite shape: `{ topic: TopicRef, invitee: TopicMemberSchema }`. Not to be confused with self-`join` (see §3 for `join` semantics).
- `TopicJoinOptionsSchema` — options for accepting an invitation (`inviteToken` required in Phase 2; see §3).
- `TopicLeaveOptionsSchema` — self-leave only; no `agentId` parameter.
- `TopicPostOptionsSchema` — `{ selector?: TopicSelectorSchema, idempotencyKey?, queueMode? }` (per-post selector override allowed; falls back to the topic's `defaultSelector`).
- `TopicCreateReceiptSchema` — `{ topic: TopicRef, members: TopicMemberSchema[] }`. Does **not** send a first message; callers `post` separately.
- `TopicJoinReceiptSchema`, `TopicLeaveReceiptSchema` — typed closed-union outcomes (`ok`, `rejected` with typed `ConversationError`).
- `FanoutSendReceiptSchema` = `z.discriminatedUnion('status', [ 'accepted', 'partial', 'queued', 'rejected' ])`:
  - `accepted`: `deliveries: DeliverySummary[]` (every selected member delivered successfully).
  - `partial`: `accepted[]`, `rejected[]` (per-member failure with typed error). **Only allowed when the message row commit succeeded and at least one recipient accepted**.
  - `queued`: `queuePosition` — only when every selected recipient is queued and none accepted or rejected.
  - `rejected`: `error: ConversationError` — no recipient accepted; the message append is still committed (see §3) but no deliveries remain.
  - **Status priority (deterministic):** `any accepted → accepted (if none rejected and none queued) or partial`; `no accepted but any queued → queued`; `no accepted no queued but any rejected → rejected`. Exhaustive; encoded at the type level via the discriminated union.
- `DeliverySummarySchema` — `{ recipientAgentId, sessionId, messageId, sequenceNumber, dedupeHit, correlationId? }`.
- `ConversationErrorSchema` **(MODIFY — additive closed-union branches only)**:
  - `TopicNotFound`, `NotAMember`, `AlreadyMember`, `SelectorUnsupported`, `RecipientNotMember`, `InviteRequired`, `InviteInvalid`, `ConversationClosed`.
  - `ConversationClosed` supersedes the Phase 1 `ThreadClosed` where applicable: the error applies uniformly to closed threads and closed topics (Rule 12). `ThreadClosed` is removed (migration doc covers this rename).
  - No string fallbacks; every runtime failure path maps to a typed branch.
- `CloseConversationReceiptSchema` **(MODIFY — field rename)** — the receipt field `thread: ThreadRef` is renamed to `ref: ConversationRef` to cover thread and topic closes. Callers read `receipt.ref` and narrow by `kind`.
- `ConversationApi` **(MODIFY)** — add:
  ```ts
  createTopic(options: TopicCreateOptions): Promise<TopicCreateReceipt>;
  invite(options: TopicInviteOptions): Promise<TopicInviteReceipt>;
  join(topic: TopicRef, options: TopicJoinOptions): Promise<TopicJoinReceipt>;
  leave(topic: TopicRef, options?: TopicLeaveOptions): Promise<TopicLeaveReceipt>;
  post(topic: TopicRef, message: OutboundTopicMessage, options?: TopicPostOptions): Promise<FanoutSendReceipt>;
  close(ref: ConversationRef, options?: CloseConversationOptions): Promise<CloseConversationReceipt>; // ref covers threads and topics
  ```

#### `ConversationRef` widening — impact table

| Surface | Phase 1 | Phase 2 | Migration note |
|---------|---------|---------|----------------|
| `ConversationApi.close` argument | `ThreadRef` | `ConversationRef` (`ThreadRef \| TopicRef`) | No runtime break for existing `close(thread)` callers (subtype assignable); callers that type against the receipt field must rename (see next row). |
| `CloseConversationReceipt.thread` | field present | **field renamed** to `ref: ConversationRef` | Breaking. Migration doc includes mechanical rename. |
| `InboundMessage.conversation` | `ThreadRef` | `ConversationRef` | Breaking for consumers pattern-matching on the object shape; narrow by `kind`. |
| `TurnTrace.conversation.kind` | `z.literal('thread')` | `z.enum(['thread', 'topic'])` | Breaking for trace consumers doing `=== 'thread'` without narrow. |
| `TurnTrace.ConversationMessageSummary.kind` | `z.literal('thread')` | `z.enum(['thread', 'topic'])` | Same. |
| `ConversationError` union branches | Phase 1 set + `ThreadClosed` | Phase 1 set (minus `ThreadClosed`) + new branches + `ConversationClosed` | `ThreadClosed → ConversationClosed` is a mechanical rename. |

Public API contract discipline:

- `close` accepts `ConversationRef` (`ThreadRef | TopicRef`) — closes either. Narrow on `ref.kind` before acting on the receipt.
- `post` MUST NOT accept `ThreadRef`. `send` MUST NOT accept `TopicRef`. Rule 4: illegal states must not compile. Type tests enforce this.
- No `any` anywhere in `public-types/conversation/**`.
- All new runtime validation uses Zod schemas in the same module as the inferred types (no hand-maintained duplicate validator/type pairs).

### 3. Introduce topic runtime to the internal conversation service

**Rule enforcement:** Rule 1, Rule 4, Rule 5, Rule 12.

**Files:**
- `packages/core/src/internal/conversation/types.ts` **(MODIFY)**
- `packages/core/src/internal/conversation/ConversationService.ts` **(MODIFY)**
- `packages/core/src/internal/conversation/ConversationRouter.ts` **(MODIFY)**
- `packages/core/src/internal/conversation/TopicSelector.ts` **(NEW)**

Responsibilities:

- `createTopic`:
  - Assign deterministic `topicId` (`topic-<uuidv7>`) if not provided.
  - Persist topic + initial members in one transaction (same pattern as Phase 1 `startThread` atomicity). If either fails, topic is not created.
  - Emit `topic.member.joined` for every initial member to every initial member's inbox (including themselves — chat-client convention).
  - Return typed `TopicCreateReceipt`.
- **Membership model (Phase 2 — owner-gated, invite-based):**
  - Membership is declared at `createTopic` OR through an explicit owner-initiated `invite(topic, invitee)` flow. Only these two paths add members.
  - `invite` — only the topic `owner` may call; emits a single-use `inviteToken` (opaque string; stored transactionally on a new `conversation_topic_invites` table — see §4) and delivers an `internal` observation to the invitee (out of Phase 2 scope — can be returned on the receipt as `{ token }` and handed off by application code). For Phase 2 the invite token is returned in `TopicInviteReceipt.token`; the invitee's application code passes it to `join`.
  - `join(topic, { inviteToken })` — consumes the invite token. Fails with `InviteRequired` / `InviteInvalid` if missing/invalid. On success: (a) insert member row; (b) invalidate invite token; (c) emit `topic.member.joined` to all current members (including the joiner). Atomic.
  - `leave` — self only. No `agentId` parameter. On accepted leave: emit `topic.member.left` to every remaining member; update membership row with `leftAt`; the leaver does not receive the event.
- `post`:
  1. Validate sender is a current member.
  2. Apply selector (default from topic; per-post override allowed). Selector is a pure function of `(members, sender, post context)`; no random or time-based inputs — must be deterministic for tests.
  3. If `selector.kind === 'explicit_recipient'` and the recipient is not a current member → return `rejected` with `RecipientNotMember`. **No message row is appended in this path** (the precondition failed before commit).
  4. Append one row to `conversation_messages` (atomic with the per-recipient delivery rows). Sequence number is assigned on append.
  5. Fan out to each selected recipient via `ConversationRouter.routeObservations` (one observation per recipient inbox). Each recipient sees exactly one `topic.message.received`.
  6. **Idempotency replay rule (authoritative):** replay with same `(tenantId, conversationId, senderAgentId, idempotencyKey)` returns the **original verdict byte-for-byte** — same status (`accepted | partial | queued | rejected`), same `DeliverySummary` list reconstructed from `conversation_message_deliveries`, with `dedupeHit: true` on every summary. Replay never retries previously-rejected or previously-queued recipients. The committed message row is authoritative.
  7. **Status priority (per §1):** `any accepted && none rejected && none queued → accepted`; `any accepted && (any rejected || any queued) → partial`; `no accepted && any queued → queued`; otherwise → `rejected`. Encoded at the type level via the discriminated union.
  8. Per-recipient queue/reject semantics (from Phase 1) apply per-recipient inbox: queue-depth overflow contributes typed `QueueFull` rejection; in-flight recipient under `queueMode: 'reject'` contributes typed rejection.
  9. After commit, inject a framework-emitted `conversation / outbound.committed` observation into the **sender's own inbox** (pre-next-turn). This is how the projection reducer learns of successful outbound posts. Injection is idempotent on replay (same `(messageId, senderAgentId)` produces at most one outbound-committed observation over the agent's lifetime).
- `close` (ref):
  - Thread `ref`: unchanged from Phase 1 semantics.
  - Topic `ref`: mark topic `closed`, emit `topic.closed` to every current member, persist the status change transactionally.
  - Subsequent `post` / `send` on a closed conversation → `rejected` with `ConversationClosed`.
- `ConversationService` MUST retain Phase 1 thread methods (`startThread`, `send`, thread `close`) with unchanged semantics. Topic methods are additive.
- `ConversationRouter.routeObservation` MUST be extended to a `routeObservations(targets[])` form that performs per-target CAS deliveries so a single `post` does not tear the fan-out atomicity (fan-out is all-or-nothing at the message-append boundary; per-recipient delivery errors are surfaced via `partial` receipts without losing the append).

Deterministic contracts (Phase 2 MUST):

- `round_robin` uses the topic's persisted participant registration order (stable across restarts) and a persisted `rotationCursor` column on `conversation_topics`.
- Sequence numbers are assigned at message append; all `DeliverySummary` entries from one `post` share the same `sequenceNumber`.
- Dedupe hits set `dedupeHit: true` on every `DeliverySummary` returned by a replay.
- Scale bound: Phase 2 supports up to **`MAX_TOPIC_MEMBERS = 64`** members per topic. `createTopic` / `invite` rejects with `SelectorUnsupported` (or a dedicated `TopicCapacityExceeded` branch — choose and keep closed-set) past the bound. Document the bound in §11 and the migration. Raising the bound is a future-phase performance question (per-member CAS).

> [!NOTE]
> Phase 2 does not introduce cross-runtime brokers, shared topic documents, voting/consensus selectors, or open self-join. Those remain deferred per the planned-architecture doc.

Fan-out delivery recipients are recorded in a new `conversation_message_deliveries` table keyed on `(tenantId, conversationId, sequenceNumber, recipientAgentId)`. Per-recipient idempotency and sequence replay read join this table. Do not duplicate message rows per recipient.

- `conversation_message_deliveries` **(NEW)**:
  - `(tenantId, conversationId, sequenceNumber, recipientAgentId)` unique
  - `sessionId`
  - `deliveredAt`
  - `dedupeHit` (boolean)
  - `status` (`delivered|rejected|queued`) + `error` (JSON; typed `ConversationError` on read; `NULL` for `delivered`)
  - `queuePosition` (nullable; set only for `queued` status)

Store interface changes (`IWorkingMemorySessionStore`):

- `createConversationTopic({ tenantId, conversationId, ownerAgentId, defaultSelector, members })`.
- `updateConversationTopic({ tenantId, conversationId, patch })` — single consolidated mutator for `status`, `rotationCursor`, selector fields. Rule 12: avoid per-field store methods.
- `addConversationTopicMember(...)`, `removeConversationTopicMember(...)` (sets `leftAt`), `listConversationTopicMembers(...)`.
- `issueConversationTopicInvite(...)`, `consumeConversationTopicInvite(...)`, `revokeConversationTopicInvite(...)`.
- `recordConversationDelivery({ tenantId, conversationId, sequenceNumber, recipientAgentId, sessionId, dedupeHit, status, error?, queuePosition? })`.
- `listConversationDeliveriesBySequence(...)` — reconstructs `DeliverySummary[]` for idempotency replay.
- Extend `appendConversationMessage` to accept `conversationKind` + `selectorKind` + `recipientAgentId: string | null` (thread posts pass `'thread'` and a non-null recipient; topic posts pass `'topic'` and `null`).
- Extend idempotency lookup to cover both threads and topics uniformly (key still `(tenantId, conversationId, senderAgentId, idempotencyKey)`).

Atomicity requirements:

- `createTopic` writes topic row + all member rows + staged `topic.member.joined` observations in one transaction.
- `invite` writes the invite row + stages any observation in one transaction.
- `join` consumes the invite row + writes the member row + stages the joined observation in one transaction.
- `post` writes one message row + N delivery rows in one transaction. Inbox CAS updates happen after the message commit and are idempotent on replay (delivery rows are the authoritative record; inbox writes re-derive from them).
- `close` updates topic status + stages `topic.closed` observations atomically.

### 7. Policy-safe conversation read surface

**Rule enforcement:** Policy purity rule (see `apps/docs/3-how_to_keep_policy_pure.md`), Rule 1, Rule 4, Rule 5, Rule 12 (avoid overengineering).

**Files:**
- `packages/core/src/loop/types.ts` **(MODIFY)** — extend `MentalState['memory']` with a typed, **deeply read-only** `conversation` projection.
- `packages/core/src/loop/learning/conversationReducer.ts` **(NEW)** — deterministic reducer that folds conversation observations into `M.memory.conversation`.
- `packages/core/src/loop/internalContext.ts` **(MODIFY)** — wire the reducer so the framework runs it in the canonical Learning pipeline. **Always on.** No opt-in capability flag (Rule 12 — the slice is absent when no conversation observations have been folded, so there is no cost to leave it on).
- `packages/core/src/public-types/conversation/projection.ts` **(NEW)** — exported typed shape of `M.memory.conversation` for consumer agents.

Projection shape (Zod + inferred type; exposed to Policy as `DeepReadonly<ConversationProjection>`):

```ts
type ConversationProjection = {
  threads: Record<ConversationId, {
    ref: ThreadRef;
    status: 'open' | 'closed' | 'archived';
    lastInboundSequence?: number;
    lastOutboundSequence?: number;
    pendingOutgoing: boolean;
  }>;
  topics: Record<ConversationId, {
    ref: TopicRef;
    status: 'open' | 'closed' | 'archived';
    members: Array<{ agentId: string; role: 'owner' | 'participant' }>;
    lastInboundSequence?: number;
    lastOutboundSequence?: number;
    currentSelector: TopicSelector;
  }>;
};
```

Requirements:

1. Reducer is pure and deterministic. It ONLY reads conversation observations already on the inbox and the previous `M.memory.conversation` slice.
2. The projection is exposed on `m.memory.conversation` typed as `DeepReadonly<ConversationProjection>` — Policy cannot mutate at the type level **and** the framework freezes the object at runtime (defense in depth; Rule 4).
3. The reducer must not read `ctx.*`, must not perform I/O, must not reach persistence.
4. Update rules:
   - `topic.member.joined` adds/updates member entry.
   - `topic.member.left` removes entry (keeps status unchanged).
   - `topic.closed` / `thread.closed` updates status.
   - `topic.message.received` / `message.received` updates `lastInboundSequence`.
   - `delivery.failed` clears `pendingOutgoing` but does not advance inbound sequence.
   - `outbound.committed` updates `lastOutboundSequence` and clears `pendingOutgoing`.
5. Outbound tracking is populated exclusively from `conversation / outbound.committed` observations injected by ApiBinder post-commit (see §5 item 6). Agents never write this path; there is no other source of outbound state.
6. No feature gate. The reducer is part of the canonical Learning pipeline. Agents that never see conversation observations have an empty projection (`threads: {}, topics: {}`) — zero serialization overhead.

> [!IMPORTANT]
> Policy purity: no `ctx.conversation.*` in Policy. Policy reads the projection (read-only at type and runtime levels) and emits intents. Execution calls the effectful API. This preserves the Phase 1 and Phase 2 effect boundary.

### 11. Clean API constraints (MUST hold after implementation)

1. `ctx.conversation.createTopic / invite / join / leave / post / close` are fully typed, Zod-backed, and schema-exported.
2. No new public `any` in the conversation module (schemas, types, receipts, errors, projection, observation payloads, trace fields).

8. `M.memory.conversation` projection is populated only by the framework-owned reducer; the type is `DeepReadonly<ConversationProjection>` and the runtime object is `Object.freeze`d.

10. Phase 2-upgraded canonical examples (existing `conversation-reference-agent` + `conversation-responder-agent`) demonstrate fan-out + selector + policy-safe read.

## ✅ Acceptance Criteria

1. `ctx.conversation.createTopic / invite / join / leave / post / close(ref)` exist as typed, schema-backed public API contracts.
2. No new public `any` in conversation contracts, observation payloads, receipts/errors, projection, or trace fields touched in this phase.
3. Topic and thread observations both flow through the canonical `ObservationSchema` and inbox normalization; the `conversation` branch has a single source of truth (outer `kind` derived from payload union).
4. `createTopic` is atomic (topic row + all member rows + staged joined observations in one transaction); `invite` and `join` atomicity likewise hold.
5. `post` returns a deterministic `FanoutSendReceipt` with exhaustive `accepted | partial | queued | rejected` statuses and typed per-recipient errors; status priority rules are encoded in the discriminated union.
6. Selectors `broadcast | round_robin | explicit_recipient` are deterministic and test-covered; `broadcast` ordering is `(role, registeredAt, agentId)`; `round_robin` cursor persists across restarts.
7. Idempotent replay returns the original verdict byte-for-byte, sets `dedupeHit: true` on every `DeliverySummary`, emits zero duplicate inbox observations, injects at most one `outbound.committed` per successful post, and never retries previously-queued or previously-rejected recipients.
8. Per-recipient queue/reject semantics are deterministic and test-covered.
9. `M.memory.conversation` projection is populated only by the framework reducer, typed as `DeepReadonly<ConversationProjection>`, and runtime-frozen. Agent code cannot mutate it.
10. `TurnTrace` includes optional compact topic/fan-out/selector fields and parses successfully under Zod; non-conversation turns remain unaffected; `conversation.kind` widening is documented as breaking.
11. `post(threadRef, ...)` and `send(topicRef, ...)` fail to compile; type tests enforce this.
12. Upgraded canonical example agents (`conversation-reference-agent`, `conversation-responder-agent`) demonstrate broadcast, round-robin, explicit recipient, idempotent replay, invite→join flow, and projection reads in Policy. Phase 1 thread behavior in these examples still passes after the upgrade.
13. Existing impacted tests are updated/replaced as documented (no compat shims); all new tests are implemented and deterministic.
14. Migration guide exists at `apps/docs/migration/5.2-conversation-phase-2-topics-fanout-and-policy-safe-surfaces-migration.md`, is written incrementally alongside implementation, and covers every user-visible change.
15. Downstream docs enumerated in §Downstream Doc Updates are updated/reviewed as specified (every root `apps/docs/*.md` is accounted for).
16. `MAX_TOPIC_MEMBERS = 64` enforced; typed error on overflow.
17. Final verification passes: `yarn test` and `yarn build`, zero TypeScript errors, Prisma migration applies cleanly on a fresh database, and `apps/docs/planned_architecture/multi-agent-communication.md` marks Phase 2 as delivered with a link to the migration doc.
