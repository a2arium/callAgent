# Migration guide: Adopting `flow.md` for APLRET agents (4.1)

This guide helps you add and maintain **`flow.md`** — the canonical **behavioral map** for agents with awaits, major branches, or non-trivial control flow.

There is **no framework package upgrade** required for the documentation standard itself. Optional validators or scaffolds shipped under [todo 4.1](../todo/4.1-flow-md-standard.md) are additive.

**Related:** [How-to: `flow.md` for APLRET agents](../13-flow_md_for_aplret_agents.md) · [APLRET contracts](../0-aplret_contracts.md) · [How to test APLRET agents](../11-how_to_test_aplret_agents.md)  

---

## Who is affected

| You… | Action |
|------|--------|
| Maintain an agent with `await_*`, multiple branches, planning/repair, or structured LLM steering | **Add** `flow.md` next to `agent.ts` and keep it updated with behavior changes. |
| Only have a minimal single-turn agent | **Optional** `flow.md`; skip unless the procedure is already hard to explain. |
| Review agent PRs | Treat **`flow.md`** like code when behavior over time changes. |

---

## Overview

1. Copy the **required section order** from [How-to: `flow.md`](../13-flow_md_for_aplret_agents.md).
2. Fill **State vocabulary** from `types.ts` — spellings must match code **exactly**.
3. Build the **Flow table** from Policy → Execution → Transition paths you actually implement.
4. Add **Branches** with IDs `B1`, `B2`, … for major failures and side paths.
5. Write **Turn semantics** for awaits and inbox-gated resumes.
6. Add **Code map** pointing to real files.
7. Align **tests** to major rows and branch IDs (see [How to test](../11-how_to_test_aplret_agents.md)).

## Step-by-step: creating `flow.md` from an existing agent

### 1. Name and purpose

- Title: `# Flow: <same-name-as-agent-card-or-folder>`
- **Purpose**: 1–3 sentences on what the agent accomplishes for the user or caller.

### 2. Flow summary

Number 4–10 steps: happy path, key failures, explicit await/resume points.

### 3. State vocabulary

Lift from code:

- Stages (if using StageFacade — names must match facade config)
- Normalized observation kinds (from `Obs` union)
- Intent kinds (domain-named)
- Execution result categories Transition switches on
- Terminal outcomes (success/failure semantics)

### 4. Flow table

One row per **major** path. Columns: Current condition → Policy emits → Execution does → Transition outcome → Next turn consequence.

### 5. Branches and failure paths

For each important failure or alternate path, add `### Bn: …` with trigger, response, outcome.

### 6. Turn semantics

State inbox rules, effect boundary, and what resumes the loop (especially child/tool completions).

### 7. Code map

List `agent.ts`, `types.ts`, and the main behavioral files (normalizers, reducers, policy, effects, transition).

---

## Maintenance rule

If a PR changes stages, observations, intents, awaits, major branches, or terminal outcomes, **update `flow.md` in the same PR**.

See **Keeping `flow.md` in sync** in [doc 13](../13-flow_md_for_aplret_agents.md).

---

## Test mapping (recommended)

- Dominant success path → e.g. `golden.test.ts` or equivalent.
- Each await/resume path → `resume.test.ts` or dedicated cases.
- Each major failure branch → `failure.test.ts` or per-`Bn` describes.

Optional section at bottom of `flow.md`:

```md
## Covered by tests
- B1 -> tests/failure.test.ts
```

## Checklist

- [ ] Required sections present in order
- [ ] Vocabulary matches `types.ts` spelling
- [ ] Flow table matches Transition behavior
- [ ] Awaits and terminals explicit
- [ ] Tests cover documented branches
- [ ] Same PR updates `flow.md` when behavior changes
