# Migration Guide: Manifest Split (Agent Card & Runtime)

As of version `0.3.0`, CallAgent has transitioned from a single-file `agent.json` (or `.manifest`) to a dual-manifest structure. This split separates **public identity** from **private runtime configuration**, aligning with the [A2A (Agent-to-Agent)](https://a2a-protocol.org) protocol standards.

## 1. The Core Concept

The manifest is now split into two distinct files located in your agent's directory:

1.  **`agent-card.json` (Public Metadata)**: Contains information used for discovery and interoperability. This is what other agents see.
2.  **`agent-runtime.json` (Internal Configuration)**: Contains CallAgent-specific settings that control how the agent executes.

> [!IMPORTANT]
> This change is **not backward compatible**. You must migrate your existing `agent.json` or inline manifest definitions to the new structure.

## 2. Decision Framework: Where does a field go?

| Put it in `agent-card.json` if it answers: | Put it in `agent-runtime.json` if it answers: |
| :--- | :--- |
| **Who** is this agent? (`name`, `version`, `description`) | **How** should CallAgent run this agent? (`runMode`) |
| **What** can this agent do? (`skills`, `capabilities`) | What **limits/safety** apply? (`budgets`, `safety`, `hitl`) |
| **How** is it discovered/called? (`supportedInterfaces`) | What are its **internal needs**? (`dependencies`, `memory`, `cache`) |

## 3. Field Mapping

Use the following table to map your legacy fields to the new files:

| Legacy Field | New Destination | Rationale |
| :--- | :--- | :--- |
| `name` | **Both** | Required for matching identity between card and runtime. |
| `version` | **Both** | Must match to ensure the runtime configuration aligns with the public card. |
| `description` | `agent-card.json` | Used for discovery and LLM-based agent selection. |
| `skills` | `agent-card.json` | Describes capabilities to external consumers. |
| `capabilities` | `agent-card.json` | Publicly declared features (e.g., streaming). |
| `budgets` | `agent-runtime.json` | Internal execution limits (max turns, latency). |
| `hitl` | `agent-runtime.json` | Human-in-the-loop triggers and policies. |
| `safety` | `agent-runtime.json` | Content filtering and PII scrubbing rules. |
| `cache` | `agent-runtime.json` | Internal result caching behavior. |
| `dependencies` | `agent-runtime.json` | Required sub-agents or external service hooks. |
| `memory` | `agent-runtime.json` | Memory allocation and persistence settings. |
| `config` | `agent-runtime.json` | Custom agent-specific knobs and feature flags. |
| `runMode` | `agent-runtime.json` | Controls the execution model (`loop`, `legacy`). |

## 4. Example Migration

### Legacy `agent.json` (Before)
```json
{
  "name": "weather-agent",
  "version": "1.0.0",
  "description": "Answers weather questions",
  "skills": [{ "id": "forecast", "name": "Forecast lookup" }],
  "budgets": { "maxTurns": 8 },
  "safety": { "piiScrubbing": true },
  "cache": { "enabled": true },
  "runMode": "loop"
}
```

### New Split Files (After)

**`agent-card.json`**
```json
{
  "name": "weather-agent",
  "version": "1.0.0",
  "description": "Answers weather questions",
  "skills": [{ "id": "forecast", "name": "Forecast lookup" }]
}
```

**`agent-runtime.json`**
```json
{
  "name": "weather-agent",
  "version": "1.0.0",
  "budgets": { "maxTurns": 8 },
  "safety": { "piiScrubbing": true },
  "cache": { "enabled": true },
  "runMode": "loop"
}
```

## 5. `createAgent` API Changes

The `createAgent` function is now **asynchronous** and automatically resolves manifests relative to the caller's directory (using `import.meta.url`).

### Automatic Resolution (Recommended)
Place `agent-card.json` and `agent-runtime.json` in the same folder as your agent file.
```ts
export const agent = await createAgent({}, import.meta.url);
```

### Explicit Paths
```ts
export const agent = await createAgent({
  agentCard: { path: './custom-card.json' },
  runtimeManifest: { path: './custom-runtime.json' }
}, import.meta.url);
```

### Inline Definition
```ts
export const agent = await createAgent({
  agentCard: {
    inline: {
      name: 'weather-agent',
      version: '1.0.0',
      description: '...'
      // ... other required Card fields
    }
  },
  runtimeManifest: {
    inline: {
      name: 'weather-agent',
      version: '1.0.0',
      runMode: 'loop'
    }
  }
}, import.meta.url);
```

## 6. Validation Rules

The framework enforces strict validation during startup:

1.  **Identity Match**: `name` and `version` must be identical in both files. If they differ, the agent will fail to load with a `Manifest identity mismatch` error.
2.  **Schema Compliance**: Files are validated against strict Zod schemas. Extraneous fields are not allowed at the top level. Move custom settings to the `config` object in `agent-runtime.json`.
3.  **Missing Files**: By default, `createAgent` expects both files to exist in the agent's directory.

## 7. Security Best Practices

> [!WARNING]
> Never put sensitive information (API keys, credentials, private internal paths) in `agent-card.json`.

*   **`agent-card.json`** is intended to be public (exposed at `/.well-known/agent-card.json` in A2A-compliant servers).
*   **`agent-runtime.json`** is for local runtime controls. While safer than the card, it should still only contain configuration. Use environment variables for actual secrets.
