# Observation Taxonomy Migration Guide

This guide details how to migrate your agent implementations to adapt to the removal of the generic `ObservationConfig` type and the introduction of strict Zod schemas for observations.

## 1. Removal of `ObservationConfig`

Previously, agents defined a strict `ObservationConfig` to override the payload shapes of `user`, `tool`, `child`, `internal`, and `env` observation types. The framework then piped these generics everywhere. This has been removed to comply with Rule 12 (Avoid Type-Level Overengineering).

**Before:**
```typescript
type ObservationConfig = {
  user: string | { text: string };
  tool: { summary: string };
  child: { summary: string };
  internal: { value: string };
  env: { value: string };
};

export const agent = createAgent<Sensory, Obs, unknown, Intent, unknown, ObservationConfig>({
  // ...
});
```

**After:**
`ObservationConfig` has been entirely removed from the framework. `createAgent` no longer accepts a 6th type parameter representing observation shapes.

```typescript
export const agent = createAgent<Sensory, Obs, unknown, Intent, unknown>({
  // ...
});
```

From the framework's standpoint, ALL observation payloads are `unknown` natively.

## 2. Using Zod in Perception

Because the framework now provides `Observation` shapes with `unknown` payloads, the agent's `Perception` module is strictly responsible for validating and unpacking those payloads into the specific types expected by the agent's cognition layer.

**Before:**
```typescript
perception: (env) => {
    const userObs = env.inbox.current.find(o => o.source === 'user');
    // Typescript previously knew userObs.payload was { text: string } based on generic
    const text = userObs.payload.text; 
    return { kind: 'user_message', text };
}
```

**After:**
```typescript
import { z } from 'zod';

const UserPayloadSchema = z.object({ text: z.string() });

perception: (env) => {
    const userObs = env.inbox.current.find(o => o.source === 'user');
    if (!userObs) return { kind: 'idle' };

    // Validate the unknown payload explicitly
    const parsed = UserPayloadSchema.safeParse(userObs.payload.value);
    if (!parsed.success) {
        return { kind: 'error', reason: 'Invalid payload' };
    }

    return { kind: 'user_message', text: parsed.data.text };
}
```

## 3. Strict Envelope Fields

If your agents manually inject observations into the `inbox` during custom workflows or testing, ensure you conform strictly to the newly enforced Zod envelopes.

### Tool Observations
`tool` observations must now contain: `token`, `tool`, and either `result` or `error`.
```typescript
{
    source: 'tool',
    kind: 'tool.completed',
    payload: {
        token: 'tool-token-123',
        tool: 'fetchWeather',
        result: { temp: 72 } // Can be unknown, validated by perception
    }
}
```

### Child Observations
`child` observations must enforce `token` rather than drifting between `agentId` and `token`.
```typescript
{
    source: 'child',
    kind: 'child.completed',
    payload: {
        token: 'child-token-456',
        result: { status: 'ok' },
        agentId: 'helper-bot'
    }
}
```

### Internal and Env Observations
These must adhere strictly to the allowed list of `kind` values:
- `internal`: `llm.responded`, `plan.proposed`, `plan.updated`, `goal.updated`, `validation.failed`, `state.noted`.
- `env`: `config.updated`, `clock.tick`, `snapshot.available`, `external.event`.

Instead of raw exceptions, emit `internal` observations with kind `validation.failed` to allow the agent (or LLM) an opportunity to self-correct during the next cognitive loop turn.
