# Migration Guide: Remove `ctx.vars` and Read-Only `ctx.world` (v3.3.1)

This guide covers the removal of `ctx.vars` and `memory.vars`, and the enforcement of read-only `ctx.world` in CallAgent v3.3.1. There is **no backwards compatibility**: code that used `ctx.vars` or mutable `ctx.world` will no longer compile or run as before.

**Migration order (3.3 vs 3.3.1):** The v3.3.1 vars/world changes and the v3.3 [invariant error shapes](3.3-invariant-error-shapes-migration.md) are **independent**: neither depends on the other. We recommend **doing both migrations in one upgrade** when moving to 3.3.1 — one pass over the codebase and one test cycle. If you need to adopt only the vars/world changes (e.g. you already use the new error handling), you can follow this guide alone.

## Summary of changes

| Area | Before | After |
|------|--------|--------|
| `ctx.vars` | Optional scratchpad (get/set/merge/delete) | **Removed** — does not exist; compile error if used |
| `MentalState.memory.vars` | Optional key-value store | **Removed** — not on type or snapshot |
| `ctx.world` | Sometimes mutable (update/patch) | **Read-only** — only `ctx.world.read()`; no update/patch |
| `persistChildContext` | Accepted `vars` in options | **Signature**: `{ tenantId, sessionId, agentId }` only |
| `ensureAgentContext` | Required `ctx.vars` | No longer checks or requires `vars` |
| `SerializedWorkingMemory` | Had `variables` | **Removed** — only goal, thoughts, decisions |
| `WorkingMemoryState` | Had `variables` | **Removed** (types + memory-engine) |

## End-to-end example: agent handler before and after

**Before (v3.3):** Agent used `ctx.vars` for stage and user data, and `ctx.world.patch()` to record the last action.

```typescript
async handleTask(ctx: TaskContext) {
    ctx.vars.set('stage', 'collecting');
    const input = await ctx.requestInput('Name?', { setToken: true });
    ctx.vars.set('user.name', input.value?.name);

    const theme = ctx.vars.get<string>('user.preferences.theme') ?? 'light';
    ctx.world.patch({ lastAction: 'greeting', theme });

    await ctx.complete(100, 'Done');
}
```

**After (v3.3.1):** Control state (stage, token) lives in **StageFacade** / `requestInput` options; business state lives in **worldModel** and is written only in **Learning**; Execution only reads.

In your **loop modules** (e.g. `oneTurn`), the **Learning** function receives a `MemoryWriter` as the `writer` argument. Use it to update the world model from observations:

```typescript
// Learning module (runs in the loop; writer is provided by the runtime)
learning: async (prev, prevAction, observation, mem, writer) => {
    const next = { ...prev };
    next.worldModel = { ...(prev.worldModel || {}) };

    // Example: from user input observation, write into worldModel
    const userObs = observation?.source === 'user' ? observation : null;
    const payload = (userObs as { payload?: { value?: { name?: string } } })?.payload?.value;
    if (payload?.name) {
        next.worldModel.userName = payload.name;
    }
    if (payload?.theme) {
        next.worldModel.userPreferences = { ...(next.worldModel.userPreferences as object || {}), theme: payload.theme };
    }
    next.worldModel.lastAction = 'greeting';
    writer.world.set(next.worldModel);
    return next;
},
```

In **Execution** (e.g. your tool handler or agent step), only read the world; do not mutate it:

```typescript
// Execution: read-only access
async execute(action, ctx, mem, m) {
    const world = await ctx.world.read();  // or use m.worldModel if you have M
    const theme = (world as Record<string, unknown>).userPreferences?.theme ?? 'light';
    // ... use theme; do not call ctx.world.update() or ctx.world.patch()
    return { action, result: { ok: true } };
}
```

Control state (stage, input token) is set via **StageFacade** and `requestInput` options instead of `ctx.vars`:

```typescript
// Instead of ctx.vars.set('stage', 'awaiting_input')
await ctx.requestInput('Name?', {
    setStage: 'awaiting_input',
    setToken: true,
    setTokenPath: 'input.token'
});
```

See **[How to use StageFacade in APLRET](../5-how_to_use_stage_facade_in_aplret.md)** for defining stages, invariants, and control marks.

## 1. Removing `ctx.vars` usage

### Control state (tokens, stage, input handles)

Use the **StageFacade** and pending control state instead of vars:

- **Before:** `ctx.vars.set('stage', 'awaiting_input'); ctx.vars.set('inputToken', token);`
- **After:** Use `requestInput(..., { setStage: 'awaiting_input', setToken: true })` and/or `env.pending.controlVars` (e.g. set via Learning from observations). For a full guide, see **[How to use StageFacade in APLRET](../5-how_to_use_stage_facade_in_aplret.md)**.

### Business state (facts, entities, decisions)

Store in `MentalState.worldModel` and update only from **Learning** via `MemoryWriter.world.set()`:

- **Before:** `ctx.vars.set('user.preferences.theme', 'dark');`
- **After:** In your **Learning** module, call `writer.world.set(newWorldModel)`. The `writer` is the `MemoryWriter` passed into the learning function by the loop (see [End-to-end example](#end-to-end-example-agent-handler-before-and-after)). To merge with the current world, read from `mem.world.get()` (or from `prev.worldModel`), merge, then call `writer.world.set(merged)`. Policy and Execution read via `ctx.world.read()`.

### Ephemeral scratch

If you need short-lived working data that is not control state:

- **Before:** `ctx.vars.set('tempCalculation', value);`
- **After:** Use Learning-owned `MentalState.memory.scratch` (or another Learning-owned field) and expose read/write only through Learning; do not expose a generic vars facade to Execution.

## 2. Read-only `ctx.world`

- **Before:** Code might call `ctx.world.update(fn)` or `ctx.world.patch({ ... })` to mutate the world model.
- **After:** Only Learning may mutate `worldModel` via `MemoryWriter.world.set()`. Execution and Policy may only call `ctx.world.read()`, which returns a **deep read-only copy**. Mutating the return value does not change `MentalState`.

**Migrating `ctx.world.update(fn)` or `ctx.world.patch(p)`:**

If you had:

```typescript
ctx.world.patch({ lastAction: 'greeting', count: (ctx.world.read()?.count ?? 0) + 1 });
```

move the logic into **Learning**: in the learning function, compute the new world from the previous state and observations, then call `writer.world.set(newWorldModel)`. Example:

```typescript
// In learning:
const current = prev.worldModel || {};
const nextWorld = {
    ...current,
    lastAction: 'greeting',
    count: ((current as { count?: number }).count ?? 0) + 1
};
writer.world.set(nextWorld);
```

## 3. Memory-engine and type changes

- **TaskContext** / **AgentTaskContext**: The `vars` property has been removed. Remove any `ctx.vars` usage and any `ensureAgentContext` reliance on `vars`.
- **SerializedWorkingMemory**: The `variables` field has been removed. Serialization/deserialization uses only `goal`, `thoughts`, and `decisions`.
- **WorkingMemoryState**: The `variables` field has been removed. Session state no longer includes a variables map.
- **extendContextWithMemory**: No longer assigns `context.vars`. If you depended on `ctx.vars` being set after extending context, switch to `worldModel`/controlVars/scratch as above.
- **serializeVars**: Removed from the memory-engine package. Do not import or call it.

---

## 4. Snapshot and persistence

- **flushContextSnapshot** does not persist or merge any `vars`; it persists `MentalState` (including `worldModel` and `memory.scratch`) and LLM state.
- **persistChildContext** no longer accepts or merges `vars`. Call signature is `persistChildContext({ tenantId, sessionId, agentId })`.
- **applyInputProvided** (DurableHandlerRegistry) does not use `snapshot.vars`; delivered input is represented only via the observation added to the inbox (and any Learning that runs as a result).

---

## 5. Compilation error resolution

| Error / symptom | Fix |
|-----------------|-----|
| `Property 'vars' does not exist on type 'TaskContext'` | Remove `ctx.vars` usage; use controlVars, worldModel, or scratch as above. |
| `MentalState.memory.vars` not assignable / missing | Remove `memory.vars` from fixtures and types; use `worldModel` (and optional `memory.scratch`) instead. |
| `ctx.world.update is not a function` | Replace with Learning that calls `MemoryWriter.world.set()` and/or patch helpers. |
| `ensureAgentContext` fails because `ctx.vars` is missing | Upgrade to a version that does not require `vars`; ensure context is extended with memory so other required methods exist. |
| `SerializedWorkingMemory` missing `variables` | Stop reading or writing `variables`; use only goal, thoughts, decisions. |

---

## 6. Testing

- Replace any snapshot or fixture that used `M.memory.vars` or `snapshot.vars` with `worldModel` (and full `MentalState` shape where required).
- Remove tests that asserted on `mergeVarsIntoMental`, `iterateMentalTargets`, or vars merging in snapshots.
- Tests that relied on `persistChildContext(..., { vars })` should call `persistChildContext({ tenantId, sessionId, agentId })` and assert on `worldModel` or other persisted state instead of vars.

## 8. FAQ

**What happens to my existing persisted snapshots that had `M.memory.vars`?**  
The framework no longer reads or writes `vars` on load/save. When you load an old snapshot, any `vars` key in `M.memory` is ignored. The rest of the snapshot (e.g. `worldModel`, `memory.scratch`, goals, plans) is unchanged. There is no automatic migration of old `vars` data into `worldModel`; if you need that data, you must migrate it once (e.g. with a script that reads old snapshots and writes new ones with the same data in `worldModel`).

**Can I keep using `ctx.vars` with a polyfill or wrapper?**  
No. The type no longer has `vars`, and the runtime does not attach it. By design, there is no backwards-compatible facade. You must migrate to controlVars / worldModel / scratch.

**I was using `ctx.vars` to pass state between turns — what is the 1:1 replacement?**  
- For **control** state (tokens, stage, “awaiting X”): use **StageFacade** and `env.pending.controlVars` (see [StageFacade guide](../5-how_to_use_stage_facade_in_aplret.md)).  
- For **business** state (facts, user preferences, conversation summary): use **worldModel**. Write in Learning via `writer.world.set()`; read in Policy/Execution via `ctx.world.read()`.

**Does `ctx.world.read()` return a live reference or a snapshot?**  
A **snapshot**: the runtime returns a deep copy (e.g. JSON round-trip or equivalent) and may freeze it. Mutating the returned object does **not** change `MentalState.worldModel`.

**Where does `MemoryWriter` come from? Can I call it from Execution?**  
The loop (e.g. `oneTurn`) creates a `MemoryWriter` per turn and passes it **only** into the **Learning** function. Execution does not receive a writer. To update the world model, you must do it inside Learning, based on observations (e.g. user input, tool results) that were produced in earlier steps of the turn or previous turns.
