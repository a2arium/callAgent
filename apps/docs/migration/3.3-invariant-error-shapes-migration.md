# Migration Guide: Invariant Error Shapes (v3.3)

This guide provides instructions for migrating to the structured invariant error handling introduced in CallAgent v3.3.

**Migration order (3.3 vs 3.3.1):** The v3.3 invariant error shapes and the v3.3.1 vars/world changes are **independent**: neither depends on the other. We recommend **doing both migrations in one upgrade** when moving to 3.3.1 — one pass over the codebase, one test cycle, and fewer versions to support. If you are already on 3.3 and will move to 3.3.1 later, you can do this migration first and the [vars/world migration](3.3.1-remove-memory-vars-migration.md) when you upgrade to 3.3.1.

## Why this change?

Previously, when the framework hit an invariant violation (e.g. budget exceeded, invalid token, or malformed observation), it threw a plain `Error` with a free-form message. That made it impossible to programmatically distinguish between, say, a turn-limit violation and a tool failure. Callers had to parse `e.message` with string matching, which was brittle and not type-safe.

In v3.3, every framework invariant violation throws an **InvariantError** (or, for non-invariant module failures, **ModuleExecutionError**) with a **machine-readable `code`** and a **typed `detail`** payload. You can catch by code, assert in tests, and log structured data without relying on message text.

## Overview

The framework has moved from throwing plain `Error` objects for internal invariant violations to using structured `InvariantError` and `ModuleExecutionError` types. This change improves robustness, allows for programmatically inspectable error details, and ensures adherence to the APLRET contract.

## Error code catalog

`ctx.throw` and framework-thrown invariant errors use a **closed set** of codes. The `detail` object is a discriminated union keyed by `type`. Use the correct `detail` shape for each code.

| Code | When thrown | Detail `type` | Detail shape |
|------|-------------|----------------|--------------|
| `STAGE_REQUIRES_KEY` | Stage invariant: required key missing | `stage_invariant` | `{ stage, required?, forbidden?, pendingSnapshot? }` |
| `STAGE_FORBIDS_KEY` | Stage invariant: forbidden key present | `stage_invariant` | same |
| `INPUT_TOKEN_NOT_FOUND` | Input token missing | `token_validation` | `{ category: 'input', token?, reason: 'missing' \| 'expired' \| 'mismatch' \| 'unknown_token', ... }` |
| `INPUT_TOKEN_EXPIRED` | Input token expired | `token_validation` | same |
| `TOOL_TOKEN_NOT_FOUND` | Tool token missing | `token_validation` | `{ category: 'tool', ... }` |
| `CHILD_TOKEN_NOT_FOUND` | Child task token missing | `token_validation` | `{ category: 'child', ... }` |
| `TOKEN_MISMATCH` | Token mismatch | `token_validation` | same |
| `OBSERVATION_VALIDATION_FAILED` | Observation envelope invalid (see §Observation validation below) | `observation_validation` | `{ source?, kind?, reason, observationIndex?, inboxSummary?, validation? }` |
| `CONTINUE_WITHOUT_OBSERVATIONS` | Transition invariant | `transition_invariant` | `{ transitionKind, reason, pendingSnapshot? }` |
| `AWAIT_MISSING_TOKEN` | Await without token | `transition_invariant` | same |
| `TERMINAL_WITH_PENDING` | Terminal with pending work | `transition_invariant` | same |
| `GOAL_NOT_FOUND` | Goal API: goal not found | `goal_invariant` | `{ goalId?, reason: 'goal_not_found' \| 'goal_has_active_children' \| 'priority_out_of_range' }` |
| `GOAL_HAS_ACTIVE_CHILDREN` | Goal has active children | `goal_invariant` | same |
| `GOAL_PRIORITY_OUT_OF_RANGE` | Goal priority out of range | `goal_invariant` | same |
| `BUDGET_TURNS_EXCEEDED` | Turn limit reached | `budget_exceeded` | `{ budget: 'turns', limit, actual }` |
| `BUDGET_LATENCY_EXCEEDED` | Latency budget exceeded | `budget_exceeded` | `{ budget: 'latency', limit, actual }` |
| `BUDGET_COST_EXCEEDED` | Cost budget exceeded | `budget_exceeded` | `{ budget: 'cost', limit, actual }` |
| `SESSION_NOT_FOUND` | Session not found | `session_config` | `{ reason: 'session_not_found', taskId? }` |
| `LIMIT_MAX_PROMPTS_EXCEEDED` | Max prompts limit exceeded | `session_config` | `{ reason: 'limit_max_prompts_exceeded', limit?, actual? }` |

Types are exported from `@a2arium/callagent-core`: `InvariantErrorCode`, `InvariantErrorDetail`, `InvariantErrorContext`.

## Breaking Changes

### 1. `BaseError` Update
The `BaseError` class now uses a strictly typed `Record<string, unknown>` for its `details` property instead of `any`.

### 2. `InvariantError` and `ModuleExecutionError` Classes
These classes now inherit from `BaseError`. Their constructors have changed to enforce structured payloads. `InvariantError` has an `invariant` (or `payload`) property with `code`, `message`, `detail`, and optional `stage`, `correlationId`, `turnId`.

### 3. `TaskContext.throw` Signature
The `ctx.throw` method is now strictly typed to require an `InvariantErrorCode`, a message, a discriminated union of `InvariantErrorDetail`, and an optional `InvariantErrorContext` (stage, correlationId, turnId). All runtime implementations (streaming, runner, task engine) delegate to `throwInvariantError()`, so `instanceof InvariantError` is reliable across execution paths.

### 4. Observation validation behavior
Invalid observation envelopes are **no longer thrown** as `OBSERVATION_VALIDATION_FAILED`. The framework now injects a `source: 'internal', kind: 'validation.failed'` observation into the inbox so Perception and Learning can handle them. This aligns with the APLRET contract and avoids failing the turn on malformed data. **If your code previously caught `OBSERVATION_VALIDATION_FAILED` in a try/catch, that path will no longer run** — you must handle validation failures in your Perception or Learning module by inspecting `env.inbox.current` for observations with `kind === 'validation.failed'`.

## Migration Steps

### For Agent Developers

#### Update `ctx.throw` Usage
If your agent explicitly throws invariant errors using `ctx.throw`, you must update the arguments to match the new types.

**Before:**
```typescript
ctx.throw('CUSTOM_CODE', 'Something went wrong', { extra: 'data' });
```

**After:** Use one of the allowed codes and the matching detail shape. Example for goal invariant:
```typescript
ctx.throw(
    'GOAL_NOT_FOUND',
    'Goal not found',
    { type: 'goal_invariant', reason: 'goal_not_found', goalId: targetGoalId }
);
```

Example for budget:
```typescript
ctx.throw(
    'BUDGET_TURNS_EXCEEDED',
    'Max turns reached',
    { type: 'budget_exceeded', budget: 'turns', limit: 50, actual: 50 }
);
```

> [!NOTE]
> `ctx.throw` is now restricted to framework-defined `InvariantErrorCode`s and shapes. If you need to throw custom errors from an agent, use a regular `throw new Error()` or define a custom error class extending `BaseError`.

#### Catching and inspecting invariant errors
Replace message-based checks with code and detail.

**Before:**
```typescript
try {
    await runAgent(ctx);
} catch (e) {
    if (e instanceof Error && e.message.includes('budget')) {
        // retry with smaller scope
    }
    throw e;
}
```

**After:**
```typescript
import { InvariantError } from '@a2arium/callagent-core';

try {
    await runAgent(ctx);
} catch (e) {
    if (e instanceof InvariantError && e.code === 'BUDGET_TURNS_EXCEEDED') {
        const detail = e.detail;
        if (detail.type === 'budget_exceeded' && detail.budget === 'turns') {
            const { limit, actual } = detail;
            // retry with smaller scope using limit/actual
        }
    }
    throw e;
}
```

#### Observation validation: from throw to inbox
If you previously caught observation validation errors:

**Before:** Try/catch around a call that could throw `OBSERVATION_VALIDATION_FAILED`.

**After:** Do not rely on a thrown error. In your **Perception** or **Learning** module, check the current inbox for a validation failure observation and handle it (e.g. log, skip, or update mental state):

```typescript
// In perception or learning: inspect env.inbox.current
const validationFailed = env.inbox.current?.find(
    (o) => o.source === 'internal' && (o as { kind?: string }).kind === 'validation.failed'
);
if (validationFailed) {
    // handle: e.g. log payload, return safe default, or apply a recovery state
}
```

### Real-world scenario: agent that retries on budget exceeded

**Before (v3.2):**
```typescript
async function runWithRetry(ctx, task) {
    try {
        return await engine.startTask({ task, ... });
    } catch (e) {
        if (e?.message?.includes('turn') && e?.message?.includes('exceeded')) {
            return runWithRetry(ctx, { ...task, budget: { maxTurns: 10 } });
        }
        throw e;
    }
}
```

**After (v3.3):**
```typescript
import { InvariantError } from '@a2arium/callagent-core';

async function runWithRetry(ctx, task) {
    try {
        return await engine.startTask({ task, ... });
    } catch (e) {
        if (e instanceof InvariantError && e.code === 'BUDGET_TURNS_EXCEEDED') {
            const d = e.detail;
            if (d.type === 'budget_exceeded' && d.budget === 'turns') {
                return runWithRetry(ctx, { ...task, budget: { maxTurns: Math.max(5, d.limit - 10) } });
            }
        }
        throw e;
    }
}
```

### For Framework Contributors

The following is for **framework and package contributors** only. If you are only implementing or migrating an agent, you can skip this section.

#### Using `throwInvariantError`
Always use the `throwInvariantError` factory instead of manual `new InvariantError()` calls to ensure correct payload construction.

```typescript
import { throwInvariantError } from '@a2arium/callagent-core';

throwInvariantError(
    'BUDGET_TURNS_EXCEEDED',
    'Max turns reached',
    { type: 'budget_exceeded', budget: 'turns', limit: 50, actual: 50 }
);
```

#### Handling Module Failures
When a framework module (Perception, Policy, etc.) fails, wrap the error in a `ModuleExecutionError`. If the caught error is already an `InvariantError`, rethrow it unchanged so callers can inspect `e.invariant`.

```typescript
try {
    // ... execution logic
} catch (error) {
    if (error instanceof InvariantError) throw error;
    throw new ModuleExecutionError(
        FrameworkModule.Execution,
        error instanceof Error ? error.message : String(error),
        error instanceof Error ? error : undefined
    );
}
```

## Verification

To verify your migration, ensure that:
1. All TypeScript compilation errors related to `ctx.throw` are resolved (use the error code catalog and detail shapes above).
2. Unit tests that were previously asserting generic `Error` types or message substrings now assert `InvariantError` (or `ModuleExecutionError`) and inspect `code` and `detail` where appropriate.
3. Any handling that relied on catching observation validation errors has been moved to Perception/Learning inbox inspection.
4. Your logs now contain structured `code` and `detail` fields for framework errors.

## Data migration

Persisted snapshots and logs that contain old error objects (plain `Error` with only a message) are not automatically migrated. The new error shapes apply only to **new** throws. If you persist error payloads for debugging or analytics, update your serialization to use the new `InvariantError` payload shape; existing stored data remains as-is and can still be read as before.
