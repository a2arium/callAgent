# Migration Guide 2.4: `Intent` vs `ProposedAction`

As part of the 2.4 release and our alignment with the APLRET 2.0 specifications, the `ProposedAction` type has been completely removed from the framework. It is replaced by a strictly-typed Zod schema called `Intent`.

This is a **breaking change** and there is no backwards compatibility for `ProposedAction`. You must update your agents to use the new `Intent` types.

## Motivation

The framework previously used a loosely typed `ProposedAction` interface that allowed arbitrary fields. This led to ambiguity in module boundaries (especially between Policy and Execution) and made it difficult to enforce the single-writer rule and deterministic execution required by the APLRET architecture.

By migrating to a Zod-backed `Intent` discriminated union, we ensure:
1. **Strict Type Safety:** The shape of every intent is validated at runtime and compile-time.
2. **Clear Boundaries:** Modules emit well-defined intentions that the Execution module explicitly knows how to handle.
3. **No "Any":** The `any` type is completely eliminated from the intention pipeline.

## Migration Steps

### 1. Update Imports

If your agent or custom module imports `ProposedAction`, update the import to pull in `Intent` instead.

**Before:**
```typescript
import { ProposedAction } from '@a2arium/callagent-core';
```

**After:**
```typescript
import { Intent } from '@a2arium/callagent-core';
```

*(Note: `ExecutableAction` is also available and represents the subset of intents that the Execution layer directly handles, excluding internal intents like `noop` or `vetoed`.)*

### 2. Update Intent Mappings (The `kind` Property)

The `kind` property of actions has been refined and renamed to map directly to core primitives. You must update your policy outputs to return the correct new shapes:

| Old `ProposedAction` Kind | New `Intent` Kind | Required Fields |
| :--- | :--- | :--- |
| `tool` | `call_tool` | `toolName: string, args: Record<string, unknown>` |
| `ask_user` | `prompt_user` | `prompt: string, schema?: Record<string, unknown>` |
| `subagent` | `delegate_to_child` | `agentId: string, input: unknown` |
| `language` | `answer_with_llm` | `query: string` |
| *(custom/internal)* | `internal` | `intent: string` |

#### Example: Returning a Tool Call

**Before:**
```typescript
policy: (m) => {
    return { kind: 'tool', name: 'my-tool', args: { foo: 'bar' } };
}
```

**After (Note 'toolName' instead of 'name'):**
```typescript
policy: (m) => {
    return { kind: 'call_tool', toolName: 'my-tool', args: { foo: 'bar' } };
}
```

#### Example: Prompting the User

**Before:**
```typescript
policy: (m) => {
    return { kind: 'ask_user', prompt: 'Are you sure?', expectedShape: { confirm: 'boolean' } };
}
```

**After (Note 'schema' instead of custom fields):**
```typescript
policy: (m) => {
    return { kind: 'prompt_user', prompt: 'Are you sure?', schema: { type: 'boolean' } }; // using JSONSchema7 shape
}
```

### 3. Update Custom Shields or Modules Processing Actions

If you have custom `shield` or `learning` modules or intercept the action execution, update your logic to match the new `Intent` union types. `Intent` is strongly typed; attempting to access `a.name` on a `call_tool` intent will now cause a TypeScript error because the field is `toolName`.

```typescript
// Example Shield Validation
shield: (m, action) => {
    if (action.kind === 'call_tool' && action.toolName === 'delete-database') {
        return { action: 'veto' };
    }
    return { action: 'pass', intent: action };
}
```

### 4. Remove 'Any' Casts

Take the time to remove any `as any` or `as ProposedAction` casts and rely on the inferred Zod schema types. This will catch mismatches early and ensure your agent aligns with the cognitive loop's strict boundaries.
